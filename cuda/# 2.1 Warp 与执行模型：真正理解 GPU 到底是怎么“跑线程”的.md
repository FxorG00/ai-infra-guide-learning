# 2.1 Warp 与执行模型：真正理解 GPU 到底是怎么“跑线程”的

这一篇非常重要。

前面我们已经知道：

```text
Kernel
↓
Grid
↓
Block
↓
Thread
```

这是 CUDA 给程序员看的：

```text
编程模型
```

但是到了这一篇，我们要开始往硬件层继续往下看：

> **GPU 实际执行的时候，并不是一个 Thread 一个 Thread 单独调度。**

真正非常核心的执行单位叫：

```text
Warp
```

所以这一篇的主线其实可以概括成：

```text
Thread Block
↓
被分配到 SM
↓
Block 内 Thread 自动划分成 Warp
↓
Warp Scheduler 调度 Warp
↓
Warp 中的线程按照 SIMT 模型执行
```

然后由此引出几个非常重要的性能问题：

```text
Warp Divergence
Warp Shuffle
Warp Vote
Warp-level Reduction
```

---

# 一、Warp 到底是什么？

最简单的一句话：

> **Warp 是 NVIDIA GPU 硬件调度和执行线程时的基本单位之一。**

一个 Warp 固定包含：

$$
32
$$

个 Thread。

比如一个 Block：

```text
256 Threads
```

硬件会自动把它划分成：

```text
Warp 0:
Thread 0 ~ 31

Warp 1:
Thread 32 ~ 63

Warp 2:
Thread 64 ~ 95

Warp 3:
Thread 96 ~ 127

Warp 4:
Thread 128 ~ 159

Warp 5:
Thread 160 ~ 191

Warp 6:
Thread 192 ~ 223

Warp 7:
Thread 224 ~ 255
```

所以：

$$
256 / 32 = 8
$$

也就是：

```text
256-thread Block
=
8 个 Warp
```

---

# 二、Warp 是程序员自己创建的吗？

不是。

这点非常重要。

你启动 Kernel 时写的是：

```cpp
kernel<<<gridSize, blockSize>>>(...);
```

例如：

```cpp
kernel<<<100, 256>>>(...);
```

你只告诉 CUDA：

```text
100 个 Block

每个 Block 256 个 Thread
```

你并没有写：

```text
我要创建 8 个 Warp
```

Warp 的划分是：

> **GPU 硬件自动完成的。**

所以：

```text
Grid / Block / Thread

是 CUDA 编程模型中你直接操作的层级。
```

而：

```text
Warp

更多是硬件执行层面的概念。
```

---

# 三、Warp 怎么划分 Thread？

按照 Thread ID 顺序连续划分。

例如：

```text
Thread 0 ~ 31
→ Warp 0

Thread 32 ~ 63
→ Warp 1

Thread 64 ~ 95
→ Warp 2
```

所以一个简单的 Warp ID 可以写成：

```cpp
int warpId = threadIdx.x / 32;
```

而一个 Thread 在自己 Warp 内的位置：

```cpp
int laneId = threadIdx.x % 32;
```

---

# 四、lane 是什么？

Warp 里面有 32 个 Thread。

我们通常把这 32 个位置叫：

```text
lane 0
lane 1
lane 2
...
lane 31
```

例如：

```text
Thread 64
```

它属于：

```text
Warp 2
```

因为：

$$
64 / 32 = 2
$$

同时：

$$
64 \bmod 32 = 0
$$

所以它是：

```text
Warp 2
Lane 0
```

再比如：

```text
Thread 70
```

那么：

$$
70 / 32 = 2
$$

$$
70 \bmod 32 = 6
$$

所以：

```text
Warp 2
Lane 6
```

---

# 五、为什么 Block Size 经常选 32 的倍数？

现在你应该真正理解之前那个经验规则了。

比如：

```text
blockSize = 256
```

那么：

$$
256 / 32 = 8
$$

刚好是：

```text
8 个完整 Warp
```

但如果：

```text
blockSize = 48
```

那么：

```text
Thread 0 ~ 31
→ Warp 0

Thread 32 ~ 47
→ Warp 1
```

第二个 Warp 实际只有：

```text
16 个有效 Thread
```

但是硬件执行 Warp 时仍然按照 Warp 的组织方式处理。

也就是说剩下很多 lane：

```text
没有有效 Thread
```

这就会造成硬件资源浪费。

所以通常：

> **Block Size 尽量选择 32 的整数倍。**

常见：

```text
128
256
512
```

但这不代表：

```text
256 永远最快
```

只是 32 的倍数通常是一个基本要求。

---

# 六、现在真正进入硬件：Block 怎么跑到 GPU 上？

你可以先把 GPU 想成：

```text
GPU
│
├── SM 0
├── SM 1
├── SM 2
├── SM 3
└── ...
```

Kernel 启动后产生：

```text
Grid
↓
很多 Block
```

这些 Block 会被分配到不同 SM。

例如：

```text
Block 0 → SM 0
Block 1 → SM 1
Block 2 → SM 2
Block 3 → SM 3
Block 4 → SM 0
...
```

Block 到了 SM 以后：

```text
Block
↓
拆成多个 Warp
↓
Warp Scheduler 调度 Warp
```

---

# 七、所以千万不要建立这个错误理解

不要想成：

```text
Thread 0
→ CUDA Core 0

Thread 1
→ CUDA Core 1

Thread 2
→ CUDA Core 2
```

并不是这种：

```text
1 Thread = 1 CUDA Core
```

的固定绑定关系。

更准确的思维应该是：

```text
Thread
↓
组成 Warp
↓
Warp 被 SM 调度
↓
Warp 的指令被发射到执行单元
```

所以硬件视角下：

```text
Warp
```

比单独 Thread 更重要。

---

# 八、Warp Scheduler 是什么？

一个 SM 上会有 Warp Scheduler。

它的任务可以理解成：

> **从当前已经准备好的 Warp 中，选一个出来执行下一条指令。**

例如 SM 上现在驻留：

```text
Warp A
Warp B
Warp C
Warp D
Warp E
...
```

Warp Scheduler 会不断寻找：

```text
Ready Warp
```

也就是：

> 当前有条件继续执行的 Warp。

---

# 九、为什么需要很多 Warp 同时待在一个 SM 上？

因为某个 Warp 不一定一直有活干。

比如：

```text
Warp A
```

发出一条 Global Memory Load：

```text
从 HBM 读取数据
```

HBM 很远。

数据回来可能需要很多 cycle。

这时候：

```text
Warp A
```

暂时不能继续执行。

如果整个 SM 只有 Warp A：

```text
计算资源就只能干等。
```

但是 GPU 不这么干。

---

# 十、GPU 怎么隐藏 Memory Latency？

假设：

```text
Warp A
```

发出：

```text
Load data from HBM
```

然后等待数据。

Scheduler 可以马上切到：

```text
Warp B
```

执行。

然后：

```text
Warp B
```

也开始等数据，

再切：

```text
Warp C
```

于是：

```text
Warp A:
等待 Memory

Warp B:
执行计算

Warp C:
准备执行

Warp D:
准备执行
```

等 Scheduler 绕一圈以后：

```text
Warp A 的数据可能已经回来了
```

于是再回来执行 Warp A。

---

# 十一、这就叫 Latency Hiding

核心不是：

> **把 HBM Latency 消灭。**

Latency 还是存在。

而是：

> **一个 Warp 等数据的时候，让别的 Warp 干活。**

这就叫：

```text
Latency Hiding
```

可以画成：

```text
Warp A:
Load → 等等等等等 → Compute

Warp B:
      Compute → Load → 等等等

Warp C:
                Compute → ...

Warp D:
                        Compute
```

最终 SM 尽可能保持忙碌。

---

# 十二、Warp 切换为什么比 CPU Thread 切换便宜？

CPU 做线程切换的时候，经常需要涉及：

```text
保存状态
恢复状态
切换上下文
```

这有明显成本。

而 GPU 上：

> 多个驻留 Warp 的状态本来就保存在 SM 上。

比如：

```text
Register State
Program State
```

因此 Scheduler 从 Warp A 换到 Warp B：

```text
不需要像 CPU 那样进行昂贵的上下文保存 / 恢复。
```

所以 GPU 很适合：

```text
同时保持大量 Warp
↓
不断在 Ready Warp 之间调度
↓
隐藏 Memory Latency
```

---

# 十三、这和 Occupancy 开始连起来了

你前面已经听过：

```text
Occupancy
```

现在可以稍微理解得更深一点。

假设一个 SM：

```text
理论上最多可以驻留很多 Warp
```

但你的 Kernel 因为：

```text
Register 用太多

Shared Memory 用太多

Block Size 不合适
```

导致实际只驻留：

```text
很少的 Warp
```

那么可能出现：

```text
Warp A 等 HBM
Warp B 也等 HBM
```

然后：

```text
没有其他 Warp 可以调度
```

SM 就真的闲下来了。

所以：

> **足够多的 Active Warp，有助于隐藏延迟。**

这也是 Occupancy 为什么重要。

但具体 Occupancy 会在 2.3 再详细学。

---

# 十四、接下来进入 SIMT

NVIDIA GPU 的执行模型叫：

```text
SIMT
```

全称：

```text
Single Instruction
Multiple Threads
```

中文：

```text
单指令，多线程
```

---

# 十五、SIMT 的核心思想是什么？

你写 CUDA 的时候，写的是：

```cpp
int idx =
    blockIdx.x * blockDim.x
    + threadIdx.x;

C[idx] = A[idx] + B[idx];
```

看起来你写的是：

> **一个 Thread 应该做什么。**

但是硬件执行的时候：

```text
Warp 内 32 个 Thread
```

会一起执行：

```cpp
C[idx] = A[idx] + B[idx];
```

只不过每个 Thread 的：

```text
idx
```

不同。

所以：

```text
Thread 0:
C[0] = A[0] + B[0]

Thread 1:
C[1] = A[1] + B[1]

Thread 2:
C[2] = A[2] + B[2]

...

Thread 31:
C[31] = A[31] + B[31]
```

---

# 十六、所以 SIMT 可以怎么理解？

一句话：

> **你按“一个 Thread”的方式写标量代码，GPU 把它放到很多 Thread 上并行执行。**

也就是：

```text
程序员视角：

写一个 Thread 的程序


硬件视角：

一个 Warp 里很多 Thread 一起执行这条指令
```

这就是 CUDA 编程很舒服的一点。

---

# 十七、SIMT 和 SIMD 有什么区别？

这篇文章专门对比了：

```text
SIMT
```

和：

```text
SIMD
```

SIMD：

```text
Single Instruction
Multiple Data
```

典型例子：

```text
CPU AVX
AVX2
AVX-512
```

SIMD 更多是：

> 一条 Vector Instruction 操作一个 Vector Register 里的多个元素。

例如：

```text
一条指令
↓
同时加 8 个 float
```

程序员看到的是：

```text
Vector
```

---

# 十八、SIMT 更像什么？

SIMT 中：

```text
Thread 0
Thread 1
Thread 2
...
```

在编程模型里是：

```text
独立 Thread
```

每个 Thread 可以有自己的：

```text
Register

Thread ID

Memory Address

逻辑状态
```

所以程序员写起来更像：

```text
普通标量程序
```

但是 GPU 硬件把它们成组执行。

---

# 十九、SIMT 最大的问题也因此出现了

既然一个 Warp：

```text
32 个 Thread
```

最好一起执行同一条指令。

那如果它们突然说：

```text
Thread 0:
我要执行 A

Thread 1:
我要执行 B

Thread 2:
我要执行 A

Thread 3:
我要执行 B
```

怎么办？

这就是：

```text
Warp Divergence
```

---

# 二十、Warp Divergence 到底是什么？

假设 Kernel：

```cpp
if (tid % 2 == 0) {
    do_A();
} else {
    do_B();
}
```

一个 Warp：

```text
Thread 0 → A
Thread 1 → B
Thread 2 → A
Thread 3 → B
...
```

那么同一个 Warp 内：

```text
一半 Thread 想执行 A

另一半 Thread 想执行 B
```

但 Warp 同一时刻不能：

```text
一半执行 A 指令
+
另一半同时执行完全不同的 B 指令
```

于是只能把路径拆开执行。

---

# 二十一、Warp Divergence 怎么执行？

可以粗略理解成：

```text
第一阶段：

执行 A 路径

偶数 Thread：
Active

奇数 Thread：
Masked Off
```

然后：

```text
第二阶段：

执行 B 路径

偶数 Thread：
Masked Off

奇数 Thread：
Active
```

所以：

```text
A 路径
+
B 路径
```

都得执行一遍。

---

# 二十二、Masked Off 是什么意思？

就是：

> 当前这条指令发出来了，但某些 lane 不参与有效计算。

例如：

```text
Warp 有 32 个 lane

执行 A 路径时：

16 active
16 inactive
```

于是 GPU 的执行资源没有完全利用。

---

# 二十三、一个经典 Divergence 例子

例如：

```cpp
if (threadIdx.x % 2 == 0) {
    y = expf(x);
} else {
    y = logf(x);
}
```

一个 Warp：

```text
Lane 0  → exp
Lane 1  → log
Lane 2  → exp
Lane 3  → log
...
```

于是：

```text
执行 exp 路径
↓
只有一半 lane 工作

执行 log 路径
↓
另一半 lane 工作
```

如果两个路径工作量差不多，

整体可能接近：

```text
两个路径都执行一遍的成本
```

---

# 二十四、是不是所有 if 都很慢？

不是。

这是非常重要的。

问题不是：

```text
代码里出现 if
```

问题是：

> **同一个 Warp 内的 Thread 是否走不同路径。**

比如：

```cpp
if (threadIdx.x / 32 == 0) {
    do_A();
} else {
    do_B();
}
```

那么：

```text
Warp 0:
所有 32 Thread → A

Warp 1:
所有 32 Thread → B
```

Warp 0 内部没有分歧。

Warp 1 内部也没有分歧。

所以这就比：

```cpp
threadIdx.x % 2
```

舒服得多。

---

# 二十五、所以真正应该避免的是

不是：

```text
Branch
```

本身。

而是：

```text
Intra-Warp Divergence
```

也就是：

> **同一个 Warp 内产生不同控制流。**

这个区别一定记住。

---

# 二十六、为什么数据布局也会影响 Divergence？

假设你有：

```text
正数
负数
正数
负数
正数
负数
...
```

然后：

```cpp
if (x > 0) {
    path_A();
} else {
    path_B();
}
```

那么一个 Warp 很可能：

```text
一半正数
一半负数
```

于是发生 Divergence。

但如果提前把数据整理成：

```text
正数 正数 正数 正数 ...
负数 负数 负数 负数 ...
```

那么：

```text
前面的 Warp
几乎全部走 A

后面的 Warp
几乎全部走 B
```

Divergence 就减少了。

所以 GPU 优化经常不仅改：

```text
代码
```

还会改：

```text
数据布局
```

---

# 二十七、文章给出的 Divergence 规避思路

主要包括：

```text
1. 让分支和 Warp 对齐

2. 某些简单情况用算术操作替代 Branch

3. 重排数据，让同类数据聚在一起

4. 尽量统一循环结构
```

核心目标其实只有一个：

> **让一个 Warp 内的 Thread 尽量执行相同控制流。**

---

# 二十八、为什么循环也会发生 Divergence？

例如：

```cpp
for (
    int i = 0;
    i < length[tid];
    ++i
) {
    ...
}
```

不同 Thread：

```text
Thread 0:
循环 3 次

Thread 1:
循环 20 次

Thread 2:
循环 5 次
```

那么：

```text
Thread 0 很早退出

Thread 2 后面退出

Thread 1 还在继续
```

到后面可能只有：

```text
少数 lane 还 Active
```

这也是 Divergence。

所以 Warp Divergence 并不只发生在：

```text
if / else
```

也可以发生在：

```text
switch

不同次数循环

不同提前退出条件
```

---

# 二十九、Volta 之后为什么还要讲 Independent Thread Scheduling？

文章这里提到了：

```text
Independent Thread Scheduling
```

从 Volta 架构开始，

Warp 内 Thread 的调度能力变得更加灵活。

Thread 可以拥有更独立的：

```text
Program Counter

Execution State
```

因此：

```text
不同 Thread 可以处在不同程序位置
```

调度器能够更灵活地处理这些情况。

---

# 三十、那 Independent Thread Scheduling 会不会消灭 Divergence？

不会。

这个一定要注意。

它只是：

> **让 Warp 内不同 Thread 的调度更加灵活。**

但如果：

```text
16 个 Thread 执行 A

16 个 Thread 执行 B
```

你依然没办法凭空获得：

```text
32 个 lane 全部有效工作
```

所以：

```text
Warp Divergence 的性能问题仍然存在。
```

---

# 三十一、接下来进入 Warp Shuffle

这一部分非常重要。

你前面已经学过：

```text
Shared Memory
```

如果 Thread A 想把自己的值给 Thread B，

以前可以：

```text
Thread A
↓
写 Shared Memory
↓
__syncthreads()
↓
Thread B
↓
读 Shared Memory
```

问题是：

```text
需要 Shared Memory

需要同步

需要额外 Memory Operation
```

---

# 三十二、Warp Shuffle 干什么？

Warp Shuffle 允许：

> **同一个 Warp 内，一个 Thread 直接读取另一个 Thread 的 Register 值。**

数据路径可以想成：

```text
Thread A Register
        ↓
   Warp Shuffle
        ↓
Thread B Register
```

而不是：

```text
Register
↓
Shared Memory
↓
同步
↓
Shared Memory
↓
Register
```

所以它非常适合 Warp 内通信。

---

# 三十三、最基础的 Shuffle：__shfl_sync

```text
lane: 一个 warp 内部线程的编号。
一个 warp 通常有 32 个线程，所以 laneId=0~31；
Lane[0] 就对应第 0 个；Lane[31] 就对应第 31 个。 
```

基本形式：

```cpp
__shfl_sync(
    mask,
    var,
    srcLane
);
```

可以理解成：

> **从 srcLane 那个 Thread 那里，把它的 var 拿过来。**

例如：

```cpp
float x =
    __shfl_sync(
        0xffffffff,
        value,
        0
    );
```

意思是：

> Warp 内参与的 Thread 都读取 Lane 0 的 `value`。

---

# 三十四、这就是 Warp Broadcast

例如初始：

```text
Lane 0: value = 100
Lane 1: value = 20
Lane 2: value = 30
Lane 3: value = 40
```

执行：

```cpp
value =
    __shfl_sync(
        0xffffffff,
        value,
        0
    );
```

之后：

```text
Lane 0 → 100
Lane 1 → 100
Lane 2 → 100
Lane 3 → 100
...
```

Lane 0 的 Register 值被广播给 Warp 中的 Thread。

---

# 三十五、0xffffffff 是什么？

Shuffle API 第一个参数：

```cpp
mask
```

代表：

> **哪些 lane 参与这次 Warp-level 操作。**

一个 Warp 有：

```text
32 个 lane
```

所以可以用一个：

```text
32-bit integer
```

每一位对应一个 lane。

```text
0xffffffff
```

二进制就是：

```text
11111111111111111111111111111111
```

也就是：

```text
32 个 bit 全部为 1
```

表示：

> **Warp 的 32 个 lane 全部参与。**

---

# 三十六、四种 Shuffle

文章介绍了四种：

```cpp
__shfl_sync
```

```cpp
__shfl_up_sync
```

```cpp
__shfl_down_sync
```

```cpp
__shfl_xor_sync
```

你现在最重要的是理解它们的方向。

---

# 三十七、__shfl_sync

```cpp
__shfl_sync(mask, var, srcLane)
```

意思：

> **直接指定我要读哪个 Lane。**

例如：

```cpp
__shfl_sync(mask, x, 0);
```

就是：

```text
读取 Lane 0 的 x
```

---

# 三十八、__shfl_down_sync

```cpp
__shfl_down_sync(
    mask,
    var,
    offset
);
```

当前 Lane 会去读取：

```text
Lane ID + offset
```

位置的值。

例如：

```text
offset = 2
```

那么：

```text
Lane 0 ← Lane 2

Lane 1 ← Lane 3

Lane 2 ← Lane 4

Lane 3 ← Lane 5
...
```

这个操作后面做：

```text
Reduction
```

非常好用。

---

# 三十九、__shfl_up_sync

方向反过来：

```text
Lane ID - offset
```

例如：

```text
Lane 4 ← Lane 2

Lane 5 ← Lane 3
```

它以后做：

```text
Prefix Sum
Scan
```

很常见。

---

# 四十、__shfl_xor_sync

这个稍微特别一点。

它读取：

$$
\mathrm{srcLane}
=
\mathrm{laneId}
\oplus
\mathrm{laneMask}
$$

其中：

```text
⊕
```

是：

```text
XOR
```

例如：

```cpp
__shfl_xor_sync(
    mask,
    value,
    1
);
```

会形成：

```text
Lane 0 ↔ Lane 1

Lane 2 ↔ Lane 3

Lane 4 ↔ Lane 5
...
```

因为：

```text
0 XOR 1 = 1
1 XOR 1 = 0

2 XOR 1 = 3
3 XOR 1 = 2
```

这种模式特别适合：

```text
蝶形通信
```

# 四十一、Warp Shuffle 最经典的应用：Reduction

假设一个 Warp 的 32 个 Thread：

```text
Lane 0 有一个值
Lane 1 有一个值
...
Lane 31 有一个值
```

我们想：

```text
把 32 个值加起来
```

最直观的方法可以用：

```text
Shared Memory
```

但 Warp Shuffle 可以直接在 Register 之间传值。

---

# 四十二、Warp Reduction 的核心代码

```cpp
float warp_reduce_sum(float val) {

    for (
        int offset = 16;
        offset > 0;
        offset >>= 1
    ) {
        val +=
            __shfl_down_sync(
                0xffffffff,
                val,
                offset
            );
    }

    return val;
}
```

第一次看到会有点抽象。

我们用 8 个 Thread 简化理解。

---

# 四十三、假设只有 8 个 Lane

初始：

```text

Lane 1: 2

Lane 2: 3

Lane 3: 4

Lane 4: 5

Lane 5: 6

Lane 6: 7

Lane 7: 8
```

我们最终想得到：

$$
1+2+3+4+5+6+7+8=36
$$

```text
Lane 0
读取 Lane 4
```

所以：

$$
1+5=6
$$

Lane 1：

$$
2+6=8
$$

Lane 2：

$$
3+7=10
$$

Lane 3：

$$
4+8=12
$$

现在前四个 Lane：

```text
6
8
10
12
```

---

# 四十五、第二轮 offset = 2

Lane 0：

```text
当前是 6
```

读取 Lane 2：

```text
10
```

得到：

$$
6+10=16
$$

Lane 1：

$$
8+12=20
$$

于是：

```text
Lane 0: 16
Lane 1: 20
```

---

# 四十六、第三轮 offset = 1

Lane 0：

```text
16
```

再读取 Lane 1：

```text
20
```

所以：

$$
16+20=36
$$

最终：

```text
Lane 0
```

得到整个 Warp 的和。

# 四十七、为什么 Reduction 只需要 log2(N) 步？

因为每一轮有效范围减半：

```text
32
↓
16
↓
8
↓
4
↓
2
↓
1
```

所以 32 个 Thread：

$$
\log_2 32 = 5
$$

轮。

对应：

```text
offset = 16

offset = 8

offset = 4

offset = 2

offset = 1
```

# 四十八、这为什么比 Shared Memory 版本舒服？

Shared Memory 版本可能需要：

```text
写 Shared Memory
↓
__syncthreads()
↓
读 Shared Memory
↓
再写
↓
再同步
...
```

Warp Shuffle：

```text
Register
↓
Register
```

直接交换。

因此可以：

```text
减少 Shared Memory 使用

减少同步

减少指令
```

这也是后面 Reduce 优化的重要基础。

# 四十九、注意：Warp Shuffle 只能 Warp 内通信

这是一个重要限制。

例如：

```text
Warp 0
```

不能直接通过：

```cpp
__shfl_sync(...)
```

读取：

```text
Warp 1
```

的 Register。

Shuffle 的通信范围：

```text
同一个 Warp
```

所以如果：

```text
整个 Block 有 256 Thread
=
8 Warp
```

而你想做：

```text
整个 Block Reduction
```

就需要：

```text
第一步：

每个 Warp 自己 Reduce
```

然后：

```text
第二步：

8 个 Warp 的结果再合并
```

这就是文章最后的 Block Reduction。

# 五十、Warp Vote 又是什么？

文章接下来介绍：

```cpp
__all_sync
```

```cpp
__any_sync
```

```cpp
__ballot_sync
```

它们不是用来搬浮点值。

它们是在做：

> **Warp 内对一个布尔条件进行集体判断。**

---

# 五十一、__all_sync

```cpp
__all_sync(mask, predicate)
```

意思：

> 参与的所有 Lane 的 predicate 都是 true 吗？

例如：

```text
32 Thread
全部满足 x > 0
```

返回：

```text
true
```

如果哪怕一个不满足：

```text
false
```

---

# 五十二、__any_sync

```cpp
__any_sync(mask, predicate)
```

意思：

> 只要有任何一个 Lane 的 predicate 为 true，就返回 true。

例如：

```text
Warp 中有没有 Thread 找到目标？
```

就可以：

```cpp
int found =
    __any_sync(
        mask,
        data[tid] == target
    );
```

---

# 五十三、__ballot_sync

这个更有意思。

```cpp
__ballot_sync(
    mask,
    predicate
);
```

返回：

```text
一个 32-bit Mask
```

其中：

```text
bit 0 → Lane 0 的 predicate

bit 1 → Lane 1 的 predicate

...

bit 31 → Lane 31 的 predicate
```

比如：

```text
Lane 0: true
Lane 1: false
Lane 2: true
Lane 3: true
```

结果低四位可能是：

```text
1101
```

于是整个 Warp：

> 哪些 Thread 满足条件，一次就知道了。

---

# 五十四、__activemask() 是什么？

```cpp
__activemask()
```

会返回：

> **当前 Warp 里哪些 Lane 是 Active 的。**

例如发生 Divergence 后，

可能：

```text
Lane 0 ~ 15 Active

Lane 16 ~ 31 Inactive
```

那么 Active Mask 就会反映这个状态。

---

# 五十五、__syncwarp() 又是什么？

```cpp
__syncwarp(mask);
```

可以理解成：

> **指定 Warp 内这些 Lane 在这里进行同步。**

这个概念在 Volta 之后尤其重要。

因为有 Independent Thread Scheduling 后，

不能再随便假设：

```text
Warp 内所有 Thread 永远严格 lockstep 到每一个代码位置。
```

因此在某些 Warp-level 数据依赖场景里，需要显式：

```cpp
__syncwarp();
```

---

# 五十六、width 参数是什么？

Shuffle 还有一个参数：

```cpp
width
```

例如：

```cpp
__shfl_down_sync(
    mask,
    value,
    offset,
    8
);
```

这个：

```text
8
```

意味着：

> 把一个 32-thread Warp 逻辑上拆成多个 8-thread 子组。

也就是：

```text
Lane 0 ~ 7
一个组

Lane 8 ~ 15
一个组

Lane 16 ~ 23
一个组

Lane 24 ~ 31
一个组
```

每组内部独立做 Shuffle。

---

# 五十七、现在看文章最后的 Block Reduction

假设：

```text
Block Size = 256
```

那么：

$$
256 / 32 = 8
$$

也就是：

```text
8 个 Warp
```

目标：

> 把 256 个 Thread 的值全部加起来。

---

# 五十八、第一步：每个 Warp 自己 Reduce

每个 Thread：

```cpp
float val = input[tid];
```

然后：

```cpp
val = warp_reduce_sum(val);
```

于是：

```text
Warp 0 Lane 0
→ Warp 0 的 Sum

Warp 1 Lane 0
→ Warp 1 的 Sum

...

Warp 7 Lane 0
→ Warp 7 的 Sum
```

现在 256 个值：

```text
变成了 8 个值
```

---

# 五十九、第二步：Lane 0 把结果写进 Shared Memory

声明：

```cpp
__shared__ float warp_sums[32];
```

为什么最多 32？

因为一个 Block 最大通常：

```text
1024 Threads
```

而：

$$
1024 / 32 = 32
$$

所以最多：

```text
32 个 Warp
```

---

# 六十、只有每个 Warp 的 Lane 0 写入

代码：

```cpp
int laneId =
    threadIdx.x % 32;

int warpId =
    threadIdx.x / 32;
```

然后：

```cpp
if (laneId == 0) {
    warp_sums[warpId] = val;
}
```

于是：

```text
warp_sums[0]
=
Warp 0 Sum

warp_sums[1]
=
Warp 1 Sum

...

warp_sums[7]
=
Warp 7 Sum
```

---

# 六十一、为什么这里需要 __syncthreads()？

因为：

```text
8 个 Warp
```

可能执行速度不完全一致。

必须确保：

```text
所有 Warp 的 Lane 0
```

都把自己的结果写完以后，

才能进行下一步。

所以：

```cpp
__syncthreads();
```

---

# 六十二、第三步：让第一个 Warp 再 Reduce 一次

现在只剩：

```text
8 个数
```

于是让：

```text
Warp 0
```

来处理：

```text
warp_sums[0 ~ 7]
```

其余 Lane：

```text
补 0
```

然后再调用：

```cpp
warp_reduce_sum(...)
```

最终：

```text
Warp 0 Lane 0
```

拿到：

> **整个 Block 的 Sum。**

```text

├── Warp 0 → Reduce → 1 个 Sum
├── Warp 1 → Reduce → 1 个 Sum
├── Warp 2 → Reduce → 1 个 Sum
├── Warp 3 → Reduce → 1 个 Sum
├── Warp 4 → Reduce → 1 个 Sum
```

# 六十四、为什么这种方法比“全部用 Shared Memory”好？

如果 256 个 Thread 全部通过 Shared Memory 不断折半：

```text

↓
128
↓
64
↓
32
↓
16
↓
8
↓
4
↓
2
↓
1
```

过程中需要多次：

```text

__syncthreads()
```

而 Warp Shuffle 版本：

```text
Warp 内部分
```

直接使用：

```text
Register-to-Register
```

只有：

```text
Warp 之间
```

才需要少量 Shared Memory。

所以：

```text
Shared Memory 用得更少

同步次数更少

Warp 内通信更快
```

# 六十五、现在把 Warp 和 Shared Memory 的作用域彻底区分

你前面学：

```text
=

```

所以：

```text

```

都可以通过 Shared Memory 交换数据。

但是：

# 六十七、为什么前面学的 Bank Conflict 是 Warp 级问题？

你前面刚问过：

```text

```

为什么可能 Bank Conflict。

现在可以更准确理解：

Bank Conflict 判断的是：

> **同一个 Warp 在执行一次 Shared Memory 指令时，不同 Lane 的访问如何映射到 Bank。**

# 六十八、Global Memory Coalescing 也是 Warp 级问题

你前面学：

为什么很好？

现在也可以更准确说：

> **一个 Warp 的 32 个 Lane 访问连续地址，硬件可以更高效地合并 Memory Transaction。**

所以：

```text
Coalescing
```

也是从 Warp 的访问模式来看的。

这也是为什么这一章这么重要：

第七句：

> **Warp Shuffle 可以让同 Warp Thread 直接交换 Register 数据。**

第九句：

> **很多 GPU 性能问题最终都应该站在 Warp 的视角分析。**
