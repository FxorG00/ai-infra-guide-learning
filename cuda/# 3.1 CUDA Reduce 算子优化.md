# 一、Reduce 算子基础

## 1.1 什么是 Reduce？

Reduce（归约、规约）就是：

> 把多个数据按照某种运算规则合并成一个结果。

例如 Sum Reduce：

$$
y=\sum_{i=0}^{N-1}x_i
$$

Max Reduce：

$$
y=\max(x_0,x_1,\dots,x_{N-1})
$$

Min Reduce：

$$
y=\min(x_0,x_1,\dots,x_{N-1})
$$

在 Transformer 中其实有大量 Reduce 操作。

例如 Softmax：

$$
y_i=\frac{e^{x_i}}{\sum_{j=0}^{N-1}e^{x_j}}
$$

为了数值稳定性，实际实现通常还需要先求最大值：

$$
m=\max_j x_j
$$

$$
y_i=\frac{e^{x_i-m}}{\sum_j e^{x_j-m}}
$$

这里就包含：

```text
Max Reduce
+
Sum Reduce
```

再比如 RMSNorm：

$$
y_i=\frac{x_i}{\sqrt{\frac{1}{N}\sum_{j=0}^{N-1}x_j^2+\epsilon}}\gamma_i
$$

其中平方和也是 Reduce。

所以我们现在学习 Reduce，并不是只为了实现一个数组求和。

而是为后面的：

```text
Softmax
LayerNorm
RMSNorm
Attention
```

打基础。

---

## 1.2 为什么 Reduce 适合并行计算？

假设有 8 个数字：

```text
1  2  3  4  5  6  7  8
```

CPU 最朴素的串行写法：

```cpp
float sum = 0;

for (int i = 0; i < N; ++i) {
    sum += input[i];
}
```

存在一条很长的数据依赖链：

```text
1 + 2
    ↓
    3 + 3
        ↓
        6 + 4
            ↓
            10 + 5
                ...
```

每一步都依赖前一步的结果。

但是加法在数学上满足结合律。

因此我们可以采用树形归约：

```text
第一轮：

1+2    3+4    5+6    7+8

 3      7      11     15

第二轮：

 3+7           11+15

 10              26

第三轮：

       10+26

         36
```

如果有足够的并行计算资源，归约的计算深度从：

$$
O(N)
$$

降低到：

$$
O(\log_2 N)
$$

注意：

**总计算量并没有从 O(N) 降低到 O(log N)。**

对于 N 个数，仍然需要 N-1 次有效加法。

只是这些加法不再全部串行执行。

这是并行算法里面两个不同的概念：

- Work：总计算量。
- Span：理想并行情况下的关键路径长度。

Reduce 优化的是并行执行的关键路径，以及实际硬件上的资源利用效率。

补充：浮点数加法并不严格满足结合律，因此不同归约顺序可能产生微小的舍入误差。

---

## 1.3 为什么 Reduce 是 Memory-Bound？

假设输入为 N 个 float。

每个 float 占：

$$
4\ \mathrm{Bytes}
$$

整个数组需要读取：

$$
4N\ \mathrm{Bytes}
$$

计算量大约为：

$$
N-1\ \mathrm{FLOPs}
$$

忽略输出和额外开销，Arithmetic Intensity 为：

$$
AI=\frac{N-1}{4N}\approx0.25\ \mathrm{FLOP/Byte}
$$

也就是说：

```text
每读取 4 Bytes
只进行大约一次加法
```

GPU 的计算能力通常远远超过这种操作所需要的算力。

所以 Reduce 最终主要追求的是：

> 尽可能高效地把 Global Memory 中的数据读取出来，并减少归约过程中的额外开销。

不过，Reduce 是低算术强度算子，并不意味着每个版本都一定已经被 HBM 带宽限制。

低效版本还可能被以下因素限制：

- Warp Divergence
- Shared Memory Bank Conflict
- 同步开销
- 指令开销
- 并行度不足

解决这些问题以后，才有机会接近显存带宽上限。

---

## 1.4 一个非常重要的前提：Block Reduce 不等于完整 Reduce

原文 V0～V7 的 Kernel 都是在做：

```text
每个 Block
    ↓
处理一部分数据
    ↓
得到一个 Partial Sum
    ↓
写入 output[blockIdx.x]
```

例如：

```text
整个输入数组
│
├── Block 0 → sum0
├── Block 1 → sum1
├── Block 2 → sum2
└── Block 3 → sum3
```

输出是：

```text
output = [sum0, sum1, sum2, sum3]
```

而不是最终的一个 sum。

完整 Reduce 还需要：

```text
sum0 + sum1 + sum2 + sum3
```

可以通过：

- 启动下一个 Reduce Kernel。
- 每个 Block 对最终结果执行一次 atomicAdd。
- 将 Partial Sum 拷回 CPU 汇总。

当前这篇文章主要研究第一阶段的 Kernel 优化。

这个区别一定要记住，特别是以后做性能测试的时候。

# 二、V0：朴素并行归约

## 2.1 基本思想

先假设一个 Block 有 8 个 Thread。

每个 Thread 负责一个输入元素：

```text
Thread:   0  1  2  3  4  5  6  7

Value:    1  2  3  4  5  6  7  8
```

首先将所有数据加载到 Shared Memory。

```cpp
smem[tid] = input[gid];

__syncthreads();
```

然后进行树形归约。

第一轮 step = 1：

```text
Thread 0：smem[0] += smem[1]
Thread 2：smem[2] += smem[3]
Thread 4：smem[4] += smem[5]
Thread 6：smem[6] += smem[7]
```

结果：

```text
[3]  2  [7]  4  [11]  6  [15]  8
```

注意，没有被更新的位置仍然保留原来的值，只是后续不再需要它们。

第二轮 step = 2：

```text
Thread 0：smem[0] += smem[2]
Thread 4：smem[4] += smem[6]
```

结果：

```text
[10]  2  7  4  [26]  6  15  8
```

第三轮 step = 4：

```text
Thread 0：smem[0] += smem[4]
```

最终：

```text
smem[0] = 36
```

所以我们只需要让 Thread 0 将最终结果写出。

---

## 2.2 怎么确定每一轮哪些 Thread 工作？

观察上面的规律：

```text
step = 1：

Thread 0、2、4、6


step = 2：

Thread 0、4


step = 4：

Thread 0
```

那么第 step 轮工作的 Thread 编号，应该满足：

$$
tid\bmod(2\times step)=0
$$

所以可以写成：

```cpp
if (tid % (2 * step) == 0) {
    smem[tid] += smem[tid + step];
}
```

每一轮：

```cpp
step *= 2;
```

---

## 2.3 V0 完整代码

以下实现假设 Block Size 是 2 的整数次幂，例如 128、256、512。

```cpp
__global__ void reduce_v0(
    const float* input,
    float* output,
    int N
) {
    extern __shared__ float smem[];

    int tid = threadIdx.x;

    int gid = blockIdx.x * blockDim.x + tid;

    // Global Memory -> Shared Memory
    smem[tid] = (gid < N) ? input[gid] : 0.0f;

    __syncthreads();

    // 从小步长到大步长进行归约
    for (int step = 1;
         step < blockDim.x;
         step *= 2) {

        if (tid % (2 * step) == 0) {
            smem[tid] += smem[tid + step];
        }

        __syncthreads();
    }

    // 每个 Block 输出一个结果
    if (tid == 0) {
        output[blockIdx.x] = smem[0];
    }
}
```

启动：

```cpp
int block_size = 256;

int grid_size = (N + block_size - 1) / block_size;

reduce_v0<<<
    grid_size,
    block_size,
    block_size * sizeof(float)
>>>(d_input, d_output, N);
```

这里第三个 Kernel Launch 参数：

```cpp
block_size * sizeof(float)
```

就是给每个 Block 分配动态 Shared Memory。

对应：

```cpp
extern __shared__ float smem[];
```

你之前学过这个语法，现在应该没有问题。

---

## 2.4 为什么每一轮都需要 __syncthreads()？

考虑：

```text
第一轮：

Thread 2 更新 smem[2]
```

下一轮：

```text
Thread 0 需要读取 smem[2]
```

如果没有同步，就可能发生：

```text
Thread 0 已经进入第二轮

但是 Thread 2 第一轮还没更新完
```

于是 Thread 0 读到旧值。

所以每一轮必须满足：

```text
所有 Thread 完成本轮 Shared Memory 更新
                    ↓
             __syncthreads()
                    ↓
              开始下一轮
```

这和你之前写 Matrix Transpose 的同步原理完全一样。

---

## 2.5 为什么越界的 Thread 要补 0？

例如：

```text
Block Size = 256

但是最后一个 Block 只剩 100 个有效元素
```

我们可以让：

```text
前 100 个 Thread：读取真实数据

后 156 个 Thread：初始化为 0
```

因为：

$$
x+0=x
$$

所以补零不会影响 Sum Reduce 的结果。

但是这些 Thread 仍然会参与 Block 的归约和同步。

不能简单地写成：

```cpp
if (gid >= N) {
    return;
}
```

然后让其余线程继续依赖原来的完整归约结构。

否则 Shared Memory 中部分位置可能没有初始化，后续还可能读取这些位置。

补零同时解决了：

```text
边界处理
+
保持统一的归约结构
```

---

## 2.6 V0 最大的问题：Warp Divergence

现在回到真实的 GPU。

一个 Block 有 256 个 Thread，也就是 8 个 Warp。

考虑 Warp 0：

```text
Thread 0 ~ 31
```

第一轮：

```cpp
if (tid % 2 == 0)
```

工作情况：

```text
Thread 0  工作
Thread 1  不工作
Thread 2  工作
Thread 3  不工作
...
Thread 30 工作
Thread 31 不工作
```

画出来：

```text
Lane:    0 1 2 3 4 5 6 7 ...

Active:  1 0 1 0 1 0 1 0 ...
```

一个 Warp 只有一半 Lane 真正进行归约计算。

第二轮：

```cpp
if (tid % 4 == 0)
```

```text
Active:  1 0 0 0 1 0 0 0 ...
```

只剩四分之一 Lane 工作。

第三轮：

```cpp
if (tid % 8 == 0)
```

```text
Active:  1 0 0 0 0 0 0 0 ...
```

只剩八分之一 Lane 工作。

原文将这一问题归结为 Warp Divergence。

更准确地说，即使编译器将这个短分支转换为 Predication，而不是实际的分支跳转，仍然存在大量 Lane 没有执行有效加法的问题。

对于这种没有 else 的分支，不一定真的需要完整执行两条路径，但有效 Lane 利用率依然很差。

---

## 2.7 V0 还有一个问题：取模运算

```cpp
tid % (2 * step)
```

这是整数取模。

由于 step 都是 2 的整数次幂，编译器可能对它进行优化。

但无论如何，我们下一步都可以通过改变 Thread 与任务的映射关系，把这个判断换成更简单的范围判断。

这就进入 V1。

---

# 三、V1：改变 Thread Mapping，减少 Warp Divergence

## 3.1 V0 的问题到底出在哪里？

V0 每一轮挑选工作的 Thread 时，采用的是：

```text
隔一个 Thread 选一个

隔三个 Thread 选一个

隔七个 Thread 选一个
```

工作 Thread 分散在不同 Warp 中。

但我们明明可以让：

```text
前面一部分连续的 Thread 工作

后面的 Thread 完全不工作
```

这样就可以让前面的 Warp 保持完整的有效 Lane。

注意：

> 我们不改变这一轮需要进行哪些加法，只改变这些加法由哪些 Thread 执行。

这是 V1 最重要的思想。

---

## 3.2 怎么改变映射？

还是假设 Block Size = 8。

第一轮 step = 1。

原来 V0：

| Thread | 负责的计算 |
|---|---|
| 0 | smem[0] + smem[1] |
| 2 | smem[2] + smem[3] |
| 4 | smem[4] + smem[5] |
| 6 | smem[6] + smem[7] |

我们改成：

| Thread | 负责的计算 |
|---|---|
| 0 | smem[0] + smem[1] |
| 1 | smem[2] + smem[3] |
| 2 | smem[4] + smem[5] |
| 3 | smem[6] + smem[7] |

虽然工作的 Thread 变了，但是负责的计算完全没有变。

所以我们只需要重新计算当前 Thread 要处理的 Shared Memory 下标。

$$
index=tid\times2\times step
$$

对应代码：

```cpp
int index = tid * 2 * step;

if (index < blockDim.x) {
    smem[index] += smem[index + step];
}
```

这就是 V1。

---

## 3.3 V1 Kernel

```cpp
__global__ void reduce_v1(
    const float* input,
    float* output,
    int N
) {
    extern __shared__ float smem[];

    int tid = threadIdx.x;
    int gid = blockIdx.x * blockDim.x + tid;

    smem[tid] = (gid < N) ? input[gid] : 0.0f;

    __syncthreads();

    for (int step = 1;
         step < blockDim.x;
         step *= 2) {

        int index = tid * 2 * step;

        if (index < blockDim.x) {
            smem[index] += smem[index + step];
        }

        __syncthreads();
    }

    if (tid == 0) {
        output[blockIdx.x] = smem[0];
    }
}
```

启动配置和 V0 一样。

---

## 3.4 为什么 V1 的 Warp Divergence 减少了？

假设 Block Size = 256。

第一轮 step = 1：

$$
index=2\times tid
$$

需要：

$$
2\times tid<256
$$

也就是：

$$
tid<128
$$

因此只有 Thread 0～127 工作。

对应：

```text
Warp 0：全部工作
Warp 1：全部工作
Warp 2：全部工作
Warp 3：全部工作

Warp 4：全部跳过
Warp 5：全部跳过
Warp 6：全部跳过
Warp 7：全部跳过
```

这时候没有 Warp 内部分歧。

对比 V0：

```text
V0：

8 个 Warp 都有部分 Lane 工作


V1：

4 个完整 Warp 工作
4 个 Warp 跳过
```

两者都完成了 128 次加法，但是 V1 的加法任务集中在更少的 Warp 中。

接下来每轮也是如此：

| step | 工作线程数 | 完整工作的 Warp | 部分工作的 Warp |
|---:|---:|---:|---:|
| 1 | 128 | 4 | 0 |
| 2 | 64 | 2 | 0 |
| 4 | 32 | 1 | 0 |
| 8 | 16 | 0 | 1 |
| 16 | 8 | 0 | 1 |
| 32 | 4 | 0 | 1 |
| 64 | 2 | 0 | 1 |
| 128 | 1 | 0 | 1 |

所以 V1 并没有完全消灭 Warp Divergence。

但是前几轮的工作分布已经改善了很多。

另外，没有工作的 Warp 仍然驻留在 Block 中，并参与后续的 `__syncthreads()`，它们占用的寄存器等资源也不会立刻释放。

所以这里改善的是有效指令执行效率，不是 Occupancy。

# 四、V2：解决 Shared Memory Bank Conflict

## 4.1 V1 引入了一个新的问题

V1 虽然改善了 Warp Divergence，但是你仔细看：

```cpp
int index = tid * 2 * step;

smem[index] += smem[index + step];
```

一个 Warp 内，相邻 Thread 访问的 Shared Memory 地址不再是连续的。

而是：

$$
stride=2\times step
$$

你在 2.2 已经学过：

$$
bank(i)=i\bmod32
$$

这里正好用得上。

---

## 4.2 V1 第一轮为什么是 2-way Bank Conflict？

当：

```cpp
step = 1;
```

那么：

```cpp
index = tid * 2;
```

Warp 0 的第一组 Shared Memory 读取：

```text
Lane 0  -> smem[0]
Lane 1  -> smem[2]
Lane 2  -> smem[4]
...
Lane 15 -> smem[30]

Lane 16 -> smem[32]
Lane 17 -> smem[34]
...
Lane 31 -> smem[62]
```

对应 Bank：

```text
Lane 0  -> Bank 0
Lane 1  -> Bank 2
...
Lane 15 -> Bank 30

Lane 16 -> Bank 0
Lane 17 -> Bank 2
...
Lane 31 -> Bank 30
```

32 个 Lane 只访问了 16 个不同的 Bank。

每个 Bank 被两个 Lane 访问，而且访问不同地址。

因此产生：

```text
2-way Bank Conflict
```

另一组读取：

```cpp
smem[index + step]
```

也有类似的冲突。

注意：

Bank Conflict 应该针对同一个 Warp 的同一条 Shared Memory 访问指令进行分析。

不是因为一个 Thread 读取两个同 Bank 的地址，就叫 Bank Conflict。

---

## 4.3 第二轮为什么是 4-way Bank Conflict？

当：

```cpp
step = 2;
```

有：

$$
index=4\times tid
$$

那么：

```text
Lane 0  -> smem[0]  -> Bank 0

Lane 8  -> smem[32] -> Bank 0

Lane 16 -> smem[64] -> Bank 0

Lane 24 -> smem[96] -> Bank 0
```

因此产生 4-way Bank Conflict。

第三轮 step = 4 时，完整 Warp 会出现 8-way Bank Conflict。

对于 256 线程的这个具体例子，后续活跃 Lane 数也会减少，因此冲突程度不会无限增长。

所以 V1 实际上是在：

```text
减少 Warp Divergence
        ↓
但改变了 Shared Memory 的访问步长
        ↓
引入 Bank Conflict
```

这就是 CUDA 性能优化中的 Trade-off。

---

## 4.4 V2 的核心思想：为什么一定要从相邻元素开始加？

之前 V0、V1 的归约顺序是：

```text
先相邻两个元素相加

然后间隔 2 的元素相加

然后间隔 4 的元素相加
```

但是 Sum Reduce 并不要求必须先把相邻元素加起来。

我们完全可以反过来：

```text
先把前半部分和后半部分对应相加

然后剩下的前半部分继续折半
```

例如：

```text
原始数据：

1  2  3  4  5  6  7  8
```

第一轮 step = 4：

```text
Thread 0：1 + 5 = 6
Thread 1：2 + 6 = 8
Thread 2：3 + 7 = 10
Thread 3：4 + 8 = 12
```

结果：

```text
[6] [8] [10] [12]  5  6  7  8
```

第二轮 step = 2：

```text
Thread 0：6 + 10 = 16
Thread 1：8 + 12 = 20
```

第三轮 step = 1：

```text
Thread 0：16 + 20 = 36
```

这个模式是不是非常眼熟？

你之前理解 Warp Shuffle Reduce 的时候：

```cpp
offset = 16;
offset = 8;
offset = 4;
offset = 2;
offset = 1;
```

本质上也是类似的折半归约。

---

## 4.5 V2 Kernel

```cpp
__global__ void reduce_v2(
    const float* input,
    float* output,
    int N
) {
    extern __shared__ float smem[];

    int tid = threadIdx.x;
    int gid = blockIdx.x * blockDim.x + tid;

    smem[tid] = (gid < N) ? input[gid] : 0.0f;

    __syncthreads();

    for (int step = blockDim.x / 2;
         step > 0;
         step >>= 1) {

        if (tid < step) {
            smem[tid] += smem[tid + step];
        }

        __syncthreads();
    }

    if (tid == 0) {
        output[blockIdx.x] = smem[0];
    }
}
```

这里的：

```cpp
step >>= 1;
```

对于正整数，就相当于：

```cpp
step /= 2;
```

---

## 4.6 为什么 V2 消除了 Bank Conflict？

假设：

```text
Block Size = 256

第一轮 step = 128
```

Warp 0 进行：

```cpp
smem[tid] += smem[tid + 128];
```

分别分析两个读取操作。

第一个读取：

```cpp
smem[tid]
```

```text
Lane 0  -> smem[0]  -> Bank 0
Lane 1  -> smem[1]  -> Bank 1
...
Lane 31 -> smem[31] -> Bank 31
```

没有 Bank Conflict。

第二个读取：

```cpp
smem[tid + 128]
```

```text
Lane 0  -> smem[128] -> Bank 0
Lane 1  -> smem[129] -> Bank 1
...
Lane 31 -> smem[159] -> Bank 31
```

同样没有 Bank Conflict。

你可能会疑惑：

> smem[0] 和 smem[128] 不都是 Bank 0 吗？

没错。

但它们是两个不同的读取操作。

我们不能把同一条 C++ 表达式中的两个数组下标，直接当成一条 Shared Memory Load 指令。

在这个标量访问模式下，每组读取都是由不同 Lane 访问连续的 Shared Memory 地址。

因此不存在之前 V1 的 Bank Conflict。

---

## 4.7 V2 与 V1 的根本区别

V1：

```cpp
int index = tid * 2 * step;

smem[index] += smem[index + step];
```

同一个 Warp 内：

```text
Shared Memory 访问步长 = 2 * step
```

V2：

```cpp
smem[tid] += smem[tid + step];
```

同一个 Warp 内：

```text
Shared Memory 访问步长 = 1
```

所以：

| 版本 | Warp 内有效线程分布 | Shared Memory 访问 |
|---|---|---|
| V0 | 分散 | 交错 |
| V1 | 集中 | 跨步访问，有 Bank Conflict |
| V2 | 集中 | 连续访问，无此类 Bank Conflict |

注意：

V2 在 step 小于 32 的最后几轮仍然会出现部分 Lane 工作的情况。

所以原文所说的消除 Divergence，更准确地理解为消除了前面完整 Warp 阶段的分歧，并非所有轮次都完全没有分歧。

---

# 五、V3：每个 Thread 处理两个元素

## 5.1 V2 还有什么问题？

V2 中：

```text
256 个 Thread
负责读取 256 个元素
```

然后：

```text
第一轮归约：
只有前 128 个 Thread 进行加法

第二轮归约：
只有前 64 个 Thread 进行加法

第三轮归约：
只有前 32 个 Thread 进行加法
```

后面很多 Thread 已经没有计算任务。

你可以发现：

后半部分 Thread 只负责：

```text
从 Global Memory 读取一个 float
        ↓
写入 Shared Memory
        ↓
等待其他 Thread 进行归约
```

那么有没有办法让每个 Thread 在读取数据时，就先进行一次加法？

当然可以。

---

## 5.2 把第一轮归约提前到 Register 中进行

假设我们现在只有 4 个 Thread，但是需要处理 8 个元素。

```text
input：

1  2  3  4  5  6  7  8
```

让每个 Thread 负责两个元素：

```text
Thread 0：input[0] + input[4] = 6

Thread 1：input[1] + input[5] = 8

Thread 2：input[2] + input[6] = 10

Thread 3：input[3] + input[7] = 12
```

这一步直接在每个 Thread 的局部变量中计算。

然后写入 Shared Memory：

```text
smem：

6  8  10  12
```

接下来正常做 Shared Memory Reduce。

这样就相当于：

```text
在 Global Memory 加载阶段
直接完成了第一轮归约
```

---

## 5.3 为什么不让 Thread 0 读取 input[0] 和 input[1]？

例如：

```cpp
int gid = tid * 2;

float val = input[gid] + input[gid + 1];
```

这种写法数学上也是正确的。

但是如果编译器使用两条独立的标量加载指令：

第一条读取：

```text
Thread 0 -> input[0]
Thread 1 -> input[2]
Thread 2 -> input[4]
...
```

第二条读取：

```text
Thread 0 -> input[1]
Thread 1 -> input[3]
Thread 2 -> input[5]
...
```

每条指令都是 stride = 2 的访问模式。

虽然缓存可能帮助复用这些数据，但单条标量 Load 的访问模式不是最理想的。

所以 V3 采用：

```cpp
input[gid]

input[gid + blockDim.x]
```

假设 Block Size = 256。

第一条 Load：

```text
Lane 0  -> input[0]
Lane 1  -> input[1]
...
Lane 31 -> input[31]
```

第二条 Load：

```text
Lane 0  -> input[256]
Lane 1  -> input[257]
...
Lane 31 -> input[287]
```

两次都是连续访问。

也就是：

```text
每个 Thread 自己的两个元素不相邻

但是同一个 Warp 在同一条指令中的访问是连续的
```

这句话非常重要。

GPU 的 Coalescing 主要是从 Warp 视角分析的，而不是单个 Thread 视角。

---

## 5.4 为什么 gid 的计算也要改？

原来 V2：

```cpp
int gid = blockIdx.x * blockDim.x + tid;
```

因为每个 Block 负责 blockDim.x 个元素。

现在 V3 每个 Block 负责：

$$
2\times blockDim.x
$$

个元素。

所以：

```cpp
int gid = blockIdx.x * (blockDim.x * 2) + tid;
```

假设 Block Size = 256：

```text
Block 0：
负责 input[0 ~ 511]

Block 1：
负责 input[512 ~ 1023]

Block 2：
负责 input[1024 ~ 1535]
```

如果忘记修改 gid，就会出现不同 Block 重复处理同一段数据。

---

## 5.5 V3 Kernel

```cpp
__global__ void reduce_v3(
    const float* input,
    float* output,
    int N
) {
    extern __shared__ float smem[];

    int tid = threadIdx.x;

    int gid =
        blockIdx.x * (blockDim.x * 2) + tid;

    // 每个 Thread 负责两个元素
    float val = 0.0f;

    if (gid < N) {
        val += input[gid];
    }

    if (gid + blockDim.x < N) {
        val += input[gid + blockDim.x];
    }

    // 先在 Register 中进行局部求和
    // 再写入 Shared Memory
    smem[tid] = val;

    __syncthreads();

    for (int step = blockDim.x / 2;
         step > 0;
         step >>= 1) {

        if (tid < step) {
            smem[tid] += smem[tid + step];
        }

        __syncthreads();
    }

    if (tid == 0) {
        output[blockIdx.x] = smem[0];
    }
}
```

注意启动配置：

```cpp
int block_size = 256;

int grid_size =
    (N + 2 * block_size - 1) / (2 * block_size);

reduce_v3<<<
    grid_size,
    block_size,
    block_size * sizeof(float)
>>>(d_input, d_output, N);
```

Shared Memory 大小还是：

```cpp
block_size * sizeof(float)
```

而不是乘 2。

因为两个输入元素已经在 Thread 的局部变量中合并成了一个 val。

---

## 5.6 V3 到底减少了什么？

假设：

```text
N = 1024

Block Size = 256
```

V2：

```text
4 个 Block

每个 Block 加载 256 个元素

每个 Block 进行 8 轮 Shared Memory Reduce
```

V3：

```text
2 个 Block

每个 Block 加载 512 个元素

每个 Block 还是进行 8 轮 Shared Memory Reduce
```

可以总结为：

| 指标 | V2 | V3 |
|---|---:|---:|
| 每个 Thread 处理元素 | 1 | 2 |
| 每个 Block 处理元素 | 256 | 512 |
| Block 数量 | 4 | 2 |
| 每个 Block 的 Shared Memory | 1024 B | 1024 B |
| 每个 Block 的归约轮数 | 8 | 8 |
| 输出 Partial Sum 数量 | 4 | 2 |

V3 并没有减少必须读取的输入数据量。

真正减少的是整个 Grid 的：

```text
Block 调度开销

Shared Memory 归约次数

同步开销

Partial Sum 数量
```

注意，这里的 Block 数量减少，不是 Kernel Launch 次数减少。

V2 和 V3 都只启动了一次 Kernel。

另外，V3 也没有彻底解决后半部分 Thread 在归约中闲置的问题。

它只是让每个 Thread 在进入 Shared Memory Reduce 之前承担更多有效工作。

---

## 5.7 V3 是一个很重要的 CUDA 优化模式

之前我们一直在写：

```text
一个 Thread
负责一个数据
```

但是高性能 CUDA Kernel 经常采用：

```text
一个 Thread
负责多个数据
```

这样可以：

- 摊销 Thread 和 Block 的固定开销。
- 增加每个 Thread 的有效计算量。
- 减少跨线程通信。
- 提高指令级并行的机会。

不过也可能增加 Register 使用量，所以仍然要考虑 Occupancy。

这个思想后面 GEMM 中也会出现。

一个 Thread 可能负责的不再只是一个输出元素，而是多个输出元素。

---

# 六、V4：展开最后一个 Warp

## 6.1 V3 的同步还有优化空间

假设 Block Size = 256。

归约的 step 为：

```text
128
64
32
16
8
4
2
1
```

每一轮之后都执行：

```cpp
__syncthreads();
```

但是观察参与计算的 Thread 数：

| step | 参与计算的 Thread 数 | 参与计算的 Warp |
|---:|---:|---|
| 128 | 128 | Warp 0～3 |
| 64 | 64 | Warp 0～1 |
| 32 | 32 | Warp 0 |
| 16 | 16 | Warp 0 |
| 8 | 8 | Warp 0 |
| 4 | 4 | Warp 0 |
| 2 | 2 | Warp 0 |
| 1 | 1 | Warp 0 |

从 step = 32 开始，只有 Warp 0 在执行归约计算。

那么为什么还要让整个 Block 的 256 个 Thread 一起执行 `__syncthreads()` 呢？

我们可以把后半段归约交给第一个 Warp，并且改用 Warp 范围的同步。

这就是 V4。

---

## 6.2 为什么 step = 32 有一点特殊？

当：

```cpp
step = 32;
```

Warp 0 的 Thread 执行：

```cpp
smem[tid] += smem[tid + 32];
```

虽然只有 Warp 0 在工作，但是它读取了：

```text
smem[32 ~ 63]
```

这些位置此前可能由 Warp 1 更新。

因此必须确保进入 step = 32 前，前面的 Block 级归约已经完成。

也就是说：

```text
step = 64
        ↓
__syncthreads()
        ↓
Warp 0 读取最后 64 个值
        ↓
后面只需要 Warp 内部协作
```

这是 Block-level Synchronization 向 Warp-level Synchronization 的转换点。

---

## 6.3 原文的传统写法

原文采用类似这样的形式：

```cpp
__device__ void warpReduce(
    volatile float* smem,
    int tid
) {
    smem[tid] += smem[tid + 32];
    smem[tid] += smem[tid + 16];
    smem[tid] += smem[tid + 8];
    smem[tid] += smem[tid + 4];
    smem[tid] += smem[tid + 2];
    smem[tid] += smem[tid + 1];
}
```

这是经典 CUDA Reduce 优化教程中经常出现的写法。

它依赖传统的 Warp-synchronous Programming。

其中：

```cpp
volatile float* smem
```

主要用于限制编译器对这些内存访问进行某些优化，例如将读取长期保留在 Register 中。

但是：

> volatile 并不等于同步，也不提供线程间的 Barrier。

Volta 及之后的 GPU 引入了 Independent Thread Scheduling。

因此，不能把 Warp 内线程永远严格同步作为正确性的保证。

你在 2.4 已经学过这个问题。

所以原文 V4 不应该直接照搬到现代 GPU 上。

---

## 6.4 一个使用显式 Warp 同步的 V4 写法

为了保留 V4 使用 Shared Memory 完成最后一个 Warp 归约的思想，我们可以写成：

```cpp
__device__ void finish_warp_reduce(
    float* smem,
    int lane
) {
    // 这里由完整的 Warp 0 调用
    // 进入前，Shared Memory 中的 64 个值已经准备好

    smem[lane] += smem[lane + 32];

    __syncwarp();

    if (lane < 16) {
        smem[lane] += smem[lane + 16];
    }

    __syncwarp();

    if (lane < 8) {
        smem[lane] += smem[lane + 8];
    }

    __syncwarp();

    if (lane < 4) {
        smem[lane] += smem[lane + 4];
    }

    __syncwarp();

    if (lane < 2) {
        smem[lane] += smem[lane + 2];
    }

    __syncwarp();

    if (lane == 0) {
        smem[0] += smem[1];
    }
}
```

注意这里的两个细节。

第一：

```cpp
__syncwarp();
```

放在 if 外面。

保证 Warp 0 的所有 32 个 Lane 都参加同步。

第二：

每轮只有当前需要更新左半部分的 Lane 才写入 Shared Memory。

这样这一轮的读取位置和写入位置不重叠。

不能只是对原文的无条件更新代码随意插入同步，就认为所有数据竞争都解决了。

---

## 6.5 V4 的主要 Kernel 结构

前面加载数据的部分和 V3 完全一样。

归约部分改成：

```cpp
for (int step = blockDim.x / 2;
     step > 32;
     step >>= 1) {

    if (tid < step) {
        smem[tid] += smem[tid + step];
    }

    __syncthreads();
}

if (tid < 32) {
    finish_warp_reduce(smem, tid);
}

if (tid == 0) {
    output[blockIdx.x] = smem[0];
}
```

这个版本假设 Block Size 是不小于 64 的 2 的整数次幂。

---

## 6.6 V4 节省了多少次 Block 级同步？

对于 Block Size = 256：

V3：

```text
加载完成：1 次

step = 128：1 次
step = 64 ：1 次
step = 32 ：1 次
step = 16 ：1 次
step = 8  ：1 次
step = 4  ：1 次
step = 2  ：1 次
step = 1  ：1 次

合计：9 次 __syncthreads()
```

V4：

```text
加载完成：1 次

step = 128：1 次
step = 64 ：1 次

合计：3 次 __syncthreads()
```

后续使用 Warp 范围的同步。

因此省去了 6 次 Block 级 Barrier。

原文这里写的是最后 5 轮，但按照它的 `step > 32` 循环条件，实际上被移出循环的是：

```text
32、16、8、4、2、1
```

共 6 轮。

---

## 6.7 V4 你现在需要学到什么程度？

你需要理解的是：

> 当线程之间的协作范围缩小时，同步范围也应该相应缩小。

```text
多个 Warp 协作
        ↓
Block Barrier


只剩一个 Warp 协作
        ↓
Warp Barrier
```

但是不需要花大量时间优化这种 Shared Memory Warp Reduce。

因为你已经学会了：

```cpp
__shfl_down_sync()
```

后面的 V6 会给出更加直接的方案。

---

# 七、V5：完全循环展开（Loop Unrolling）

## 7.1 为什么 V4 还有可以优化的地方？

V4 中，前面的归约仍然是：

```cpp
for (int step = blockDim.x / 2;
     step > 32;
     step >>= 1) {

    if (tid < step) {
        smem[tid] += smem[tid + step];
    }

    __syncthreads();
}
```

对于 Block Size = 256，我们其实早就知道循环只需要处理：

```text
step = 128

step = 64
```

那么是不是可以直接写成：

```cpp
if (tid < 128) {
    smem[tid] += smem[tid + 128];
}

__syncthreads();

if (tid < 64) {
    smem[tid] += smem[tid + 64];
}

__syncthreads();
```

这样就不需要：

```text
循环条件判断

循环变量更新

循环跳转
```

这就是 Loop Unrolling（循环展开）。

---

## 7.2 但是如果 Block Size 不是 256 呢？

假设我们想同时支持：

```text
128 Threads

256 Threads

512 Threads
```

难道要手写三个完全不同的 Kernel 吗？

不用。

你之前学过 C++，这里就可以使用模板。

```cpp
template<int BLOCK_SIZE>
__global__ void reduce_v5(...) {
    ...
}
```

调用：

```cpp
reduce_v5<256><<<...>>>(...);
```

这里：

```cpp
BLOCK_SIZE
```

是编译期常量。

和：

```cpp
blockDim.x
```

有一个重要区别。

| 写法 | 编译器是否直接知道具体值 |
|---|---|
| `blockDim.x` | 一般在运行时确定 |
| `BLOCK_SIZE` 模板参数 | 编译时确定 |

因此编译器可以根据不同模板参数生成不同的 Kernel。

---

## 7.3 模板怎么帮助我们消除无用代码？

例如：

```cpp
template<int BLOCK_SIZE>
__global__ void example() {
    if (BLOCK_SIZE >= 512) {
        // 操作 A
    }

    if (BLOCK_SIZE >= 256) {
        // 操作 B
    }

    if (BLOCK_SIZE >= 128) {
        // 操作 C
    }
}
```

当调用：

```cpp
example<256><<<...>>>();
```

编译器知道：

```text
BLOCK_SIZE >= 512：false

BLOCK_SIZE >= 256：true

BLOCK_SIZE >= 128：true
```

于是优化后，可以直接删除 A，保留 B 和 C。

普通的 `if` 在这里就有机会被编译器优化掉。

如果使用 C++17，还可以写得更加明确：

```cpp
if constexpr (BLOCK_SIZE >= 512) {
    ...
}
```

`if constexpr` 可以理解成编译期条件选择。

---

## 7.4 V5 Kernel

这里沿用 V4 中具有显式同步的 `finish_warp_reduce` 辅助函数。

为了方便理解，下面支持 64、128、256、512、1024 线程的配置。

```cpp
template<int BLOCK_SIZE>
__global__ void reduce_v5(
    const float* input,
    float* output,
    int N
) {
    static_assert(
        BLOCK_SIZE == 64 ||
        BLOCK_SIZE == 128 ||
        BLOCK_SIZE == 256 ||
        BLOCK_SIZE == 512 ||
        BLOCK_SIZE == 1024
    );

    __shared__ float smem[BLOCK_SIZE];

    int tid = threadIdx.x;

    int gid =
        blockIdx.x * (BLOCK_SIZE * 2) + tid;

    float val = 0.0f;

    if (gid < N) {
        val += input[gid];
    }

    if (gid + BLOCK_SIZE < N) {
        val += input[gid + BLOCK_SIZE];
    }

    smem[tid] = val;

    __syncthreads();

    if constexpr (BLOCK_SIZE >= 1024) {
        if (tid < 512) {
            smem[tid] += smem[tid + 512];
        }
        __syncthreads();
    }

    if constexpr (BLOCK_SIZE >= 512) {
        if (tid < 256) {
            smem[tid] += smem[tid + 256];
        }
        __syncthreads();
    }

    if constexpr (BLOCK_SIZE >= 256) {
        if (tid < 128) {
            smem[tid] += smem[tid + 128];
        }
        __syncthreads();
    }

    if constexpr (BLOCK_SIZE >= 128) {
        if (tid < 64) {
            smem[tid] += smem[tid + 64];
        }
        __syncthreads();
    }

    if (tid < 32) {
        finish_warp_reduce(smem, tid);
    }

    if (tid == 0) {
        output[blockIdx.x] = smem[0];
    }
}
```

启动：

```cpp
constexpr int block_size = 256;

int grid_size =
    (N + block_size * 2 - 1) / (block_size * 2);

reduce_v5<block_size><<<
    grid_size,
    block_size
>>>(d_input, d_output, N);
```

编译时可以使用：

```bash
nvcc -O3 -std=c++17 reduce.cu -o reduce
```

---

## 7.5 为什么这里可以用静态 Shared Memory？

之前写：

```cpp
extern __shared__ float smem[];
```

是因为 Block Size 可能在运行时才知道。

但是现在：

```cpp
template<int BLOCK_SIZE>
```

已经将 Block Size 变成了编译期常量。

所以可以直接声明：

```cpp
__shared__ float smem[BLOCK_SIZE];
```

不需要再通过 Kernel Launch 第三个参数传 Shared Memory 大小。

注意：

这只是这里的一种实现选择。

模板 Kernel 同样可以继续使用动态 Shared Memory。

---

## 7.6 模板参数和实际 Block Size 必须一致

例如：

```cpp
reduce_v5<256><<<grid, 256>>>(...);
```

是正确的。

但是如果写成：

```cpp
reduce_v5<256><<<grid, 128>>>(...);
```

模板内部假设有 256 个 Thread，而实际只有 128 个 Thread。

就可能出现 Shared Memory 初始化不完整等错误。

模板参数并不会自动改变 Kernel Launch 的 Block Size。

这是两个不同的东西，需要你自己保证一致。

---

## 7.7 还有一种更简单的循环展开方式

CUDA 支持：

```cpp
#pragma unroll
```

例如：

```cpp
#pragma unroll
for (int step = BLOCK_SIZE / 2;
     step > 0;
     step >>= 1) {

    ...
}
```

它可以提示编译器进行循环展开。

原文 V5 使用手动展开加模板参数，目的是让你明确理解：

```text
编译期已知信息
        ↓
编译器能够生成更加特化的代码
```

这就是模板在高性能 CUDA Kernel 中经常出现的原因之一。

不过循环展开也不是越多越好。

展开可能增加：

```text
代码体积

Register Pressure

指令 Cache 压力
```

实际收益仍然需要 Benchmark。

而且编译器有时已经能够自动展开某些循环，所以不能保证手动展开一定更快。

# 八、V6：使用 Warp Shuffle 替代 Shared Memory

这一节对你来说应该是最容易的。

因为你在 2.1 已经独立理解过 Warp Reduce 和 Block Reduce 了。

---

## 8.1 V0～V5 为什么一直使用 Shared Memory？

因为一个 Block 内：

```text
Thread 0 的 Register

Thread 1 的 Register
```

一般是各自私有的。

Thread 0 不能直接写：

```cpp
Thread1.val
```

所以之前的版本都通过：

```text
Register
    ↓
Shared Memory
    ↓
其他 Thread 读取
```

来进行跨线程通信。

但是你已经知道：

同一个 Warp 内可以使用 Shuffle。

```cpp
__shfl_down_sync(...)
```

让参与线程直接交换局部值。

这样就不需要通过 Shared Memory 中转。

---

## 8.2 复习 Warp Reduce

```cpp
__device__ __forceinline__
float warp_reduce_sum(float val) {

    for (int offset = 16;
         offset > 0;
         offset >>= 1) {

        val += __shfl_down_sync(
            0xFFFFFFFF,
            val,
            offset
        );
    }

    return val;
}
```

整个过程：

```text
32 个 Thread 的 val

offset = 16
        ↓
前 16 个 Lane 得到有效中间结果

offset = 8
        ↓
前 8 个 Lane 得到有效中间结果

offset = 4
        ↓
前 4 个 Lane 得到有效中间结果

offset = 2
        ↓
前 2 个 Lane 得到有效中间结果

offset = 1
        ↓
Lane 0 得到完整 Warp Sum
```

这里所有 32 个 Lane 都调用 Shuffle。

但最终只有 Lane 0 的值是我们需要的完整归约结果。

另外补充一个之前容易误解的小细节：

`__shfl_down_sync` 的目标 Lane 超出指定 width 时，不是自动返回 0，而是返回调用线程自己的值。

不过上述完整 Warp 的树形归约不依赖后半部分无用的中间结果，因此 Lane 0 的最终结果仍然正确。

---

## 8.3 V6 不只是优化最后一个 Warp

注意 V6 和 V4 的区别。

V4：

```text
整个 Block 先使用 Shared Memory 归约

直到只剩最后一个 Warp

再进行 Warp 内归约
```

V6：

```text
每个 Warp 从一开始就使用 Shuffle 归约

然后所有 Warp 的结果再合并
```

假设：

```text
Block Size = 256

Warp 数量 = 8
```

那么：

```text
Warp 0：32 个值 -> sum0

Warp 1：32 个值 -> sum1

Warp 2：32 个值 -> sum2

...

Warp 7：32 个值 -> sum7
```

现在整个 Block 只剩 8 个结果。

再让 Warp 0 完成最后的归约即可。

这就是你之前已经学过的两级归约。

---

## 8.4 将 Block Reduce 封装成辅助函数

为了后面的 V7 更容易理解，我们可以将归约部分单独封装。

```cpp
__device__ __forceinline__
float block_reduce_sum(float val) {

    __shared__ float warp_sums[32];

    int tid = threadIdx.x;

    int lane = tid % 32;
    int wid = tid / 32;

    // 第一级：Warp 内归约
    val = warp_reduce_sum(val);

    if (lane == 0) {
        warp_sums[wid] = val;
    }

    // 确保所有 Warp 的结果都准备好
    __syncthreads();

    // 第二级：Warp 0 汇总所有 Warp 的结果
    if (wid == 0) {

        int num_warps = blockDim.x / 32;

        val = (lane < num_warps)
            ? warp_sums[lane]
            : 0.0f;

        val = warp_reduce_sum(val);
    }

    return val;
}
```

这里的前提是：

```text
一维 Block

Block Size 是 32 的倍数

所有 Block Thread 都调用这个函数
```

并且只有 Thread 0 返回的 val 是完整 Block Sum。

这个辅助函数用于当前每个 Block 只调用一次的场景。

如果以后在同一个 Kernel 中反复调用它，还要考虑 Shared Memory 被下一轮覆盖之前是否需要额外同步。

---

## 8.5 V6 Kernel

```cpp
__global__ void reduce_v6(
    const float* input,
    float* output,
    int N
) {
    int tid = threadIdx.x;

    int gid =
        blockIdx.x * (blockDim.x * 2) + tid;

    // 继承 V3：每个 Thread 加载两个元素
    float val = 0.0f;

    if (gid < N) {
        val += input[gid];
    }

    if (gid + blockDim.x < N) {
        val += input[gid + blockDim.x];
    }

    // Warp Reduce + Block Reduce
    val = block_reduce_sum(val);

    if (tid == 0) {
        output[blockIdx.x] = val;
    }
}
```

是不是突然变得非常简单？

因为现在你已经可以把 Reduce 当成一个可复用的 CUDA Device Function。

以后写 Softmax 或 RMSNorm 时，也可以用类似方式封装 Warp Reduce 和 Block Reduce。

---

## 8.6 V6 到底减少了多少 Shared Memory？

假设 Block Size = 256。

V2～V5：

```cpp
__shared__ float smem[256];
```

每个 Block 需要：

$$
256\times4=1024\ \mathrm{Bytes}
$$

V6：

```cpp
__shared__ float warp_sums[32];
```

每个 Block 需要：

$$
32\times4=128\ \mathrm{Bytes}
$$

而对于 256 Thread 的 Block，实际只使用了前 8 个位置。

也就是：

$$
8\times4=32\ \mathrm{Bytes}
$$

分配 32 个 float 是为了兼容最多 32 个 Warp 的 Block。

同时，V6 只需要一次 Block 级同步。

所以：

| 对比项 | V2 | V6 |
|---|---|---|
| Warp 内通信 | Shared Memory | Shuffle |
| 跨 Warp 通信 | Shared Memory | Shared Memory |
| 每 Block Shared Memory | 1024 B | 128 B |
| Block Barrier 次数 | 9 | 1 |

这里减少 Shared Memory 的主要价值，不一定是直接提高 Occupancy。

因为 1024 Bytes 本身对于现代 SM 也不算很多。

更加重要的是减少了：

```text
Shared Memory Load

Shared Memory Store

Block Barrier

地址计算
```

这才是 V6 的主要优化方向。

# 九、V7：Vectorized Load + Grid Stride Loop

这是原文最终优化版本。

我建议你重点理解这一版。

因为它将前面学过的大量 CUDA 优化技巧组合在了一起。

---

## 9.1 V6 还有什么问题？

V6 中，每个 Thread 负责两个 float。

假设原文的数据规模：

$$
N=2^{27}
$$

Block Size：

$$
256
$$

每个 Block 处理：

$$
256\times2=512
$$

个元素。

所以 Grid Size：

$$
G=\frac{2^{27}}{512}=262144
$$

也就是需要 262144 个 Block。

但是 A100 只有 108 个 SM。

GPU 不可能让这些 Block 全部同时驻留。

因此实际上：

```text
第一批 Block
        ↓
完成

第二批 Block
        ↓
完成

第三批 Block
        ↓
完成

...
```

不断重复。

这本身是正常的 CUDA 调度方式。

但是每个 Block 都需要重新进行：

```text
加载

Warp Reduce

Shared Memory 汇总

Block Barrier

Partial Sum 写出
```

那么能不能：

> 让较少的 Block 在每个 Thread 内部循环，先处理大量数据，再进行一次 Block Reduce？

这就是 Grid Stride Loop。

---

## 9.2 先单独理解 Grid Stride Loop

假设：

```text
N = 20

Grid Size = 2

Block Size = 4
```

总 Thread 数：

$$
T=2\times4=8
$$

那么可以让 Thread：

```text
Thread 0：
负责 input[0]、input[8]、input[16]

Thread 1：
负责 input[1]、input[9]、input[17]

Thread 2：
负责 input[2]、input[10]、input[18]

Thread 3：
负责 input[3]、input[11]、input[19]

Thread 4：
负责 input[4]、input[12]

...
```

对应：

```cpp
int gid = blockIdx.x * blockDim.x + threadIdx.x;

int stride = gridDim.x * blockDim.x;

float val = 0.0f;

for (int i = gid; i < N; i += stride) {
    val += input[i];
}
```

你之前笔记里的理解：

```text
第 i 个 Thread
负责全局下标 mod 总线程数等于 i 的数据
```

在这里完全适用。

每个 Thread 先在自己的 Register 中累加：

```text
Thread 0：
input[0] + input[8] + input[16]

Thread 1：
input[1] + input[9] + input[17]

...
```

所有数据处理结束后，再对每个 Thread 的 val 进行 Block Reduce。

---

## 9.3 为什么 Grid Stride Loop 仍然是 Coalesced Access？

这是很多人第一次看到 Grid Stride Loop 时会疑惑的地方。

单个 Thread 的访问：

```text
input[0]

input[8]

input[16]
```

明明是不连续的。

为什么还是 Coalesced？

因为我们需要站在 Warp 视角，观察同一次循环迭代中所有 Lane 的地址。

第一轮：

```text
Thread 0 -> input[0]
Thread 1 -> input[1]
Thread 2 -> input[2]
...
```

第二轮：

```text
Thread 0 -> input[8]
Thread 1 -> input[9]
Thread 2 -> input[10]
...
```

第三轮：

```text
Thread 0 -> input[16]
Thread 1 -> input[17]
Thread 2 -> input[18]
...
```

虽然单个 Thread 跨步访问，但是不同 Thread 在同一轮访问的是连续地址。

对于真实完整 Warp，原理完全一样。

所以：

```text
单个 Thread 的时间方向：
可以跨步访问

同一个 Warp 的空间方向：
尽量连续访问
```

你之前写 Matrix Transpose 时，固定 offset 分析 Warp 内地址，其实也是完全一样的思维方式。

---

## 9.4 为什么原文固定 Grid Size 为 SM 数量乘 4？

原文采用：

```cpp
int num_sms;

cudaDeviceGetAttribute(
    &num_sms,
    cudaDevAttrMultiProcessorCount,
    0
);

int grid_size = num_sms * 4;

int block_size = 256;
```

对于原文的 A100：

```text
SM 数量：108

Grid Size：108 × 4 = 432
```

整个 Kernel 只启动 432 个 Block。

每个 Block 通过 Grid Stride Loop 处理大量输入数据。

对比 V6：

```text
V6：

262144 个 Block
        ↓
262144 个 Partial Sum


V7：

432 个 Block
        ↓
432 个 Partial Sum
```

这样后续归约也会更加轻松。

---

## 9.5 SM 数量乘 4 是什么意思？

你可以暂时理解成：

```text
平均给每个 SM 准备 4 个 Block 的工作量
```

但是它不代表 GPU 一定会：

```text
严格给每个 SM 分配 4 个 Block
```

也不代表每个 SM 一定能够同时驻留这 4 个 Block。

仍然取决于：

```text
Register 使用量

Shared Memory 使用量

Block Size

硬件资源限制
```

例如 A100 每个 SM 最大 64 个 Warp。

如果 Block Size = 256，那么每个 Block 有 8 个 Warp。

假设每个 SM 同时驻留 4 个 Block：

$$
4\times8=32\ \mathrm{Warps}
$$

理论上对应：

$$
\frac{32}{64}=50\%
$$

的 Occupancy。

所以原文的 SM 数量乘 4，只是一个用于实验的 Grid Size 选择。

并不是说这样一定可以达到 100% Occupancy，也不是对所有 GPU 都最优。

以后你可以尝试：

```text
SM 数量 × 1

SM 数量 × 2

SM 数量 × 4

SM 数量 × 8

SM 数量 × 16
```

然后实际测量哪个更快。

---

## 9.6 现在再加入 float4

你在 2.2 已经学过：

```cpp
float4
```

一个 float4 包含四个 float：

```cpp
struct float4 {
    float x;
    float y;
    float z;
    float w;
};
```

这里只是帮助理解其成员结构，CUDA 已经提供了这个类型，不需要自己定义。

大小：

$$
4\times4=16\ \mathrm{Bytes}
$$

原来：

```cpp
float x = input[i];
```

每个 Thread 一次读取 1 个 float。

现在：

```cpp
const float4* input4 =
    reinterpret_cast<const float4*>(input);
```

这是你之前学过的：

```text
改变看待同一块内存的视角
```

原来：

```text
input[0]
input[1]
input[2]
input[3]

input[4]
input[5]
input[6]
input[7]
```

转换为：

```text
input4[0]：
input[0 ~ 3]

input4[1]：
input[4 ~ 7]
```

没有发生内存复制。

只是将指针重新解释成 float4 类型的指针。

---

## 9.7 float4 为什么可能更快？

对于同样 512 Bytes 数据：

使用普通 float 标量 Load，可能需要一个 Warp 执行 4 次加载指令。

而使用 float4：

```text
32 个 Lane

每个 Lane 加载 16 Bytes
```

一次 Warp 级的向量加载覆盖：

$$
32\times16=512\ \mathrm{Bytes}
$$

因此有机会用更少的 Load 指令完成相同的数据读取。

核心优化是：

```text
减少 Memory Instruction 数量

降低指令调度开销

增加每次迭代处理的数据量
```

注意：

float4 不会凭空减少需要读取的输入数据量。

也不代表显存带宽能够直接提升 4 倍。

在实际机器码中是否生成 128-bit Load，还要看编译器和具体代码。

另外，原文将 128B 作为一次内存事务进行解释，这是简化模型。

按照 NVIDIA 针对现代 GPU 的 Coalescing 分析方式，连续且对齐的 32 个 float，通常可以用四个 32B Sector 来描述。

你现在主要区分清楚：

```text
单条 Thread Load 的宽度

Warp 请求的总数据量

底层内存事务数量
```

它们是不同的概念。

---

## 9.8 float4 + Grid Stride Loop 怎么组合？

原来的 Grid Stride Loop：

```cpp
for (int i = gid; i < N; i += stride) {
    val += input[i];
}
```

现在 input 已经被看作 float4 数组。

因此新的数组长度为：

```cpp
int N4 = N / 4;
```

接下来：

```cpp
for (int i = gid; i < N4; i += stride) {

    float4 data = input4[i];

    val += data.x
         + data.y
         + data.z
         + data.w;
}
```

注意：

这里的 i 和 stride 都是以 float4 为单位的数组下标。

不是原来 float 数组的下标。

所以不需要再把 stride 乘 4。

因为：

```cpp
input4[i]
```

本身的指针运算就已经按照 16 Bytes 为单位进行偏移了。

---

## 9.9 用一个具体例子理解

假设总线程数为 8。

为了方便观察，假设输入有 80 个 float。

转换成 float4 后：

$$
N4=80/4=20
$$

那么：

```text
Thread 0：

input4[0]
input4[8]
input4[16]
```

对应原始 float：

```text
input[0 ~ 3]

input[32 ~ 35]

input[64 ~ 67]
```

Thread 1：

```text
input4[1]
input4[9]
input4[17]
```

对应：

```text
input[4 ~ 7]

input[36 ~ 39]

input[68 ~ 71]
```

第一轮：

```text
Thread 0 -> 0 ~ 3
Thread 1 -> 4 ~ 7
Thread 2 -> 8 ~ 11
...
Thread 7 -> 28 ~ 31
```

整个线程组覆盖了连续的 32 个 float。

所以：

```text
每个 Thread 读取 4 个连续 float

相邻 Thread 读取相邻的 float4

每轮整体访问连续的 Global Memory
```

这就是 Vectorized Load 与 Coalescing 的结合。

## 9.10 如果 N 不是 4 的倍数怎么办？

例如：

```text
N = 19
```

那么：

$$
N4=\lfloor19/4\rfloor=4
$$

完整 float4 可以处理：

```text
input[0 ~ 15]
```

还剩：

```text
input[16]
input[17]
input[18]
```

因此尾部起始位置：

```cpp
int tail_start = N4 * 4;
```

接下来使用普通 float 标量加载处理。

```cpp
for (
    int i = tail_start + gid;
    i < N;
    i += stride
) {
    val += input[i];
}
```

这里重新以 float 为单位。

由于尾部最多只有 3 个元素，所以实际上只有最前面的几个 Thread 会参与。

当然也可以写成：

```cpp
int tail_idx = tail_start + gid;

if (tail_idx < N) {
    val += input[tail_idx];
}
```

对于这个场景已经足够。

## 9.11 V7 完整 Kernel

沿用 V6 中已经封装好的：

```cpp
warp_reduce_sum()

block_reduce_sum()
```

最终的 V7 可以写成：

```cpp
__global__ void reduce_v7(
    const float* input,
    float* output,
    int N
) {
    int tid = threadIdx.x;

    int gid =
        blockIdx.x * blockDim.x + tid;

    int stride =
        gridDim.x * blockDim.x;

    float val = 0.0f;

    // 将 input 视为 float4 数组
    const float4* input4 =
        reinterpret_cast<const float4*>(input);

    int N4 = N / 4;

    // 每个 Thread 循环处理多个 float4
    for (int i = gid;
         i < N4;
         i += stride) {

        float4 data = input4[i];

        val += data.x
             + data.y
             + data.z
             + data.w;
    }

    // 处理不足 4 个元素的尾部
    int tail_idx = N4 * 4 + gid;

    if (tail_idx < N) {
        val += input[tail_idx];
    }

    // 所有 Thread 已经得到自己的局部和
    // 接下来进行 Block Reduce
    val = block_reduce_sum(val);

    // 写出每个 Block 的结果
    if (tid == 0) {
        output[blockIdx.x] = val;
    }
}
```

启动：

```cpp
int device_id;

cudaGetDevice(&device_id);

int num_sms;

cudaDeviceGetAttribute(
    &num_sms,
    cudaDevAttrMultiProcessorCount,
    device_id
);

int block_size = 256;

int grid_size = num_sms * 4;

reduce_v7<<<grid_size, block_size>>>(
    d_input,
    d_output,
    N
);
```

对应输出空间：

```cpp
cudaMalloc(
    &d_output,
    grid_size * sizeof(float)
);
```

因为每个 Block 输出一个 Partial Sum。

注意，float4 加载要求 input 地址满足 16B 对齐。

如果 input 是 cudaMalloc 返回的基础地址，通常满足要求。

但是如果 input 是某个带偏移的指针，例如：

```cpp
input = original_input + 1;
```

就不能直接认为它满足 float4 的对齐要求。

此外，以上代码以原文的 int 范围内数据规模为前提。处理更大的数组时，应考虑使用 size_t 或其他足够宽的整数类型计算全局索引。

---

## 9.12 V7 的完整数据流

假设 Block Size = 256。

```text
Global Memory
       │
       │ float4 Vectorized Load
       │ Grid Stride Loop
       ▼
每个 Thread 的局部 val
       │
       │ Register 中不断累加
       ▼
256 个 Thread Local Sum
       │
       │ Warp Shuffle Reduce
       ▼
8 个 Warp Sum
       │
       │ Lane 0 写 Shared Memory
       ▼
Shared Memory
       │
       │ __syncthreads()
       ▼
Warp 0 读取 8 个 Warp Sum
       │
       │ 其余 Lane 补零
       │ Warp Shuffle Reduce
       ▼
Block Sum
       │
       ▼
output[blockIdx.x]
```

这是非常典型的高性能 CUDA Reduction 的分层结构。

核心思想：

> 尽量在较小的通信范围内完成计算，只把必须交换的结果传递到更大的范围。

---

## 9.13 V7 还能继续优化吗？

可以。

例如原来的累加：

```cpp
val += data.x
     + data.y
     + data.z
     + data.w;
```

每次循环更新同一个 val。

这可能形成较长的指令依赖链。

可以考虑多个独立的 accumulator：

```cpp
float sum0 = 0.0f;
float sum1 = 0.0f;
float sum2 = 0.0f;
float sum3 = 0.0f;

for (int i = gid; i < N4; i += stride) {

    float4 data = input4[i];

    sum0 += data.x;
    sum1 += data.y;
    sum2 += data.z;
    sum3 += data.w;
}

float val = sum0 + sum1 + sum2 + sum3;
```

这样：

```text
sum0 的加法链

sum1 的加法链

sum2 的加法链

sum3 的加法链
```

相互独立。

编译器和硬件可能有更多机会利用 Instruction-Level Parallelism。

但也可能：

```text
增加 Register Usage
        ↓
降低 Occupancy
```

这个优化不属于原文 V7 的基本实现，是结合之前 Occupancy 和 ILP 知识补充的进一步优化方向。

最终是否更快，需要实际测试。

# 十一、怎么实际测试这些性能？

你刚才已经提前学过第 8 章性能分析工具链了。

现在终于可以用上了。

---

## 11.1 第一步：准备统一的测试条件

例如：

```cpp
int N = 1 << 26;

int block_size = 256;
```

所有版本使用：

```text
同一个 GPU

同一个输入数组

同一种数据类型

相同的计时方式
```

如果你要完全对照原文的数据规模，可以使用：

```cpp
int N = 1 << 27;
```

但前提是显存和 Host 内存足够。

---

## 11.2 第二步：注意 Grid Size 不一样

不能所有版本都使用同一个 Grid Size。

因为每个 Block 负责的数据量变了。

V0、V1、V2：

```cpp
int grid_size =
    (N + block_size - 1) / block_size;
```

V3、V4、V5、V6：

```cpp
int grid_size =
    (N + block_size * 2 - 1) / (block_size * 2);
```

V7：

```cpp
int grid_size = num_sms * 4;
```

这个区别非常重要。

因为 Grid Size 同时决定：

```text
每个 Block 负责什么数据

整个 Grid 能否覆盖所有输入

输出数组需要多大空间
```

---

## 11.3 第三步：先验证正确性

一开始可以让所有输入都是 1：

```cpp
std::vector<float> h_input(N, 1.0f);
```

那么理论结果：

$$
sum=N
$$

把所有 Partial Sum 拷回 CPU：

```cpp
cudaMemcpy(
    h_output.data(),
    d_output,
    grid_size * sizeof(float),
    cudaMemcpyDeviceToHost
);
```

然后使用 double 在 CPU 中汇总：

```cpp
double result = 0.0;

for (float x : h_output) {
    result += x;
}
```

验证：

```cpp
printf("Result: %.0f\n", result);
printf("Expected: %d\n", N);
```

不过全 1 输入只是初步测试。

还应该使用非均匀输入，并测试 N 不是 Block Size 或 4 的整数倍的情况。

例如：

```text
N = 1

N = 31

N = 257

N = 1027

N = 2^20 + 3
```

这样才能发现：

```text
索引计算错误

尾部元素遗漏

重复读取

边界处理错误
```

对于一般浮点数输入，CPU 和 GPU 的归约顺序不同，需要使用合理的浮点误差容忍范围，而不是要求结果始终完全相等。

---

## 11.4 第四步：CUDA Event 测量平均耗时

例如测试 V6：

```cpp
int warmup = 10;
int repeat = 100;

// 预热
for (int i = 0; i < warmup; ++i) {

    reduce_v6<<<grid_size, block_size>>>(
        d_input,
        d_output,
        N
    );
}

CUDA_CHECK(cudaGetLastError());
CUDA_CHECK(cudaDeviceSynchronize());

cudaEvent_t start, stop;

CUDA_CHECK(cudaEventCreate(&start));
CUDA_CHECK(cudaEventCreate(&stop));

// 开始计时
CUDA_CHECK(cudaEventRecord(start));

for (int i = 0; i < repeat; ++i) {

    reduce_v6<<<grid_size, block_size>>>(
        d_input,
        d_output,
        N
    );
}

CUDA_CHECK(cudaEventRecord(stop));
CUDA_CHECK(cudaGetLastError());
CUDA_CHECK(cudaEventSynchronize(stop));

float total_ms = 0.0f;

CUDA_CHECK(cudaEventElapsedTime(
    &total_ms,
    start,
    stop
));

double avg_ms = total_ms / repeat;

printf("Kernel time: %.4f ms\n", avg_ms);

CUDA_CHECK(cudaEventDestroy(start));
CUDA_CHECK(cudaEventDestroy(stop));
```

每个版本都使用这个计时逻辑，只需要替换对应的 Kernel Launch 和启动配置。

---

## 11.5 第五步：计算有效带宽

Reduce 主要读取 N 个 float。

为了方便比较各版本，可以统一使用输入数据量作为有效数据量：

$$
B=4N
$$

如果测得平均时间为 avg_ms，那么：

```cpp
double bytes = (double)N * sizeof(float);

double bandwidth = bytes / (avg_ms * 1e-3) / 1e9;
```

这个 bandwidth 的单位就是 GB/s。

也可以计算输入和输出的有效读写总量：

```cpp
double bytes =
    (double)N * sizeof(float)
    + (double)grid_size * sizeof(float);
```

但需要明确采用哪个口径，并在所有版本中保持一致。

假设你的 GPU 理论峰值带宽为：

```cpp
double peak_bandwidth = 2039.0;
```

那么：

```cpp
double utilization =
    bandwidth / peak_bandwidth * 100.0;

printf("Bandwidth: %.2f GB/s\n", bandwidth);

printf("Relative peak bandwidth: %.2f%%\n",
       utilization);
```

2039 GB/s 是原文 A100 的参数。

你自己的 GPU 不一定是这个值。

---

## 11.6 第六步：使用 Nsight Compute 验证优化原因

你现在不需要每个版本都进行复杂的 Profiling。

最推荐做以下几个有针对性的实验。

### 实验 A：V0 和 V1

我们想验证：

```text

```

主要观察：

```text
Warp 执行效率相关指标

Source Counters

分支和 Predication 相关信息
```

### 实验 B：V1 和 V2

我们想验证：

```text

```

可以使用：

```bash

```

然后再分析 V2。

观察：

```text
Shared Memory Bank Conflicts
```

这应该是最容易与理论建立联系的一组实验。

因为你现在已经可以自己推导：

```text
V1 为什么访问相同 Bank

V2 为什么访问不同 Bank
```

### 实验 C：V3 和 V6

我们想验证：

```text
Shared Memory Load / Store 是否减少

```

可以使用：

### 实验 D：V6 和 V7

```

```

注意：

二者不能直接画等号。

## 11.7 如何单独验证 float4 和 Grid Stride Loop 的收益？

原文 V7 一次性引入了两个优化：

```text
float4

Grid Stride Loop
```

如果 V7 比 V6 快了，我们不能立即确定提升主要来自哪一个。

更加严谨的实验可以拆成三个版本：

```text
V6：
每线程处理两个元素 + Warp Shuffle


V7a：
标量 Grid Stride Loop + Warp Shuffle


V7b：
float4 Grid Stride Loop + Warp Shuffle
```

比较：

```text
V6 vs V7a：

主要观察 Grid Stride Loop 的收益


V7a vs V7b：

主要观察向量化加载的收益
```

这样就能避免一次修改多个变量，导致不知道究竟哪个优化产生了效果。

这是性能工程中很重要的实验习惯。

# 十二、如何得到整个数组的最终 Reduce 结果？

原文主要给出了 Block Partial Sum。

但是如果你在 LeetGPU 上写完整的 Reduce 算子，通常还需要输出一个最终的 sum。

现在补充两种常见实现思路。

---

## 12.1 方案一：使用第二个 Kernel

例如第一阶段：

```cpp
reduce_v7<<<432, 256>>>(
    d_input,
    d_partial,
    N
);
```

得到：

```text
432 个 Partial Sum
```

第二阶段再归约这 432 个值。

例如使用每个 Thread 读取两个元素的 V6：

```cpp
reduce_v6<<<1, 256>>>(
    d_partial,
    d_result,
    432
);
```

一个 256 Thread 的 V6 Block 最多处理 512 个元素。

所以只需要一个 Block 就可以完成剩余 432 个值的归约。

流程：

```text
原始 N 个元素
        ↓
Reduce Kernel 1
        ↓
432 个 Partial Sum
        ↓
Reduce Kernel 2
        ↓
最终一个 sum
```

如果两个 Kernel 位于同一个 CUDA Stream，那么后面的 Kernel 会在前面的 Kernel 完成后执行。

不需要在两个 Launch 之间特意插入 CPU 端的 `cudaDeviceSynchronize()`。

这种方案的优点：

- 不需要大量 Block 竞争同一个原子地址。
- 归约结构比较清晰。
- 容易控制归约顺序。

缺点：

- 需要中间输出数组。
- 多一次或多次 Kernel Launch。
- 需要额外的 Global Memory 读写。

---

## 12.2 方案二：每个 Block 进行一次 atomicAdd

假设你已经完成：

```cpp
val = block_reduce_sum(val);
```

原来：

```cpp
if (tid == 0) {
    output[blockIdx.x] = val;
}
```

现在可以改成：

```cpp
if (tid == 0) {
    atomicAdd(output, val);
}
```

这样每个 Block 的局部和都会原子地累加到最终的 output 中。

注意，在 Kernel 执行之前，必须将 output 初始化为 0。

```cpp
cudaMemset(d_output, 0, sizeof(float));
```

否则就会在未初始化的数据上累加。

如果你使用 CUDA Event 连续运行多个这样的 Reduce，每次执行前也需要重新初始化 output，或者设计其他正确的测试流程。

否则重复运行会把上一次结果继续累加进去。

这种方式的优点：

```text
一次 Kernel 就能完成最终 Reduce
```

缺点：

```text
多个 Block 竞争同一个 Global Memory 地址

浮点数累加顺序可能不固定
```

但是 V7 只启动少量 Block，因此 Global Atomic 数量也会比较少。

这就是为什么：

```text
Grid Stride Loop

+

Warp Reduce

+

Block Reduce

+

Global Atomic
```

经常可以组合使用。

---

## 12.3 为什么不是每个 Thread 都直接 atomicAdd？

例如：

```cpp
atomicAdd(output, input[gid]);
```

当然也可以实现数组求和。

但是假设有 N 个有效 Thread，就会产生大约 N 次 Global Atomic。

所有 Thread 竞争同一个地址。

而我们先进行：

```text
Thread Local Sum

Warp Reduce

Block Reduce
```

最后只有每个 Block 的 Thread 0 执行：

```cpp
atomicAdd(output, val);
```

就可以把大量 Atomic 操作减少到 Grid Size 次。

这正是你在 2.4 学过的 Hierarchical Reduction。

# 十三、把 V0～V7 的优化路线彻底串起来

## V0：最基础的并行归约

```text
Global Memory
        ↓
Shared Memory
        ↓
树形归约
        ↓
Partial Sum
```

问题：

```text
有效 Thread 分散在多个 Warp 中
```

---

## V1：改变任务映射

```cpp
int index = tid * 2 * step;
```

目标：

```text
让工作 Thread 集中在前面的 Warp
```

减少 Warp Divergence。

但是引入 Shared Memory 跨步访问。

---

## V2：改变归约顺序

```cpp
for (int step = blockDim.x / 2;
     step > 0;
     step >>= 1)
```

目标：

```text
让 Warp 内工作 Thread 连续

让 Warp 内 Shared Memory 地址连续
```

改善执行效率和 Bank Conflict。

---

## V3：每个 Thread 处理多个数据

```cpp
val = input[gid]
    + input[gid + blockDim.x];
```

目标：

```text
提前在 Thread 内进行局部归约

减少 Block 数量

摊销同步与归约开销
```

---

## V4：缩小同步范围

```text
Block 级归约
        ↓
Warp 级归约
```

目标：

```text
减少不必要的 Block Barrier
```

---

## V5：使用编译期信息

```cpp
template<int BLOCK_SIZE>
```

目标：

```text
消除不必要的运行时循环开销

生成针对固定 Block Size 的 Kernel
```

---

## V6：改变线程通信方式

```cpp
__shfl_down_sync(...)
```

目标：

```text
Warp 内通过 Shuffle 交换数据

只在 Warp 间使用 Shared Memory
```

减少 Shared Memory 访问和同步。

---

## V7：进一步改善数据加载与工作分配

```cpp
float4

Grid Stride Loop
```

目标：

```text
减少加载指令数量

增加每个 Thread 的有效工作量

减少 Block 和 Partial Sum 数量

提高有效带宽
```

---

# 十四、这篇文章真正想让你学会什么？

我认为这一篇最有价值的不是：

```text
记住 V0～V7 的代码
```

而是建立下面几种 CUDA 性能优化思维。

## 14.1 Thread Mapping

同一份计算任务，可以由不同的 Thread 来完成。

```text
数学结果不变

但是 Warp 执行效率可能完全不同
```

代表：

```text
V0 -> V1
```

---

## 14.2 Memory Access Pattern

同样的数据，可以用不同的顺序进行访问。

```text
数学结果不变

但是 Shared Memory Bank Conflict 可能完全不同
```

代表：

```text
V1 -> V2
```

这与你之前写 Matrix Transpose 完全是同一个思维。

---

## 14.3 Thread Coarsening

一个 Thread 不一定只处理一个元素。

```text
Thread 处理更多数据
        ↓
减少并行任务管理的固定开销
```

代表：

```text
V3

V7
```

这也是后面 GEMM 中 Register Tiling 的一个重要背景。

---

## 14.4 Hierarchical Communication

尽量在更小的作用域中完成工作。

```text
Thread 内：
Register

Warp 内：
Shuffle

Block 内：
Shared Memory

Block 间：
Global Memory / Atomic / 多阶段 Kernel
```

通信范围越大，通常需要考虑的同步和内存开销就越复杂。

代表：

```text
V4

V6

V7
```

---

## 14.5 Compile-time Specialization

尽可能把编译时已经知道的信息告诉编译器。

例如：

```cpp
template<int BLOCK_SIZE>
```

或者后面 GEMM 中经常出现的：

```cpp
template<
    int BM,
    int BN,
    int BK,
    int TM,
    int TN
>
```

这样编译器可以针对具体配置进行特化。

代表：

```text
V5
```

---

## 14.6 Vectorization

在地址连续且满足对齐要求的情况下：

```text
一次 Load 读取更多元素
```

代表：

```text
V7 的 float4
```

核心是减少指令开销，而不是凭空减少实际输入数据量。

# 十六、生产环境中怎么选择 Reduce 实现？

原文最后提到了 NVIDIA CUB 库。

例如：

```cpp
cub::DeviceReduce::Sum(...)
```

CUB 提供了经过优化的 GPU Reduce 实现。

它会处理许多实际工程问题，例如：

```text
GPU 架构差异

不同数据类型

不同输入规模

归约策略选择

临时空间管理
```

实际生产项目中，不是所有算子都需要自己从头实现。

通常优先使用成熟的库，并根据实际场景决定是否需要自定义 Kernel。

那么为什么还要学手写 Reduce？

因为你需要理解：

```text
成熟库为什么快？

Profiler 中的指标是什么意思？

自己的特殊算子如何优化？

Reduce 如何与其他计算融合？
```

尤其后面 Softmax、RMSNorm 等算子中，Reduce 往往只是整个 Kernel 的一个组成部分。

你可能需要把它直接融合进其他计算过程，而不是单独调用一个 Reduce 算子。

# 十九、最后总结

整个 Reduce 优化路线可以压缩成：

```text
V0：能正确并行计算
        ↓
V1：让 Warp 更有效地计算
        ↓
V2：让 Shared Memory 更高效地访问
        ↓
V3：让每个 Thread 多承担一点工作
        ↓
V4：减少不必要的大范围同步
        ↓
V5：减少运行时循环开销
        ↓
V6：减少跨线程通信开销
        ↓
V7：提高数据加载效率并摊销 Block 开销
```

而最终的高性能 Reduce 数据流：

```text
Global Memory
        ↓
Vectorized Load
        ↓
Grid Stride Loop
        ↓
Thread Local Sum
        ↓
Warp Shuffle Reduce
        ↓
Shared Memory
        ↓
Block Reduce
        ↓
Global Atomic / 第二阶段 Reduce
        ↓
Final Result
```

你现在真正需要建立的习惯是：

每优化一个 Kernel，都明确自己到底减少了什么。

```text
计算量？

Memory Traffic？

Memory Instructions？

Bank Conflict？

Warp Divergence？

Synchronization？

Atomic Contention？

还是 Block 调度开销？
```

然后使用 Benchmark 和 Profiler 验证自己的推导。

这才是 CUDA Kernel Optimization，而不只是会写 CUDA 代码。
