# 一、GEMM 的基本原理

## 1.1 矩阵维度

我们现在计算：

$$
C=AB
$$

其中：

$$
A\in\mathbb{R}^{M\times K}
$$

$$
B\in\mathbb{R}^{K\times N}
$$

$$
C\in\mathbb{R}^{M\times N}
$$

具体来说：

$$
C_{ij}=\sum_{k=0}^{K-1}A_{ik}B_{kj}
$$

三个维度的含义：

| 维度 | 含义 |
|---|---|
| M | A 的行数，也是 C 的行数 |
| N | B 的列数，也是 C 的列数 |
| K | A 的列数、B 的行数，也就是归约维度 |

可以画成：

```text
         K                   N
     ┌────────┐         ┌──────────┐
     │        │         │          │
   M │   A    │    ×  K │    B     │
     │        │         │          │
     └────────┘         └──────────┘

                ↓

                 N
           ┌──────────┐
         M │    C     │
           └──────────┘
```

这里最重要的是区分：

```text
M、N：决定输出元素的位置。

K：决定每个输出元素需要累加多少次。
```

换句话说：

```text
M、N 方向可以自然并行。

K 方向存在求和归约。
```

当然 K 方向也可以并行拆分，这就是后面可能遇到的 Split-K，但现在先不考虑。

---

## 1.2 为什么 GEMM 的计算量是 2MNK？

计算一个 C[i][j]：

```cpp
float sum = 0.0f;

for (int k = 0; k < K; ++k) {
    sum += A[i][k] * B[k][j];
}
```

每轮：

```text
一次乘法
+
一次加法
```

按照 GEMM 的标准性能统计口径，每个输出元素：

$$
2K\ \mathrm{FLOPs}
$$

整个 C 有 M × N 个元素。

所以：

$$
F=2MNK
$$

严格从数学运算次数看，K 个乘积相加只需要 K-1 次加法，但工程上 GEMM 通常统一使用 2MNK 作为 FLOPs 统计口径。

---

## 1.3 什么是 FMA？

FMA：

```text
Fused Multiply-Add
```

融合乘加。

计算：

$$
d=ab+c
$$

在 CUDA 中：

```cpp
sum += a * b;
```

编译器通常能够将其转换为一条 FP32 FFMA 指令。

虽然是一条指令，但它完成了：

```text
1 次乘法
+
1 次加法
```

所以计为：

```text
2 FLOPs
```

注意区分：

```text
Instruction 数量
≠
FLOPs 数量
```

后面 GEMM 性能优化的一个重要目标，就是让 GPU 尽可能持续执行大量 FFMA 指令。

# 二、GEMM 的性能指标

## 2.1 为什么不再主要看带宽利用率？

你之前自己实现的 Reduce V7：

```text
GPU: RTX 4060 Laptop

输入规模：2^27 个 float

Average time: 2.6651 ms

Effective bandwidth: 201.45 GB/s

Peak bandwidth: 256.03 GB/s

Bandwidth utilization: 78.68%
```

Reduce 的计算量很小，因此主要看数据搬运速度。

但是 GEMM 有大量乘加运算。

优化得比较好的 GEMM，往往希望接近计算单元的吞吐上限。

所以 GEMM 主要看：

```text
GFLOPS

TFLOPS

相对于理论峰值算力的比例

相对于 cuBLAS 的性能比例
```

---

## 2.2 怎么计算实际 TFLOPS？

**TFLOPS = Tera Floating-point Operations Per Second**，即每秒万亿次浮点运算。

- FLOPS：每秒浮点运算次数
- GFLOPS：每秒 \(10^9\) 次浮点运算
- TFLOPS：每秒 \(10^{12}\) 次浮点运算

公式：

$$
P=\frac{2MNK}{t\times10^{12}}
$$

其中 t 的单位为秒。

假设：

```cpp
int M = 4096;
int N = 4096;
int K = 4096;
```

总计算量：

$$
F=2\times4096^3
$$

如果 Kernel 耗时为 20 ms：

$$
P=\frac{2\times4096^3}{0.02\times10^{12}}
$$

得到：

$$
P\approx6.87\ \mathrm{TFLOPS}
$$

所以你之前写的 Reduce Benchmark 几乎可以直接复用。

只需要把：

```cpp
double bandwidth =
    bytes / (avg_ms / 1000.0) / 1e9;
```

换成：

```cpp
double flops = 2.0 * M * N * K;

double tflops =
    flops / (avg_ms / 1000.0) / 1e12;

printf("Performance: %.2f TFLOPS\n", tflops);
```

注意使用：

```cpp
2.0 * M * N * K
```

而不是：

```cpp
double flops = 2 * M * N * K;
```

因为后者可能先进行 int 乘法，发生整数溢出后才转换成 double。

4096³ 已经远远超过 int 的表示范围了。

---

## 2.3 怎么获得理论峰值算力？

对于普通 CUDA Core 执行 FP32 FMA，可以近似计算：

$$
P_{\mathrm{peak}}
=
N_{\mathrm{SM}}
\times
N_{\mathrm{FP32/SM}}
\times
f
\times
2
$$

其中：

- SM 数量。
- 每个 SM 的 FP32 运算单元数量。
- GPU Core Clock，单位 Hz。
- FMA 每次对应 2 FLOPs。

对于你的 RTX 4060 Laptop，可以使用 CUDA API 查询 SM 数量和 GPU 时钟频率，再结合 Ada 架构每 SM 的 FP32 运算单元数量进行估算。

```cpp
int device;
CUDA_CHECK(cudaGetDevice(&device));

int num_sms;
int clock_khz;

CUDA_CHECK(cudaDeviceGetAttribute(
    &num_sms,
    cudaDevAttrMultiProcessorCount,
    device
));

CUDA_CHECK(cudaDeviceGetAttribute(
    &clock_khz,
    cudaDevAttrClockRate,
    device
));

// Ada SM86 不是正确的架构编号。
// RTX 4060 Laptop 属于 Ada，Compute Capability 8.9。
constexpr int fp32_cores_per_sm = 128;

double peak_tflops =
    2.0 * num_sms
    * fp32_cores_per_sm
    * clock_khz
    / 1e9;

double utilization =
    tflops / peak_tflops * 100.0;

printf("Peak FP32: %.2f TFLOPS\n", peak_tflops);

printf("Compute utilization: %.2f%%\n", utilization);
```

这里得到的是根据硬件参数估算的 FP32 理论峰值，不是 GPU 实际运行时每个周期的真实算力。

笔记本 GPU 的实际频率会受到温度、功耗和动态 Boost 的影响。

另外，fp32_cores_per_sm 是针对架构选择的参数，不能换一张显卡仍然无条件使用 128。

最重要的是：

> 不要拿普通 FP32 CUDA Core 的 GEMM 性能，去除以 FP16 Tensor Core 的理论峰值算力。

它们对应不同的计算硬件和数据精度。

# 三、Roofline 模型：为什么 GEMM 需要数据复用？

## 3.1 Arithmetic Intensity

之前已经学过：

$$
AI=\frac{\mathrm{FLOPs}}{\mathrm{Bytes}}
$$

算术强度表示：

每搬运一个 Byte 的数据，可以完成多少浮点计算。

GPU 有两个基本性能上限：

```text
计算能力上限

内存带宽上限
```

因此：

$$
P\leq\min(P_{\mathrm{peak}},BW_{\mathrm{peak}}\times AI)
$$

画成简化的 Roofline：

```text
Performance
    ↑
    │
    │                  ───────────── 计算上限
    │                /
    │              /
    │            /
    │          /
    │        /
    │      /
    └──────────────────────────────→ AI
        Memory-Bound    Compute-Bound
```

左侧斜线：

数据搬运能力限制了计算性能。

右侧横线：

即使能够提供更多数据，计算单元也已经达到理论上限。

中间的交点叫 Ridge Point，也就是平衡点。

$$
AI_{\mathrm{ridge}}=\frac{P_{\mathrm{peak}}}{BW_{\mathrm{peak}}}
$$

注意，Roofline 表示理论性能上界，不代表算术强度一旦超过平衡点，Kernel 就一定能跑满计算单元。

实际还可能存在指令、同步、并行度等其他瓶颈。

---

### 3.1.0 带宽，算术强度相乘的含义

**数据搬运量=读取的字节数+写入的字节数**

Roofline 模型用的是**峰值带宽**，也就是硬件每秒能够读写的最大字节数。

我们可以从实际性能推导：

实际有效带宽：

$$
BW_{\mathrm{effective}}=\frac{\mathrm{Bytes}_{read}+\mathrm{Bytes}_{write}}{t}
$$

算术强度：

$$
AI=\frac{\mathrm{FLOPs}}{\mathrm{Bytes}_{read}+\mathrm{Bytes}_{write}}
$$

两者相乘，恰好得到实际计算性能：

$$
P_{\mathrm{actual}}=BW_{\mathrm{effective}}\times AI
$$

但实际带宽不可能超过硬件峰值带宽：

$$
BW_{\mathrm{effective}}\leq BW_{\mathrm{peak}}
$$

因此：

$$
P_{\mathrm{actual}}\leq BW_{\mathrm{peak}}\times AI
$$

再考虑硬件本身的峰值算力，就得到 Roofline 公式：

$$
\boxed{P_{\mathrm{actual}}\leq\min(P_{\mathrm{peak}},BW_{\mathrm{peak}}\times AI)}
$$

所以区别就是：

- **有效带宽 × AI**：实际计算性能。
- **峰值带宽 × AI**：假设硬件的内存读写能力被完全利用，当前算子受内存带宽限制的理论计算性能上限。

这也是为什么 Roofline 使用峰值带宽，因为我们想求的是**性能上限，而不是实际性能**。

---

## 3.2 结合你的 RTX 4060 Laptop

你之前测得的理论显存带宽：

$$
BW_{\mathrm{peak}}=256.03\ \mathrm{GB/s}
$$

为了说明问题，暂时假设你的 FP32 理论算力是 12 TFLOPS。

那么平衡点为：

$$
AI_{\mathrm{ridge}}
=
\frac{12\times10^{12}}{256.03\times10^9}
\approx46.87\ \mathrm{FLOP/Byte}
$$

这里的 12 TFLOPS 只是教学假设，实际使用时应换成你的 GPU 对应的峰值参数。

而 Reduce 的算术强度：

$$
AI_{\mathrm{reduce}}\approx0.25
$$

所以 Reduce 在通常的大规模输入下，本质上很难通过增加计算吞吐量获得巨大提升。

GEMM 不一样。

它存在大量数据复用机会，能够显著提高算术强度。

---

## 3.3 GEMM 到底在哪里存在数据复用？

假设：

```text
A：

a00 a01
a10 a11

B：

b00 b01
b10 b11
```

计算：

```text
C00 = a00*b00 + a01*b10

C01 = a00*b01 + a01*b11

C10 = a10*b00 + a11*b10

C11 = a10*b01 + a11*b11
```

你会发现：

```text
a00 同时被 C00 和 C01 使用。

b00 同时被 C00 和 C10 使用。
```

更一般地说：

```text
A[i][k]

会被 C[i][0 ~ N-1] 使用。

B[k][j]

会被 C[0 ~ M-1][j] 使用。
```

也就是说：

- A 的元素沿 N 方向复用。
- B 的元素沿 M 方向复用。

这就是 GEMM Tiling 的数学基础。

# 四、Naive GEMM：最朴素的实现

## 4.1 一个 Thread 负责一个 C 元素

这是最自然的映射：

```text
Thread 0 → C[0][0]

Thread 1 → C[0][1]

Thread 2 → C[0][2]

...
```

每个 Thread 遍历完整 K 维度。

```cpp
__global__ void gemm_naive(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K
) {
    int row =
        blockIdx.y * blockDim.y + threadIdx.y;

    int col =
        blockIdx.x * blockDim.x + threadIdx.x;

    if (row < M && col < N) {

        float sum = 0.0f;

        for (int k = 0; k < K; ++k) {

            sum += A[row * K + k]
                 * B[k * N + col];
        }

        C[row * N + col] = sum;
    }
}
```

启动：

```cpp
dim3 block(32, 8);

dim3 grid(
    (N + block.x - 1) / block.x,
    (M + block.y - 1) / block.y
);

gemm_naive<<<grid, block>>>(
    d_A, d_B, d_C, M, N, K
);
```

你之前写 Matrix Transpose 的经验在这里可以直接使用。

```text
threadIdx.x → 列

threadIdx.y → 行
```

由于 blockDim.x = 32，一个 Warp 恰好负责 C 的一行中的 32 个连续元素。

---

## 4.2 Naive GEMM 的 Global Memory 访问一定很差吗？

不一定。

我们从 Warp 的视角分析。

固定某个 k。

Warp 内所有 Thread 的 row 相同，而 col 连续。

读取 A：

```cpp
A[row * K + k]
```

整个 Warp 读取的是同一个 A 元素。

```text
Lane 0  → A[row][k]

Lane 1  → A[row][k]

...

Lane 31 → A[row][k]
```

这种访问可以由内存系统合并处理，并利用 Cache。

读取 B：

```cpp
B[k * N + col]
```

Warp 内：

```text
Lane 0  → B[k][0]

Lane 1  → B[k][1]

...

Lane 31 → B[k][31]
```

地址连续。

所以 Naive GEMM 的主要问题并不是：

```text
所有 Global Memory Access 都不 Coalesced。
```

真正的问题是：

> 不同线程反复请求同一批 A、B 数据，却没有显式组织这些数据的复用。

Cache 能够自动提供一定程度的复用，但是我们可以使用 Shared Memory，更主动地控制数据如何被整个 Block 共享。

---

## 4.3 Naive GEMM 的算术强度

一个 Thread 计算一个 C 元素。

每个 k：

```text
读取一个 A float：4B

读取一个 B float：4B

一次乘法 + 一次加法：2 FLOPs
```

所以从每线程逻辑加载量的角度：

$$
AI=\frac{2}{8}=0.25
$$

对于整个 K：

$$
AI=\frac{2K}{8K}=\frac{1}{4}
$$

注意：

这个 0.25 是忽略 Cache 复用、合并请求和输出写回后的简化逻辑访存模型。

不能直接认为 Naive GEMM 的真实 DRAM 算术强度一定是 0.25。

硬件实际访问量需要通过 Profiler 确认。

#### 我的算法

对于每个 thread：

- 读取 A：$K$ 个 float。
- 读取 B：$K$ 个 float。
- 写入 C：$1$ 个 float。
- 执行计算：$K$ 次乘加，即 $2K$ FLOPs。

总内存读写量：

$$
\mathrm{Bytes}=4(2K+1)=8K+4
$$

因此算术强度：

$$
AI=\frac{2K}{8K+4}
=\frac{1}{4+\frac{2}{K}}
$$

当 $K$ 足够大时：

$$
\boxed{AI\approx\frac14=0.25\ \mathrm{FLOPs/Byte}}
$$

图中的计算是直接忽略了最后写入 C 的 4 Bytes。

不过，这里算的是**逻辑内存访问量对应的算术强度**，没有考虑 Cache 复用、合并访问等因素，因此不一定等于实际 DRAM 的算术强度。

# 五、Block Tiling：Shared Memory 数据复用

这是你现在最需要理解的一部分。

## 5.1 什么是 Tile？

Tile 就是矩阵中的一个矩形子区域。

假设 C 是 8×8 矩阵。

我们让每个 Block 负责 4×4。

```text
C：

┌─────────┬─────────┐
│         │         │
│ Block 0 │ Block 1 │
│         │         │
├─────────┼─────────┤
│         │         │
│ Block 2 │ Block 3 │
│         │         │
└─────────┴─────────┘
```

对于一个 Block：

```text
它不再只关心一个 C 元素。

而是负责计算 C 中的一整块区域。
```

定义：

```cpp
BM = Block Tile 在 M 方向的大小

BN = Block Tile 在 N 方向的大小

BK = 每次沿 K 方向处理的数据量
```

例如：

```cpp
BM = 128;
BN = 128;
BK = 8;
```

一个 Block 最终负责：

$$
128\times128=16384
$$

个 C 元素。

但是它每次只沿 K 方向处理 8 个元素。

---

## 5.2 为什么需要沿 K 方向切分？

假设：

```text
A: 4096 × 4096

B: 4096 × 4096

C: 4096 × 4096
```

我们现在计算 C 左上角的 128×128。

数学上需要：

```text
A 的前 128 行，完整 K 维度。

B 的前 128 列，完整 K 维度。
```

也就是：

```text
A_tile: 128 × 4096

B_tile: 4096 × 128
```

这两个区域加起来：

$$
4(128\times4096+4096\times128)=4194304\ \mathrm{Bytes}
$$

也就是 4 MiB。

单个 Block 的 Shared Memory 根本放不下这么大的数据。

所以我们沿 K 维度分批加载：

```text
第一轮：

A[0:128][0:8]

B[0:8][0:128]


第二轮：

A[0:128][8:16]

B[8:16][0:128]


第三轮：

A[0:128][16:24]

B[16:24][0:128]
```

每次只需要：

```cpp
__shared__ float As[BM][BK];

__shared__ float Bs[BK][BN];
```

对于 BM=BN=128、BK=8：

$$
4(128\times8+8\times128)=8192\ \mathrm{Bytes}
$$

只需要 8 KiB。

---

## 5.3 为什么每轮计算之后可以直接丢掉这一批 A、B？

因为矩阵乘法可以分解为多个局部矩阵乘积的求和。

假设：

```text
A = [ A0 | A1 | A2 ]

B = [ B0 ]
    [ B1 ]
    [ B2 ]
```

那么：

$$
AB=A_0B_0+A_1B_1+A_2B_2
$$

我们只需要维护一个不断累加的 C_tile。

```text
C_tile 初始化为 0

        ↓

加载 A0、B0

C_tile += A0 × B0

        ↓

加载 A1、B1

C_tile += A1 × B1

        ↓

加载 A2、B2

C_tile += A2 × B2

        ↓

最终 C_tile
```

每轮 A、B 数据使用完以后，就不再需要保存。

但是 C 的 accumulator 必须一直保留，直到完整 K 维度计算结束。

所以最理想的数据生命周期是：

```text
A、B Tile：

每轮重新加载。


C accumulator：

一直留在 Register 中。
```

这是 GEMM 和之前 Matrix Transpose 很重要的区别。

Transpose：

```text
Shared Memory 主要用来改变访存方向。
```

GEMM：

```text
Shared Memory 主要用来提高数据复用率。
```

---

## 5.4 先从一个最简单的 Shared Memory GEMM 开始

原文直接使用了 128×128 的 Block Tile，并且每线程负责多个元素。

为了避免一下子引入太多索引，建议先实现下面这个更简单的版本：

```text
Block Size：16×16

C Tile：16×16

每个 Thread：负责一个 C 元素。

BK：16
```

完整代码：

```cpp
template<int TILE>
__global__ void gemm_shared_tiling(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K
) {
    __shared__ float As[TILE][TILE];
    __shared__ float Bs[TILE][TILE];

    int tx = threadIdx.x;
    int ty = threadIdx.y;

    int row = blockIdx.y * TILE + ty;
    int col = blockIdx.x * TILE + tx;

    float sum = 0.0f;

    for (int bk = 0; bk < K; bk += TILE) {

        // 加载 A 的子块
        int a_col = bk + tx;

        As[ty][tx] =
            (row < M && a_col < K)
            ? A[row * K + a_col]
            : 0.0f;

        // 加载 B 的子块
        int b_row = bk + ty;

        Bs[ty][tx] =
            (b_row < K && col < N)
            ? B[b_row * N + col]
            : 0.0f;

        __syncthreads();

        // 使用 Shared Memory 中的两个 Tile
        #pragma unroll
        for (int k = 0; k < TILE; ++k) {

            sum += As[ty][k] * Bs[k][tx];
        }

        __syncthreads();
    }

    if (row < M && col < N) {
        C[row * N + col] = sum;
    }
}
```

启动：

```cpp
constexpr int TILE = 16;

dim3 block(TILE, TILE);

dim3 grid(
    (N + TILE - 1) / TILE,
    (M + TILE - 1) / TILE
);

gemm_shared_tiling<TILE><<<grid, block>>>(
    d_A, d_B, d_C, M, N, K
);
```

这个版本建议你一定要独立写出来。

---

## 5.5 怎么理解 Shared Memory 中的计算？

假设：

```text
TILE = 4
```

某个 Thread：

```cpp
ty = 1;
tx = 2;
```

它负责计算 C_tile 中的：

```text
C[1][2]
```

那么一轮 K-Tile 内部需要：

```text
As[1][0] * Bs[0][2]

As[1][1] * Bs[1][2]

As[1][2] * Bs[2][2]

As[1][3] * Bs[3][2]
```

累加起来。

对应：

```cpp
for (int k = 0; k < TILE; ++k) {
    sum += As[ty][k] * Bs[k][tx];
}
```

这和 Naive GEMM 的数学公式完全一样。

只不过原来：

```cpp
A[row * K + k]

B[k * N + col]
```

从 Global Memory 读取。

现在：

```cpp
As[ty][k]

Bs[k][tx]
```

从 Shared Memory 读取。

---

## 5.6 为什么 K-Loop 中需要两次 __syncthreads()？

这两个 Barrier 保护的是不同的数据依赖。

第一次：

```cpp
加载 As 和 Bs;

__syncthreads();

开始计算;
```

目的是保证：

```text
所有 Thread 都已经完成当前 Tile 的写入。

然后其他 Thread 才能安全读取。
```

第二次：

```cpp
计算完成;

__syncthreads();

加载下一个 Tile;
```

目的是保证：

```text
所有 Thread 都已经读完当前 Tile。

然后才能覆盖 Shared Memory。
```

如果删除第二次同步：

```text
Warp 0 已经计算完当前 Tile。

Warp 0 开始加载下一个 Tile，覆盖 As。

但是 Warp 1 还在读取旧 As。

于是 Warp 1 读到了下一轮的数据。
```

就产生了 Data Race。

所以：

```text
第一个 Barrier：

防止读得太早。


第二个 Barrier：

防止写得太早。
```

这个区别以后学习 Double Buffering 时非常重要。

---

## 5.7 为什么不能越界就直接 return？

错误思路：

```cpp
if (row >= M || col >= N) {
    return;
}
```

在 Naive GEMM 中这样做没有问题。

但是 Shared Memory Tiling 中，一个输出位置越界的线程仍然可能负责加载其他线程需要的 A 或 B 数据。

如果它提前退出，可能导致 Shared Memory 数据缺失。

而且还要考虑后续 Barrier 和线程协作的正确性。

所以正确结构是：

```text
加载 A、B 时：

越界补零。


参与 Block 计算和同步。


最后写回 C 时：

检查输出位置是否合法。
```

这和你之前 Reduce 的补零思路完全一致。

---

# 六、Block Tiling 为什么提高算术强度？

## 6.1 先看一轮 K-Tile

**这里分析的是，一次循环，也就是 k_offset 固定。BM,BN 就是这个 block 负责的 M，N 长度；BK 就是我对 K 的分块长度。**

一个 Block 负责：

$$
BM\times BN
$$

个 C 元素。

每轮 K-Tile 处理 BK 个归约元素。

计算量：

$$
F=2BM\times BN\times BK
$$

Global Memory 中需要加载：

```text
A Tile：BM × BK 个 float。

B Tile：BK × BN 个 float。
```

总字节数：

$$
B=4(BM\times BK+BK\times BN)
$$

于是：

$$
AI=\frac{2BM\times BN\times BK}{4(BM\times BK+BK\times BN)}
$$

约掉 BK：

$$
AI=\frac{BM\times BN}{2(BM+BN)}
$$

也可以写成：

$$
AI=\frac{1}{2(\frac{1}{BM}+\frac{1}{BN})}
$$

这是原文非常重要的一个公式。

---

## 6.2 如果 BM = BN 呢？

令：

$$
BM=BN=T
$$

那么：

$$
AI=\frac{T^2}{4T}=\frac{T}{4}
$$

于是：

| Block Tile 大小 | 理想输入复用算术强度 |
|---|---:|
| 1×1 | 0.25 FLOP/B |
| 16×16 | 4 FLOP/B |
| 32×32 | 8 FLOP/B |
| 64×64 | 16 FLOP/B |
| 128×128 | 32 FLOP/B |
| 256×256 | 64 FLOP/B |

这说明：

> 扩大输出 Tile，可以让加载进来的每个 A、B 元素服务更多计算。

例如 128×128 Tile：

```text
每个 A 元素被用于 128 个不同列的 C。

每个 B 元素被用于 128 个不同行的 C。
```

所以输入数据量不变的情况下，有更多计算能够使用它们。

注意，这里的 AI 是基于每 Block 的 A、B Tile 加载量，忽略 C 写回、跨 Block Cache 复用等因素的模型。

---

## 6.3 为什么 BK 被约掉了？

这是一个非常值得思考的问题。

很多人会以为：

```text
BK 越大，数据复用率一定越高。
```

实际上，在这个简化模型中：

```text
BK 增大一倍：

计算量增大一倍。

输入加载量也增大一倍。
```

因此比值不变。

决定 Block 级输入复用率的主要是：

```text
BM

BN
```

而 BK 更多影响：

```text
Shared Memory 占用

K-Loop 迭代次数

Barrier 次数

加载指令组织

流水线设计

Register 使用量
```

例如：

```text
BK = 8：

K-Loop 迭代次数较多。

BK = 16：

K-Loop 迭代次数减半。

但是 Shared Memory 占用翻倍。
```

所以 BK 也是需要调优的参数，不是越大越好。

---

## 6.4 为什么 BM 和 BN 通常尽量接近？

在 BK 固定时：

$$
S_{\mathrm{smem}}=4BK(BM+BN)
$$

假设 Shared Memory 预算固定，那么 **BM+BN 固定**。

此时：

$$
AI=\frac{BM\times BN}{2(BM+BN)}
$$

想让 AI 最大，就希望 BM×BN 尽可能大。

根据均值不等式，在两者和固定时：

$$
BM=BN
$$

乘积最大。

所以方形 Tile 在这个简化条件下，数据复用率比较好。

但实际 GEMM 不一定都使用正方形 Tile。

例如 LLM Decode 可能：

```text
M 很小

N 很大

K 很大
```

如果仍然使用 128×128 的 C Tile，可能产生大量无效计算。

所以 Tile Shape 需要结合矩阵形状、硬件资源以及并行度选择。

---

# 七、原文的 Block Tiling：128×128 Tile 如何由 256 个 Thread 完成？

现在开始进入原文比较复杂的部分。

## 7.1 为什么不能一个 Thread 对应一个 C 元素？

原文设置：

```cpp
BM = 128;
BN = 128;
BK = 8;
BLOCK_SIZE = 256;
```

一个 Block 需要计算：

$$
128\times128=16384
$$

个 C 元素。

但只有 256 个 Thread。

所以平均每个 Thread 负责：

$$
\frac{16384}{256}=64
$$

个输出元素。

也就是每个 Thread 需要维护 64 个 accumulator。

可以表示为：

```cpp
float Ct[8][8] = {};
```

这里的 Ct 是每个 Thread 私有的数据。

如果编译器能够将这些数组元素保存在 Register 中，那么它们就是 64 个独立的浮点累加器。

注意：

> 原文的 Block Tiling 阶段实际上已经包含了每线程计算多个输出元素的思想。

后面的 Thread Tiling 则会进一步显式提取 A、B 的寄存器片段，增强 Register 数据复用。

---

## 7.2 同一个 Thread 在 GEMM 中可以有多套坐标

这是理解 GEMM 索引最关键的思想之一。

在 Matrix Transpose 中，你使用：

```cpp
int i = threadIdx.x;
int j = threadIdx.y;
```

让同一个 Thread 完成 Global Memory Load、Shared Memory Store 和最终输出。

但是 GEMM 中：

```text
A Tile 的形状：128×8

B Tile 的形状：8×128

C Tile 的形状：128×128
```

三个矩阵的形状都不同。

如果始终使用同一套线程坐标，会很难得到良好的访存模式。

所以我们先定义一维线程编号：

```cpp
int tid = threadIdx.x;
```

然后针对不同任务，重新解释这个 tid：

```text
加载 A 时：

把 256 个 Thread 看作 32×8。


加载 B 时：

把 256 个 Thread 看作 8×32。


计算 C 时：

把 256 个 Thread 看作 16×16。
```

这些并不是三种不同的实际 CUDA Block。

始终只有：

```cpp
blockDim.x = 256;
```

只是我们在代码里使用不同的映射关系。

---

## 7.3 加载 A Tile

A Tile 的形状：

```text
128 行 × 8 列
```

共有：

$$
128\times8=1024
$$

个 float。

256 个 Thread，每个负责 4 个元素。

将 tid 解释为：

```cpp
int a_col = tid % 8;

int a_row = tid / 8;
```

所以：

```text
tid 0~7：

负责第 0 行的 8 列。


tid 8~15：

负责第 1 行的 8 列。


tid 16~23：

负责第 2 行的 8 列。
```

256 个 Thread 一轮覆盖：

```text
32 行 × 8 列
```

而 A Tile 一共有 128 行。

因此沿行方向循环 4 次。

```cpp
for (int i = a_row; i < BM; i += 32) {

    int row = blockIdx.y * BM + i;

    int col = bk + a_col;

    As[i][a_col] =
        (row < M && col < K)
        ? A[row * K + col]
        : 0.0f;
}
```

例如 tid=10：

```text
a_row = 10 / 8 = 1

a_col = 10 % 8 = 2
```

它负责：

```text
As[1][2]

As[33][2]

As[65][2]

As[97][2]
```

你应该发现，这和之前 Matrix Transpose 中一个 Thread 通过 offset 处理多个元素的思想是一样的。

---

## 7.4 加载 B Tile

B Tile 的形状：

```text
8 行 × 128 列
```

同样 1024 个 float。

将 256 个 Thread 解释为：

```text
8 行 × 32 列
```

```cpp
int b_col = tid % 32;

int b_row = tid / 32;
```

这样一个 Warp 恰好负责 B 的一行中的 32 个连续元素。

每个 Thread 沿 N 方向循环：

```cpp
for (int j = b_col; j < BN; j += 32) {

    int row = bk + b_row;

    int col = blockIdx.x * BN + j;

    Bs[b_row][j] =
        (row < K && col < N)
        ? B[row * N + col]
        : 0.0f;
}
```

例如 tid=35：

```text
b_row = 1

b_col = 3
```

负责：

```text
Bs[1][3]

Bs[1][35]

Bs[1][67]

Bs[1][99]
```

同一个 Warp 的相邻线程访问连续地址。

---

## 7.5 为什么 A 和 B 的线程排布不同？

因为：

```text
A 的连续维度长度只有 BK=8。

B 的连续维度长度为 BN=128。
```

我们希望优先沿内存连续的维度分配相邻 Thread。

所以 A：

```text
一个 Warp 覆盖 4 行，每行 8 个连续 float。
```

B：

```text
一个 Warp 覆盖 1 行中的 32 个连续 float。
```

在对齐良好的情况下，这两种访问都可以具有良好的合并访问效率。

不要机械地认为：

```text
必须让一个 Warp 的 32 个地址构成单一连续区间，才算高效。
```

对于现代 GPU，以 32B Sector 进行分析时，4 段各自对齐的 8 个 float，同样可能很好地利用内存请求。

---

## 7.6 原文 C Tile 的跨步线程映射

原文将 256 个 Thread 看作：

```text
16 行 × 16 列
```

```cpp
int cy = tid / 16;

int cx = tid % 16;
```

整个 C Tile 为 128×128。

每个 Thread 负责：

```cpp
float Ct[8][8] = {};
```

但是请注意：

原文这里的 8×8，不是 C 中连续的 8×8。

而是：

```cpp
int row = cy + i * 16;

int col = cx + j * 16;
```

比如 tid=0：

```text
负责的行：

0, 16, 32, 48, 64, 80, 96, 112


负责的列：

0, 16, 32, 48, 64, 80, 96, 112
```

两两组合，共 64 个输出元素。

可以理解成：

```text
将 128×128 的 C Tile 划分成 64 个 16×16 小块。

Thread 0：

负责每个小块中的第 0 个位置。


Thread 1：

负责每个小块中的第 1 个位置。

...
```

这种布局的优点是：

在固定 i、j 时，相邻 Thread 的输出坐标在相应的小块内连续，便于组织访存。

---

## 7.7 原文这一阶段的核心计算

```cpp
for (int p = 0; p < BK; ++p) {

    for (int i = 0; i < 8; ++i) {

        int row = cy + i * 16;

        for (int j = 0; j < 8; ++j) {

            int col = cx + j * 16;

            Ct[i][j] += As[row][p]
                      * Bs[p][col];
        }
    }
}
```

这个 p 是 Shared Memory Tile 内部的 K 坐标。

需要区分两个循环：

```cpp
for (int bk = 0; bk < K; bk += BK)
```

外层 K-Loop：

```text
负责从 Global Memory 中逐批加载数据。
```

而：

```cpp
for (int p = 0; p < BK; ++p)
```

内层 p-Loop：

```text
负责使用当前 Shared Memory Tile 完成局部乘加。
```

所以：

```text
K-Loop：

决定加载哪个 A/B Tile。


p-Loop：

决定当前 Tile 中使用哪一列 A、哪一行 B。
```

---

# 八、Thread Tiling：Register 级别的数据复用

这是整篇 GEMM 教程中最值得你花时间理解的部分。

## 8.1 为什么用了 Shared Memory 之后还需要优化？

假设每个 Thread 负责 8×8 的输出。

一种直接写法：

```cpp
for (int p = 0; p < BK; ++p) {

    for (int i = 0; i < 8; ++i) {

        for (int j = 0; j < 8; ++j) {

            Ct[i][j] += As[row(i)][p]
                      * Bs[p][col(j)];
        }
    }
}
```

观察：

```cpp
As[row(i)][p]
```

固定 p、i 的时候，j 怎么变化都不影响它。

因此它可以被重复使用 8 次。

同样：

```cpp
Bs[p][col(j)]
```

固定 p、j 的时候，i 怎么变化都不影响它。

它也可以被重复使用 8 次。

所以我们可以主动把这些值先加载到 Register。

```cpp
float a_frag[8];

float b_frag[8];
```

然后：

```cpp
for (int i = 0; i < 8; ++i) {
    a_frag[i] = As[row(i)][p];
}

for (int j = 0; j < 8; ++j) {
    b_frag[j] = Bs[p][col(j)];
}

for (int i = 0; i < 8; ++i) {

    for (int j = 0; j < 8; ++j) {

        Ct[i][j] += a_frag[i] * b_frag[j];
    }
}
```

这样每轮 p：

```text
加载 8 个 A。

加载 8 个 B。

计算 64 次 FMA。
```

这就是 Register Tiling。

编译器有时也能自动从直接写法中消除重复加载，但显式组织 Register Fragment，可以使预期的数据复用关系更清晰。

---

## 8.2 为什么这种方法叫 Outer Product？

先理解内积。

假设：

```text
a = [1, 2, 3]

b = [4, 5, 6]
```

内积：

$$
a^Tb=1\times4+2\times5+3\times6
$$

得到一个标量：

$$
32
$$

而外积：

假设一个列向量：

$$
a=
\begin{bmatrix}
1\\
2
\end{bmatrix}
$$

一个行向量：

$$
b=
\begin{bmatrix}
3&4&5
\end{bmatrix}
$$

那么：

$$
ab=
\begin{bmatrix}
3&4&5\\
6&8&10
\end{bmatrix}
$$

代码：

```cpp
for (int i = 0; i < 2; ++i) {

    for (int j = 0; j < 3; ++j) {

        C[i][j] += a[i] * b[j];
    }
}
```

这就是外积计算。

外积的核心是：

```text
读取少量 A 和 B。

产生大量 C 元素的更新。
```

---

## 8.3 矩阵乘法本质上也可以看成一系列外积

原来我们把矩阵乘法理解成：

```text
A 的一行

乘以

B 的一列

得到一个 C 元素。
```

但也可以换一种视角。

固定 k：

$$
C_{ij}^{(k)}=A_{ik}B_{kj}
$$

这意味着：

```text
取 A 的第 k 列。

取 B 的第 k 行。

做一个外积。
```

得到一整个 C 矩阵的局部贡献。

最后：

$$
C=\sum_{k=0}^{K-1}A_{:,k}B_{k,:}
$$

图示：

```text
A 的第 k 列        B 的第 k 行

┌───┐
│a0 │
│a1 │       ×     [b0 b1 b2 b3]
│a2 │
└───┘

                ↓

       ┌───────────────────┐
       │a0b0 a0b1 a0b2 a0b3│
       │a1b0 a1b1 a1b2 a1b3│
       │a2b0 a2b1 a2b2 a2b3│
       └───────────────────┘
```

每个 Thread 负责的 8×8 Register Tile，就是这个思想的局部版本。

它不需要真的构造完整的外积矩阵。

而是：

```cpp
c_frag[i][j] += a_frag[i] * b_frag[j];
```

直接把结果累加到已有 accumulator 中。

---

## 8.4 Thread Tiling 的算术强度

定义：

```text
TM：每个 Thread 负责多少行 C。

TN：每个 Thread 负责多少列 C。
```

每个 p：

从 Shared Memory 加载：

$$
TM+TN
$$

个 float。

数据量：

$$
4(TM+TN)
$$

计算：

$$
TM\times TN
$$

次 FMA。

因此：

$$
AI_{\mathrm{shared}}=
\frac{2TM\times TN}{4(TM+TN)}
$$

化简：

$$
AI_{\mathrm{shared}}=
\frac{TM\times TN}{2(TM+TN)}
$$

如果：

```text
TM = 8

TN = 8
```

那么：

$$
AI_{\mathrm{shared}}=\frac{64}{32}=2
$$

也就是每个线程逻辑上从 Shared Memory 读取 1 Byte，可以完成 2 FLOPs。

注意这里算的是 Shared Memory 到 Register 的算术强度。

与前面 Block Tiling 的：

$$
AI_{\mathrm{global}}=32
$$

不是同一个存储层级，不能直接比较哪个更好。

---

## 8.5 两级 Tiling 的本质区别

Block Tiling：

```text
Global Memory
       ↓
Shared Memory
       ↓
多个 Thread 复用
```

Thread Tiling：

```text
Shared Memory
       ↓
Register
       ↓
同一个 Thread 的多个 FFMA 复用
```

所以 GEMM 实际上在解决两次带宽问题。

第一次：

> 如何减少 Global Memory 到 Shared Memory 的重复加载？

第二次：

> 如何减少 Shared Memory 到 Register 的重复加载？

这就是 GPU 存储层次与 GEMM 算法结构的对应关系。

---

## 8.6 为什么 Thread Tiling 同时能够提高 ILP？

假设一个 Thread 只计算一个 C 元素：

```cpp
sum += a0 * b0;
sum += a1 * b1;
sum += a2 * b2;
```

存在一条累加依赖链：

```text
sum0 → sum1 → sum2 → sum3
```

后一次 FMA 依赖前一次 FMA 的结果。

但是如果一个 Thread 维护 64 个 accumulator：

```cpp
Ct[0][0] += a0 * b0;

Ct[0][1] += a0 * b1;

Ct[0][2] += a0 * b2;

Ct[0][3] += a0 * b3;
```

这四条指令更新不同的 accumulator。

相互之间不存在必须等待前一条结果的依赖。

于是有更多指令级并行机会。

这就是你之前 Reduce V7 中使用多个独立 accumulator 的思想。

不过在 GEMM 中，独立 accumulator 数量天然就很多。

因此高性能 GEMM 即使 Occupancy 不高，也可能依靠 ILP 保持很高的计算吞吐量。

---

# 九、完整实现：Shared Memory + Register Tiling

下面给你一个可以作为后续优化基础的完整教学版本。

为了让代码更加容易推导，这里选择每个 Thread 负责连续的 TM×TN 输出区域，而不是原文第 4 节中的跨步分布。

这种映射与原文第 5 节的 Thread Tiling 思路一致。

## 9.1 参数定义

```cpp
BM = 128;

BN = 128;

BK = 8;

TM = 8;

TN = 8;
```

每个 Thread 负责 8×8 个输出元素。

所以线程数：

$$
T=\frac{BM}{TM}\times\frac{BN}{TN}
$$

代入：

$$
T=16\times16=256
$$

可以把 256 个 Thread 看作：

```text
16×16 个计算区域。
```

每个区域为 8×8。

---

## 9.2 怎么确定每个 Thread 的计算区域？

```cpp
constexpr int THREAD_COLS = BN / TN;

int thread_row = (tid / THREAD_COLS) * TM;

int thread_col = (tid % THREAD_COLS) * TN;
```

例如：

```text
tid = 0
```

负责：

```text
C[0:8][0:8]
```

tid=1：

```text
C[0:8][8:16]
```

tid=2：

```text
C[0:8][16:24]
```

tid=16：

```text
C[8:16][0:8]
```

画成：

```text
C Tile：

┌────────┬────────┬────────┐
│Thread 0│Thread 1│Thread 2│ ...
├────────┼────────┼────────┤
│Thread16│Thread17│Thread18│ ...
├────────┼────────┼────────┤
│Thread32│Thread33│Thread34│ ...
└────────┴────────┴────────┘
```

每个小方块代表一个 Thread 的 8×8 Register Tile。

和前面跨步版本不同，这里每个 Thread 的输出区域是连续的。

---

## 9.3 完整 Kernel

这里协作加载 A、B 时采用一个通用的一维 Grid-stride 风格循环。

不过循环范围是 Block 内的 Tile，所以更准确地说是 Block-stride Loop。

```cpp
template<
    int BM,
    int BN,
    int BK,
    int TM,
    int TN
>
__global__ void gemm_register_tiling(
    const float* A,
    const float* B,
    float* C,
    int M,
    int N,
    int K
) {
    static_assert(BM % TM == 0);
    static_assert(BN % TN == 0);

    constexpr int THREAD_COLS = BN / TN;

    constexpr int BLOCK_SIZE =
        (BM / TM) * (BN / TN);

    static_assert(BLOCK_SIZE <= 1024);
    static_assert(BLOCK_SIZE % 32 == 0);

    __shared__ float As[BM][BK];
    __shared__ float Bs[BK][BN];

    int tid = threadIdx.x;

    // 当前 Block 在整个 C 中的起始坐标
    int block_row = blockIdx.y * BM;

    int block_col = blockIdx.x * BN;

    // 当前 Thread 在 C Tile 中的起始坐标
    int thread_row =
        (tid / THREAD_COLS) * TM;

    int thread_col =
        (tid % THREAD_COLS) * TN;

    // 每个 Thread 私有的 accumulator
    float c_frag[TM][TN] = {};

    float a_frag[TM];
    float b_frag[TN];

    // 外层 K-Loop
    for (int bk = 0; bk < K; bk += BK) {

        // 1. 协作加载 A Tile
        for (int idx = tid;
             idx < BM * BK;
             idx += BLOCK_SIZE) {

            int r = idx / BK;
            int c = idx % BK;

            int gr = block_row + r;
            int gc = bk + c;

            As[r][c] =
                (gr < M && gc < K)
                ? A[gr * K + gc]
                : 0.0f;
        }

        // 2. 协作加载 B Tile
        for (int idx = tid;
             idx < BK * BN;
             idx += BLOCK_SIZE) {

            int r = idx / BN;
            int c = idx % BN;

            int gr = bk + r;
            int gc = block_col + c;

            Bs[r][c] =
                (gr < K && gc < N)
                ? B[gr * N + gc]
                : 0.0f;
        }

        __syncthreads();

        // 3. 当前 Tile 内的 p-Loop
        #pragma unroll
        for (int p = 0; p < BK; ++p) {

            // Shared Memory -> Register
            #pragma unroll
            for (int i = 0; i < TM; ++i) {

                a_frag[i] =
                    As[thread_row + i][p];
            }

            #pragma unroll
            for (int j = 0; j < TN; ++j) {

                b_frag[j] =
                    Bs[p][thread_col + j];
            }

            // Register 中的 Outer Product
            #pragma unroll
            for (int i = 0; i < TM; ++i) {

                #pragma unroll
                for (int j = 0; j < TN; ++j) {

                    c_frag[i][j] +=
                        a_frag[i] * b_frag[j];
                }
            }
        }

        // 确保没有线程仍然使用当前 Shared Tile
        __syncthreads();
    }

    // 4. 将 Register 中的结果写回 Global
    for (int i = 0; i < TM; ++i) {

        int row = block_row + thread_row + i;

        for (int j = 0; j < TN; ++j) {

            int col = block_col + thread_col + j;

            if (row < M && col < N) {

                C[row * N + col] = c_frag[i][j];
            }
        }
    }
}
```

启动：

```cpp
constexpr int BM = 128;
constexpr int BN = 128;
constexpr int BK = 8;

constexpr int TM = 8;
constexpr int TN = 8;

constexpr int block_size =
    (BM / TM) * (BN / TN);

dim3 grid(
    (N + BN - 1) / BN,
    (M + BM - 1) / BM
);

gemm_register_tiling<BM, BN, BK, TM, TN>
<<<grid, block_size>>>(
    d_A, d_B, d_C, M, N, K
);
```

注意：

Grid 的计算依据已经不是一个 Block 有多少 Thread。

而是：

```text
一个 Block 负责多大的输出 Tile。
```

和你的 Matrix Transpose 一样。

---

## 9.4 这个 Kernel 最值得注意的地方

```cpp
float c_frag[TM][TN] = {};
```

它必须在外层 K-Loop 外面初始化。

因为：

```text
第一轮 K-Tile 的结果

+

第二轮 K-Tile 的结果

+

第三轮 K-Tile 的结果

...

=

完整 C Tile
```

如果把 c_frag 放进 K-Loop 并每次初始化为 0：

之前累加的结果就会丢失。

而：

```cpp
float a_frag[TM];
float b_frag[TN];
```

每轮 p 都会覆盖。

因为 A、B 的局部数据只服务当前外积计算。

数据生命周期：

```text
As、Bs：

每轮 K-Loop 更新。


a_frag、b_frag：

每轮 p-Loop 更新。


c_frag：

整个 Kernel 计算过程中持续累加。

最后只写回一次。
```

这张逻辑关系一定要理解。

---

# 十、Register Tiling 和 Occupancy 的 Trade-off

## 10.1 寄存器到底需要多少？

假设：

```cpp
TM = 8;
TN = 8;
```

那么主要的 FP32 数据：

```cpp
float c_frag[8][8];

float a_frag[8];

float b_frag[8];
```

理论上的标量数量：

$$
64+8+8=80
$$

此外还有：

```text
全局索引

局部索引

地址

循环变量

临时加载值
```

所以实际 Register 使用量可能更高。

原文使用约 110～128 Registers/Thread 作为资源预算示例。

但这个数字不是固定的，最终应该看 nvcc 实际分配结果。

---

## 10.2 为什么不能无限扩大 TM 和 TN？

假设：

```text
TM=4，TN=4
```

accumulator 数量：

$$
16
$$

如果：

```text
TM=8，TN=8
```

accumulator 数量：

$$
64
$$

如果：

```text
TM=16，TN=16
```

accumulator 数量：

$$
256
$$

仅 accumulator 就已经非常大了，还没有考虑 A、B Fragment 和临时变量。

结果可能出现：

```text
Register Pressure 增大

        ↓

Occupancy 下降

        ↓

严重时出现 Register Spill

        ↓

数据被放入 Local Memory

        ↓

性能下降
```

所以：

> Register Tiling 不是越大越好。

它是用更多 Register 换取更高的数据复用率和 ILP。

---

## 10.3 在你的 RTX 4060 Laptop 上怎么理解？

你的显卡属于 Ada 架构，Compute Capability 8.9。

按照 NVIDIA Ada 架构的资源规格：

```text
每 SM 最大驻留 Warp 数：48

每 SM 最大驻留 Thread 数：1536

每 SM Register 数量：65536 个 32-bit Register
```

假设：

```text
Block Size = 256

Registers Per Thread = 128
```

那么一个 Block 需要：

$$
128\times256=32768
$$

个 Register。

理论上，一个 SM 最多驻留两个这样的 Block：

$$
\frac{65536}{32768}=2
$$

每个 Block：

$$
256/32=8
$$

个 Warp。

所以两个 Block 有 16 个 Warp。

对应 Occupancy：

$$
\frac{16}{48}\approx33.33\%
$$

这里只考虑寄存器限制，并假设其他资源足够。

注意原文使用的是 V100 的资源模型，因此它给出的对应 Occupancy 是 25%。

你的 GPU 最大 Warp 数不同，不能直接照抄。

---

## 10.4 怎么看真实 Register 使用量？

编译：

```bash
nvcc -O3 -arch=sm_89 -Xptxas=-v gemm.cu -o gemm
```

可以看到类似：

```text
Used 96 registers
```

或者：

```text
Used 120 registers
```

这些才是编译器实际给出的寄存器使用量。

还要关注：

```text
spill stores

spill loads

stack frame
```

如果 Spill 非常严重，说明当前 Register Tiling 或代码组织可能存在问题。

需要注意：局部数组并不保证一定放在 Register 中，能否进行寄存器化取决于编译器优化、索引方式和资源压力。

# 十一、Warp Tiling：重新组织 Warp 内的线程位置

## 11.1 为什么已经有 Block Tiling 和 Thread Tiling，还要 Warp Tiling？

现在已经有：

```text
整个 C

    ↓

128×128 的 Block Tile

    ↓

每 Thread 负责 8×8
```

但是你还没有明确控制：

> 同一个 Warp 的 32 个 Thread，在 C Tile 中分别负责哪些区域？

而 Shared Memory Bank Conflict 和 Broadcast，都需要站在 Warp 的视角分析。

所以我们需要在 Block 和 Thread 之间，再加入一层逻辑分块。

```text
Block Tile

    ↓

Warp Tile

    ↓

Thread Tile
```

注意：

Warp Tiling 是逻辑上的计算区域划分。

不会创建新的 CUDA 硬件 Warp。

硬件 Warp 仍然是由 32 个连续线程组成。

---

## 11.2 一个 Warp 的 32 个 Thread 可以怎么排布？

例如：

```text
1×32

2×16

4×8

8×4

16×2

32×1
```

假设每个 Thread 负责：

```text
TM=8

TN=8
```

如果 Warp 采用 4×8 排布：

```text
4 行 Thread

8 列 Thread
```

那么整个 Warp 负责的 C 区域为：

$$
WM=4\times8=32
$$

$$
WN=8\times8=64
$$

因此：

```text
Warp Tile：32×64

Thread Tile：8×8
```

Block Tile 为 128×128。

那么需要：

$$
\frac{128}{32}\times\frac{128}{64}=4\times2=8
$$

个 Warp。

8 个 Warp 正好对应 256 个 Thread。

---

## 11.3 为什么 4×8 比 1×32 更值得尝试？

固定一个 p。

假设 Warp 中逻辑上有 x 行、y 列 Thread，满足：

$$
xy=32
$$

一个 Thread 需要 TM 个 A 和 TN 个 B。

同一逻辑 Thread Row 上的 y 个 Thread，可以共享相同的 A Fragment。

同一逻辑 Thread Col 上的 x 个 Thread，可以共享相同的 B Fragment。

所以 Warp 所需的独立 A、B 元素数量为：

$$
xTM+yTN
$$

而计算量：

$$
2xyTM TN
$$

当 TM=TN 时，希望 x+y 尽可能小。

例如：

| Warp Shape | x+y |
|---|---:|
| 1×32 | 33 |
| 2×16 | 18 |
| 4×8 | 12 |
| 8×4 | 12 |
| 16×2 | 18 |
| 32×1 | 33 |

所以在这个理想复用模型下，4×8 和 8×4 有优势。

但是实际还需要结合：

```text
Shared Memory Bank Mapping

Broadcast

Vectorized Load

Global Memory Store

矩阵的形状
```

并不是所有情况下 4×8 都最优。

---

## 11.4 Warp Tiling 的索引怎么写？

沿用：

```cpp
BM = 128;
BN = 128;

TM = 8;
TN = 8;
```

首先计算 warpId 和 laneId。

```cpp
int warp_id = tid / 32;

int lane_id = tid % 32;
```

8 个 Warp 在 Block 中按 4×2 排列：

```cpp
int warp_row = warp_id / 2;

int warp_col = warp_id % 2;
```

每个 Warp 内部 32 个 Thread 按 4×8 排列：

```cpp
int lane_row = lane_id / 8;

int lane_col = lane_id % 8;
```

每个 Warp 负责 32×64：

```cpp
int thread_row =
    warp_row * 32 + lane_row * 8;

int thread_col =
    warp_col * 64 + lane_col * 8;
```

这就是当前 Thread 在 C Block Tile 中的计算区域起点。

例如：

```text
tid = 45
```

那么：

```text
warp_id = 45 / 32 = 1

lane_id = 45 % 32 = 13
```

Warp 1：

```text
warp_row = 0

warp_col = 1
```

Lane 13：

```text
lane_row = 1

lane_col = 5
```

因此：

```text
thread_row = 0*32 + 1*8 = 8

thread_col = 1*64 + 5*8 = 104
```

它负责 C Tile 中：

```text
行 8~15

列 104~111
```

---

## 11.5 怎么把 Warp Tiling 加入之前的 Kernel？

在前面完整的 Register Tiling Kernel 中，你只需要将：

```cpp
int thread_row =
    (tid / THREAD_COLS) * TM;

int thread_col =
    (tid % THREAD_COLS) * TN;
```

替换为上述 Warp-level Mapping。

其余：

```text
A/B 协作加载

Register Fragment 加载

Outer Product

C 写回
```

整体计算逻辑可以保持不变。

前提是使用前述匹配的 Tile 参数。

所以 Warp Tiling 的核心不是改变矩阵乘法本身。

而是改变：

```text
Warp 内 Thread

        ↓

C 计算区域

        ↓

Shared Memory 访问模式
```

---

# 十二、Vectorized Load：float4 优化

## 12.1 你在 Reduce 中已经学过这个优化

之前 V7：

```cpp
const float4* input4 =
    reinterpret_cast<const float4*>(input);
```

目的：

```text
减少 Global Memory Load 指令数量。
```

GEMM 中则有两个可以考虑向量化的地方：

```text
Global Memory -> Shared Memory

Shared Memory -> Register
```

另外还可以考虑：

```text
Register -> Global Memory
```

也就是 C 的向量化写回。

---

## 12.2 Global Memory 到 Shared Memory 的向量化

假设：

```text
A Tile = 128×8

B Tile = 8×128
```

每个 Tile 都有 1024 个 float。

每个 Block 有 256 个 Thread。

刚好：

$$
1024/256=4
$$

所以每个 Thread 可以加载一个 float4。

对于 A：

```cpp
int a_row = tid / (BK / 4);

int a_col = (tid % (BK / 4)) * 4;
```

代入 BK=8：

```cpp
int a_row = tid / 2;

int a_col = (tid % 2) * 4;
```

也就是：

```text
Thread 0：

A Tile 第 0 行，列 0~3。


Thread 1：

A Tile 第 0 行，列 4~7。


Thread 2：

A Tile 第 1 行，列 0~3。
```

对于 B：

```cpp
int b_row = tid / (BN / 4);

int b_col = (tid % (BN / 4)) * 4;
```

代入 BN=128：

```cpp
int b_row = tid / 32;

int b_col = (tid % 32) * 4;
```

一个 Warp 正好负责 B Tile 的一整行。

---

## 12.3 float4 如何读取？

```cpp
const float* ptr =
    A + global_row * K + global_col;

float4 av =
    *reinterpret_cast<const float4*>(ptr);
```

得到：

```cpp
av.x
av.y
av.z
av.w
```

对应原来的连续 4 个 float。

这里必须保证：

```text
地址满足 16B 对齐。

4 个元素都处于合法范围内。
```

对于矩阵：

仅仅 cudaMalloc 返回的基地址对齐还不够。

每一行的起始地址也需要考虑。

例如：

```text
K 是 4 的倍数。

bk 是 4 的倍数。

a_col 是 4 的倍数。
```

在这种情况下，A 的向量化行内访问比较容易保证对齐。

如果 K、N 不是 4 的倍数，或者矩阵边界不足 4 个元素，需要标量回退或其他正确的边界处理。

建议第一次实现 float4 GEMM 时先限制测试矩阵尺寸为 Tile Size 的整数倍，再单独补充一般尺寸的处理逻辑。

---

# 十三、为什么要把 A 转置存入 Shared Memory？

这是你之前学习 Matrix Transpose 的知识第一次在 GEMM 中大量使用。

## 13.1 观察 Register Fragment 的加载

之前：

```cpp
__shared__ float As[BM][BK];

__shared__ float Bs[BK][BN];
```

加载 A Fragment：

```cpp
for (int i = 0; i < TM; ++i) {

    a_frag[i] = As[thread_row + i][p];
}
```

注意：

```text
p 固定。

i 不断变化。
```

所以我们是在沿 As 的行方向移动。

对于 Row-major 二维数组：

```cpp
As[row][col]
```

内存连续的是 col。

因此：

```cpp
As[thread_row + i][p]
```

是跨步访问。

相邻 i 的内存地址相差：

$$
BK
$$

个 float。

这意味着单个 Thread 无法直接使用 float4 读取连续的 4 个 A Fragment 元素。

---

## 13.2 B 不存在这个问题

B Fragment：

```cpp
b_frag[j] = Bs[p][thread_col + j];
```

固定 p，j 连续变化。

读取的是同一行的连续元素。

可以比较自然地使用 float4。

---

## 13.3 所以把 A 在 Shared Memory 中转置

原来：

```cpp
__shared__ float As[BM][BK];
```

改成：

```cpp
__shared__ __align__(16) float As[BK][BM];
```

写入时：

```cpp
As[c][r] = A[global_row * K + global_col];
```

原来的 A[r][c] 对应：

```text
As[c][r]
```

这时候：

```cpp
a_frag[i] = As[p][thread_row + i];
```

就是连续访问。

所以可以进行：

```cpp
float4 av =
    *reinterpret_cast<const float4*>(
        &As[p][thread_row]
    );
```

一次读取 4 个连续 A Fragment 元素。

前提仍然是地址对齐。

---

## 13.4 Global Memory 仍然可以按行向量化加载

可能你会疑惑：

> A 转置以后，Global Memory 加载不就变成跨步访问了吗？

不会。

因为：

```text
Global Memory 中的 A 没有被转置。

只是存入 Shared Memory 时改变了布局。
```

例如：

```cpp
float4 av =
    *reinterpret_cast<const float4*>(
        &A[global_row * K + global_col]
    );
```

从 Global Memory 中读取连续 4 个 float。

然后分别写入：

```cpp
As[a_col + 0][a_row] = av.x;

As[a_col + 1][a_row] = av.y;

As[a_col + 2][a_row] = av.z;

As[a_col + 3][a_row] = av.w;
```

这几个 Shared Memory Store 的地址不一定连续，因此不代表整个 Global-to-Shared 路径都自动完成了 128-bit 向量化 Store。

但是我们成功让后面大量重复执行的 Shared-to-Register Load，更容易使用 float4。

也就是：

```text
Global Memory：

保持连续读取。


Shared Memory：

重新组织存储布局。


Register：

连续读取需要的 Fragment。
```

和你之前的矩阵转置优化一模一样：

> Shared Memory 不只是 Cache，还可以作为数据布局转换的中转站。

---

# 十四、GEMM 中的 Bank Conflict

这部分比你之前学的 Matrix Transpose 稍微复杂。

因为现在每个 Thread 一次可能读取多个 float。

而且同一个 Warp 中还存在大量 Broadcast。

---

## 14.1 先分析普通标量读取

对于：

```cpp
__shared__ float As[128][8];
```

Shared Memory 的 Bank 近似为：

$$
bank(r,c)=(8r+c)\bmod32
$$

如果两个 Thread 分别读取：

```cpp
As[0][p]

As[8][p]
```

对应的线性地址差：

$$
8\times8=64
$$

64 是 32 的倍数。

因此会映射到相同 Bank。

而它们是不同地址。

如果在同一个 Shared Memory 请求中发生，就会产生 Bank Conflict。

如果多个线程都读取：

```cpp
As[0][p]
```

则属于同地址读取，可以 Broadcast。

这个你之前已经完全掌握了。

---

## 14.2 float4 为什么不能直接按照 32 个 Lane 一起分析？

标量 float：

```text
每个 Lane：4B

32 个 Lane：128B
```

float4：

```text
每个 Lane：16B

32 个 Lane：512B
```

所以一个 Warp 的宽向量 Shared Memory 请求，通常需要拆分成多个较小的硬件处理单元。

对于规则的 128-bit 每线程访问，可以先按照每 8 个 Lane 一组来理解。

```text
Warp：

Lane 0~7

Lane 8~15

Lane 16~23

Lane 24~31
```

每组：

$$
8\times16=128\ \mathrm{Bytes}
$$

这种 8-lane 分组也叫 Quarter Warp。

分析 Bank Conflict 时，需要针对具体硬件拆分后的请求，而不是把 512B 的请求全部当成一次 128B 的标量访问。

注意：

真实硬件还可能对重复地址、uniform access 和 Broadcast 进行额外优化。

原文进一步讨论了跨 Quarter Warp 的请求合并。这些具体 transaction 数依赖 GPU 架构和实际指令，不能直接当作所有 NVIDIA GPU 都成立的通用规律。

你目前先掌握 Quarter Warp 内的地址分析就足够了。

---

## 14.3 为什么连续 8×8 Thread Tile 可能产生冲突？

假设 Warp 采用：

```text
4×8 Thread 排布。
```

每个 Thread 负责连续 8×8。

那么前 8 个 Lane 在 N 方向上的起始位置为：

```text
Lane 0 → col 0

Lane 1 → col 8

Lane 2 → col 16

Lane 3 → col 24

Lane 4 → col 32

Lane 5 → col 40

Lane 6 → col 48

Lane 7 → col 56
```

假设读取 B Fragment 的前四个 float：

| Lane | 读取位置 | Bank |
|---|---|---|
| 0 | 0~3 | 0~3 |
| 1 | 8~11 | 8~11 |
| 2 | 16~19 | 16~19 |
| 3 | 24~27 | 24~27 |
| 4 | 32~35 | 0~3 |
| 5 | 40~43 | 8~11 |
| 6 | 48~51 | 16~19 |
| 7 | 56~59 | 24~27 |

于是：

```text
Lane 0 和 Lane 4：

访问相同 Bank 的不同地址。


Lane 1 和 Lane 5：

访问相同 Bank 的不同地址。
```

在对应的 Quarter Warp 模型中就会产生 2-way Bank Conflict。

注意：

这次不是之前 Transpose 中的 stride=32。

而是：

```text
每个 Lane 读取 float4。

相邻 Lane 的起始地址间隔 8 个 float。
```

所以虽然使用了向量化，仍然可能存在 Bank Conflict。

# 十五、怎么解决 GEMM 中的 Bank Conflict？

## 15.1 方法一：Padding

你最熟悉的办法。

```cpp
__shared__ float As[BK][BM + 4];
```

改变每行的内存跨度。

但是要注意，原文提到 +4 Padding 可能破坏 float4 对齐，这里需要具体区分。

如果 BM 本身是 4 的倍数，那么 BM+4 仍然是 4 的倍数。

因此在基地址也正确对齐的条件下，行跨度仍然可以保持 16B 对齐。

而：

```cpp
__shared__ float As[BK][BM + 1];
```

才会比较明显地让后续行的起始地址失去 16B 对齐。

另外 Padding 是否有效，要看冲突由什么产生。

如果冲突发生在同一行内两个相距 32 个 float 的访问，单纯改变行跨度并不能改变它们之间的地址差。

所以不能看到 Bank Conflict 就直接加 Padding。

要先分析具体地址。

---

## 15.2 方法二：Swizzle

Swizzle：

通过重新映射 Shared Memory 地址，改变数据在 Bank 中的分布。

例如：

```cpp
As[k][row ^ (k * 4)] = value;
```

读取时使用同样的映射：

```cpp
float val =
    As[k][target_row ^ (k * 4)];
```

这里的逻辑是：

```text
数学上的坐标不变。

物理存储坐标发生变化。
```

XOR 中很重要的性质：

$$
(a\oplus b)\oplus b=a
$$

因此可以设计可逆的地址映射。

如果以 4 个 float 为一个整体进行 Swizzle，就可以尽量保留向量化访问需要的连续性与对齐。

不过这个具体 Swizzle 需要结合 Tile 大小和访问模式验证，不能保证消除所有冲突。

例如同一 p 上访问位置始终相差 32 的情况，就不一定能通过仅依赖 p 的 XOR 解决。

现在先理解 Swizzle 是什么，不需要马上手写复杂版本。

---

## 15.3 方法三：将一个 8×8 Thread Tile 拆成四个 4×4

这是原文中比较有意思的方案。

原来：

```text
Thread 0 → 连续的 8×8

Thread 1 → 相邻的连续 8×8
```

现在：

```text
每个 Thread 仍然负责 64 个元素。

但不再全部集中在连续 8×8 区域。

而是拆成四个分散的 4×4 区域。
```

以 Warp 的 N 方向为例：

原来的起点：

```text
Lane 0 → 0

Lane 1 → 8

Lane 2 → 16

...

Lane 7 → 56
```

现在改为：

```text
Lane 0 → 0

Lane 1 → 4

Lane 2 → 8

...

Lane 7 → 28
```

读取每个 Lane 的第一组 float4：

| Lane | 读取位置 | Bank |
|---|---|---|
| 0 | 0~3 | 0~3 |
| 1 | 4~7 | 4~7 |
| 2 | 8~11 | 8~11 |
| 3 | 12~15 | 12~15 |
| 4 | 16~19 | 16~19 |
| 5 | 20~23 | 20~23 |
| 6 | 24~27 | 24~27 |
| 7 | 28~31 | 28~31 |

刚好覆盖 32 个 Bank。

没有不同地址之间的 Bank Conflict。

每个 Lane 还需要计算剩下的四列，那么让第二组四列整体移动 32 个位置。

例如 Lane 0：

```text
第一组：

0,1,2,3


第二组：

32,33,34,35
```

Lane 1：

```text
第一组：

4,5,6,7


第二组：

36,37,38,39
```

所以原来每线程连续的 8 列，现在变成两组 4 列。

行方向也可以进行类似拆分。

最终：

```text
8×8

    ↓

4 个 4×4 子块
```

每个 Thread 负责的总元素数量没有变化。

只是改变了这些元素的空间布局。

---

## 15.4 怎么写这个新的坐标公式？

假设当前 Warp 的计算区域为：

```text
WM = 32

WN = 64
```

Warp 内部：

```text
4 行 Thread

8 列 Thread
```

每组连续 4 个元素。

那么：

```cpp
int local_row =
    lane_row * 4
    + (i / 4) * 16
    + i % 4;

int local_col =
    lane_col * 4
    + (j / 4) * 32
    + j % 4;
```

其中：

```text
i = 0~7

j = 0~7
```

例如 lane_row=0：

```text
i=0~3：

0,1,2,3

i=4~7：

16,17,18,19
```

lane_col=0：

```text
j=0~3：

0,1,2,3

j=4~7：

32,33,34,35
```

然后再加上：

```cpp
warp_row * WM

warp_col * WN
```

即可得到 Block Tile 中的坐标。

注意原文第 7 节还给出了以整个 16×16 Thread 网格为基础的分组映射。这里使用的是以 Warp Tile 为范围的对应教学映射，两者不能直接混用坐标常量。

---

## 15.5 方法四：Z-order 线程映射

原文进一步改变了 Warp 内 Lane 的二维位置。

普通行优先：

```cpp
int lane_row = lane_id / 8;

int lane_col = lane_id % 8;
```

前 8 个 Lane：

```text
Lane 0 → (0,0)

Lane 1 → (0,1)

Lane 2 → (0,2)

...

Lane 7 → (0,7)
```

这意味着整个 Quarter Warp 都位于同一行。

Z-order 映射的一种写法：

```cpp
int lane_row =
    lane_id % 2
    + (lane_id / 16) * 2;

int lane_col =
    (lane_id % 16) / 2;
```

前 8 个 Lane：

```text
Lane 0 → (0,0)

Lane 1 → (1,0)

Lane 2 → (0,1)

Lane 3 → (1,1)

Lane 4 → (0,2)

Lane 5 → (1,2)

Lane 6 → (0,3)

Lane 7 → (1,3)
```

画出来：

```text
普通排布：

0  1  2  3  4  5  6  7


Z-order 排布：

0  2  4  6

1  3  5  7
```

这样同一 Quarter Warp 中：

- 一部分 Thread 共享相同 A Fragment。
- 另一部分 Thread 共享相同 B Fragment。

因此可以同时利用两个方向的 Broadcast。

原文还对具体硬件请求数量进行了分析。

你目前不需要记住它推导出的 transaction 数字。

真正应该掌握的是：

> 改变 Warp 中 Lane 的二维位置，就能改变 Shared Memory Bank Conflict 和 Broadcast 的行为。

这和你 Reduce V0 到 V1 时改变 Thread Mapping 的思想，本质上非常相似。

# 十六、Double Buffering：双缓冲与流水线

前面的优化主要在解决：

```text
如何减少数据搬运量。

如何提升数据搬运效率。

如何增加数据复用率。
```

现在要解决另外一个问题：

> 能不能让数据搬运和计算尽可能重叠？

---

## 16.1 单缓冲的执行过程

目前的 GEMM：

```cpp
for (int bk = 0; bk < K; bk += BK) {

    load_global_to_shared();

    __syncthreads();

    compute();

    __syncthreads();
}
```

时间线：

```text
时间 ------------------------------------>

加载 Tile 0

          计算 Tile 0

                    加载 Tile 1

                              计算 Tile 1
```

简化理解：

```text
加载数据的时候，当前 Thread 可能在等待数据。

计算的时候，下一批数据还没有开始加载。
```

如果能够改成：

```text
时间 ------------------------------------>

加载 Tile 0

          计算 Tile 0
          加载 Tile 1

                    计算 Tile 1
                    加载 Tile 2

                              计算 Tile 2
```

那么访存延迟就有机会被当前计算覆盖。

这就是 Pipeline。

---

## 16.2 为什么需要两个 Shared Memory Buffer？

如果我们只有：

```cpp
__shared__ float As[BK][BM];
```

计算 Tile 0 时，它正在被 Thread 使用。

此时如果把 Tile 1 写进去：

```text
旧数据被覆盖。

正在进行的 Tile 0 计算就会出错。
```

所以使用两份空间：

```cpp
__shared__ float As[2][BK][BM];

__shared__ float Bs[2][BK][BN];
```

把它们理解成：

```text
Buffer 0

Buffer 1
```

第一轮：

```text
Buffer 0：

正在参与计算。


Buffer 1：

准备下一批数据。
```

第二轮：

```text
Buffer 1：

正在参与计算。


Buffer 0：

准备下一批数据。
```

不断交换。

```cpp
int read_buf = 0;

int write_buf = 1;
```

交换：

```cpp
read_buf ^= 1;

write_buf ^= 1;
```

这就是 Ping-Pong Buffer。

---

## 16.3 Shared Memory 层的 Double Buffering

逻辑示意：

```cpp
load_first_tile_into_shared();

__syncthreads();

for (int tile = 0; tile < num_tiles; ++tile) {

    int current = tile % 2;

    int next = current ^ 1;

    // 如果存在下一轮，预取下一批数据
    if (tile + 1 < num_tiles) {

        prefetch_next_tile_into_register();
    }

    // 使用当前 Shared Buffer 计算
    compute_using_shared(current);

    // 将预取的数据写入另一份 Shared Buffer
    if (tile + 1 < num_tiles) {

        store_prefetched_data_to_shared(next);
    }

    __syncthreads();
}
```

上面是结构示意，不是一个可以直接编译的完整 Kernel。

普通 Global Memory Load 的实际发射顺序和与计算重叠的程度，取决于编译器、指令依赖和硬件调度。

不能仅仅因为写了两份 Buffer，就认定访存和计算一定完全重叠。

---

## 16.4 为什么双缓冲可以减少 Block Barrier？

单缓冲时：

```text
Barrier 1：

保证本轮数据已经加载完成。


Barrier 2：

保证本轮旧数据已被全部使用，才能覆盖。
```

双缓冲时：

```text
正在读取 Buffer 0。

同时写入 Buffer 1。
```

读写空间不同，因此不需要为了覆盖当前 Buffer，单独等待当前轮结束后才开始准备下一轮。

在适当的流水线组织下，可以让一次 Buffer 切换前的 Barrier 同时满足：

```text
下一份数据已经写完。

上一份数据已经读完。
```

于是主循环中的 Block Barrier 可以减少。

但必须确保：

```text
任何 Buffer 被重新使用之前：

上一次读取已经完成。

下一次读取之前：

新的写入已经完成。
```

---

## 16.5 Register 层也可以 Double Buffering

之前每轮 p：

```cpp
load_a_frag();

load_b_frag();

outer_product();
```

现在想要：

```text
当前 Fragment：

进行 FFMA。


下一份 Fragment：

从 Shared Memory 提前加载。
```

可以准备两组：

```cpp
float a_frag[2][TM];

float b_frag[2][TN];
```

时间线：

```text
加载 Fragment 0

        ↓

计算 Fragment 0
预取 Fragment 1

        ↓

计算 Fragment 1
预取 Fragment 2

        ↓

计算 Fragment 2
```

示意代码：

```cpp
// 预取第一个 Fragment
load_fragment(0, 0);

for (int p = 0; p < BK; ++p) {

    int current = p & 1;

    int next = current ^ 1;

    if (p + 1 < BK) {

        load_fragment(p + 1, next);
    }

    outer_product(
        a_frag[current],
        b_frag[current],
        c_frag
    );
}
```

注意最后一轮不应该读取 p=BK。

这类流水线设计经常分成：

```text
Prologue：

提前加载第一批数据。


Main Loop：

不断重叠加载和计算。


Epilogue：

完成最后一批计算，不再发起无效预取。
```

---

## 16.6 双缓冲的代价是什么？

原来：

```text
A Shared Tile：4 KiB

B Shared Tile：4 KiB

共 8 KiB
```

双缓冲之后：

$$
2\times8=16\ \mathrm{KiB}
$$

Register Fragment 也从：

```text
一组 a_frag

一组 b_frag
```

增加到：

```text
两组 a_frag

两组 b_frag
```

所以会增加：

```text
Shared Memory Usage

Register Usage
```

可能导致：

```text
Occupancy 下降。
```

这又回到你第 2.3 章学过的 Trade-off。

使用更多资源，换取更充分的访存延迟隐藏。

是否值得，需要实测。

---

# 十七、Ampere 异步拷贝：cp.async

这一部分先建立概念即可。

## 17.1 传统 Global-to-Shared Copy

你之前写：

```cpp
As[r][c] = A[global_row * K + global_col];
```

传统实现通常可以理解成：

```text
Global Memory

        ↓ LDG

Thread Register

        ↓ STS

Shared Memory
```

也就是说，数据需要经过寄存器中转。

---

## 17.2 cp.async 有什么不同？

Ampere 开始提供硬件支持的异步 Global-to-Shared Copy。

```text
Global Memory

        ↓ cp.async

Shared Memory
```

它可以避免使用普通寄存器保存整份中转数据，并允许在等待拷贝完成的过程中执行其他独立计算。

需要注意：

cp.async 的异步并不是：

```text
发出指令以后，Shared Memory 立即可以读取。
```

拷贝仍然需要时间。

所以要通过相应的提交、等待和同步操作保证正确性。

---

## 17.3 commit_group 和 wait_group

原文介绍的 PTX 操作：

```cpp
cp.async.commit_group;

cp.async.wait_group N;
```

可以先理解为：

```text
commit_group：

将此前发出的异步拷贝组成一批。


wait_group：

等待到规定数量的异步拷贝组完成。
```

例如：

```cpp
cp.async.wait_group 0;
```

表示等待此前提交的相关异步拷贝组全部完成。

之后如果其他 Thread 还需要访问当前 Thread 写入的数据，还需要正确的 Block 级协作同步。

注意：

这些是 PTX 指令，不是可以直接作为普通 C++ 函数调用的语句。

CUDA C++ 中也可以通过：

```cpp
cuda::memcpy_async

cuda::pipeline
```

等接口组织异步拷贝。

---

## 17.4 你的 RTX 4060 Laptop 能不能使用？

可以。

RTX 4060 Laptop 属于 Ada，Compute Capability 8.9。

它具备 Ampere 之后的相关异步拷贝能力。

但是你现在没必要立刻使用 Inline PTX 实现复杂的 cp.async Pipeline。

建议先完成：

```text
正确的普通 Shared Memory GEMM

        ↓

Register Tiling

        ↓

Warp Tiling

        ↓

向量化和 Bank Conflict 优化

        ↓

Double Buffering

        ↓

cp.async
```

否则会同时面对太多复杂的索引和同步问题。

---

## 17.5 多级流水线

双缓冲：

```text
Stage 0：计算当前 Tile。

Stage 1：准备下一 Tile。
```

三级流水线：

```text
Stage 0：正在计算。

Stage 1：数据已经准备好。

Stage 2：正在异步加载。
```

更多 Stage 有机会隐藏更长的访存延迟。

但是 Shared Memory 需求也会增加。

所以：

```text
Stage 数量

Tile Size

Register Usage

Occupancy
```

需要一起考虑。

原文还提到了 Hopper 的 TMA 和 WGMMA。

这些属于更新架构的高级功能，你的 RTX 4060 Laptop 不具备 Hopper 专属的 TMA 和 WGMMA 指令能力，目前了解概念即可。

# 十八、SASS 级别优化

这一节可以先浅学。

## 18.1 PTX 和 SASS 是什么？

CUDA 编译过程可以粗略理解成：

```text
CUDA C++

        ↓ nvcc

PTX

        ↓ ptxas

SASS / GPU Machine Code
```

PTX：

可以理解成 NVIDIA GPU 的虚拟指令集表示。

SASS：

实际 GPU 架构对应的机器指令。

比如：

```text
FFMA：

浮点融合乘加。


LDG：

Global Memory Load。


LDS：

Shared Memory Load。


STS：

Shared Memory Store。
```

你写的 C++ 代码：

```cpp
c += a * b;
```

最终可能对应一条 FFMA。

但具体使用了多少寄存器、多少访存指令，以及指令如何排列，需要看最终的编译结果。

---

## 18.2 如何查看 SASS？

先编译：

```bash
nvcc -O3 -arch=sm_89 -lineinfo gemm.cu -o gemm
```

然后：

```bash
cuobjdump --dump-sass gemm
```

如果希望保存到文件：

```bash
cuobjdump --dump-sass gemm > gemm_sass.txt
```

例如检查：

```text
是否生成了 FFMA？

float4 加载是否生成了 LDG.128？

Shared Memory 是否使用 LDS.128？

是否有大量额外地址计算？

循环是否被展开？
```

这比仅凭 CUDA C++ 源代码猜测编译器行为更加可靠。

---

## 18.3 什么叫指令交错？

如果指令排列是：

```text
LDS：从 Shared Memory 读取 a。

FFMA：立刻使用 a。
```

第二条指令必须等待第一条指令的数据。

但是如果：

```text
LDS：提前读取下一轮数据。

FFMA：计算当前的 Ct[0][0]。

FFMA：计算当前的 Ct[0][1]。

FFMA：计算当前的 Ct[0][2]。

FFMA：计算当前的 Ct[0][3]。

...

FFMA：使用之前提前读取的数据。
```

中间有很多相互独立的计算。

就可能将 LDS 延迟隐藏在计算过程中。

这就是 ILP、Software Pipelining 和指令交错的关系。

---

## 18.4 Register Bank Conflict

原文还讨论了寄存器文件自身的 Bank Conflict、Reuse Cache 和底层寄存器调度。

这里先知道：

```text
不仅 Shared Memory 有 Bank 结构。

Register File 也存在底层访问资源限制。
```

但是寄存器 Bank 的具体数量、映射和操作数读取规则存在架构差异。

原文将其概括成所有架构都有 4 个 Bank，这不能作为适用于所有 GPU 的通用结论。

而且 C++ 层面并不能像 Shared Memory 数组一样，直接通过数组下标精确控制所有物理寄存器编号。

所以你现在先不深入 SASS 手工调度。

这个阶段收益通常没有前面的算法级和存储层次级优化那么容易获得。

# 十九、编译器优化：模板与 Loop Unrolling

你在 Reduce V5 已经学过：

```cpp
template<int BLOCKSIZE>
```

GEMM 中更加常见：

```cpp
template<
    int BM,
    int BN,
    int BK,
    int TM,
    int TN
>
```

因为这些参数一旦编译时确定：

```cpp
constexpr int BLOCK_SIZE =
    (BM / TM) * (BN / TN);
```

编译器就可以提前计算。

同时：

```cpp
#pragma unroll
for (int p = 0; p < BK; ++p)
```

也有机会完全展开。

对于：

```cpp
float c_frag[8][8];
```

如果所有数组索引都能够在编译时确定，那么编译器更容易把不同元素分配到独立寄存器。

这对于 GEMM 非常重要。

---

## 19.1 为什么建议循环从 0 开始？

例如：

```cpp
#pragma unroll
for (int i = 0; i < TM; ++i) {

    a_frag[i] = As[thread_row + i][p];
}
```

编译器可以很直观地知道：

```text
循环次数固定为 TM。
```

相比：

```cpp
for (int i = thread_row;
     i < thread_row + TM;
     ++i) {
    ...
}
```

前者更明确地表达了固定迭代次数，也便于局部数组索引的常量化。

不过不能绝对地说后一种一定不会被展开。

现代编译器有能力推导许多这类循环。

最终应该检查 SASS 和寄存器分配情况。

---

## 19.2 需要手动用位运算替换所有除法和取模吗？

例如：

```cpp
int warp_id = tid / 32;

int lane_id = tid % 32;
```

可以写成：

```cpp
int warp_id = tid >> 5;

int lane_id = tid & 31;
```

对于非负整数，两者等价。

但如果除数是编译期已知的 2 的整数次幂，现代编译器通常已经能够自动进行这类优化。

所以你不需要为了性能盲目将所有：

```cpp
/

%
```

手动替换成位运算。

更重要的是：

```text
让编译器知道除数是编译期常量。

检查最终机器指令。

通过 Benchmark 验证收益。
```

# 二十、Wave 与 L2 Cache

原文前面还介绍了 Wave 模型。

## 20.1 什么是 Wave？

假设：

```text
GPU 有 24 个 SM。

每个 SM 同时能驻留 2 个 Block。
```

那么一个理想的满驻留批次：

$$
24\times2=48
$$

个 Block。

可以粗略看成一个 Wave。

如果整个 Grid 有 1000 个 Block，那么 GPU 需要不断调度新的 Block。

需要注意：

实际 GPU 调度并不要求整个 Wave 全部结束后，下一批才能开始。

不同 SM 上的 Block 可以在资源释放后陆续获得新的工作。

Wave 更多是一个帮助分析并行度和尾部效应的模型。

---

## 20.2 为什么 Block 之间也有数据复用？

假设输出 C 的两个相邻 Tile：

```text
C Tile (0,0)

C Tile (0,1)
```

它们位于同一个 Block Row，N 方向位置不同。

因此它们需要：

```text
相同的 A 行区域。

不同的 B 列区域。
```

如果这两个 Block 在时间上比较接近地执行，那么 A 的数据可能已经在 L2 Cache 中。

同理：

```text
C Tile (0,0)

C Tile (1,0)
```

可能复用同一批 B 数据。

所以除了：

```text
Block 内利用 Shared Memory 复用。
```

还可以：

```text
Block 间利用 L2 Cache 复用。
```

这就是为什么 GEMM 中有时会对 Block 的逻辑遍历顺序做优化。

例如 Row-major、Column-major、Grouped 或 Swizzled Tile Order。

但 CUDA 普通 Block 的实际执行顺序不受程序员严格保证。

改变逻辑映射可以影响工作局部性，并不等于强制控制硬件调度顺序。

原文给出的 L2 命中率估算属于近似模型，不建议现在将其作为真实 Cache Hit Rate 的计算公式。

真实命中率应当使用 NCU 测量。

# 二十一、你应该怎么写 GEMM Benchmark？

这部分你已经有 Reduce Benchmark 经验了。

基本框架完全相同。

```text
申请 CPU/GPU 内存。

初始化 A、B。

拷贝 A、B 到 GPU。

Warmup。

CUDA Event Record(start)。

重复执行 GEMM。

CUDA Event Record(stop)。

Synchronize(stop)。

计算平均耗时。

计算 TFLOPS。

验证正确性。
```

## 21.1 性能计算部分

直接加入你之前的 Benchmark：

```cpp
double avg_ms = total_ms / repeat;

double flops = 2.0 * M * N * K;

double tflops =
    flops / (avg_ms * 1e-3) / 1e12;

printf("Average time: %.4f ms\n", avg_ms);

printf("Performance: %.4f TFLOPS\n", tflops);
```

如果：

```cpp
double peak_tflops = ...;
```

那么：

```cpp
double utilization =
    tflops / peak_tflops * 100.0;

printf("FP32 peak utilization: %.2f%%\n",
       utilization);
```

这就是之前 Reduce 带宽利用率的对应版本。

```text
Reduce：

Effective Bandwidth / Peak Bandwidth。


GEMM：

Effective TFLOPS / Peak TFLOPS。
```

但它们都只是基于算法工作量与峰值硬件参数的性能比例，不是 NCU 的所有硬件利用率指标。

---

## 21.2 输入矩阵怎么初始化？

一开始可以：

```cpp
std::vector<float> h_A(M * K, 1.0f);

std::vector<float> h_B(K * N, 1.0f);
```

那么理论上：

$$
C_{ij}=K
$$

验证：

```cpp
for (int i = 0; i < M * N; ++i) {

    if (h_C[i] != (float)K) {

        printf("FAILED\n");

        break;
    }
}
```

对于较小、可精确表示的整数 K，全 1 输入非常方便。

但它只能用于初步验证。

因为：

```text
矩阵转置写错。

某些输出坐标交换。

输入索引重复。

加载了错误位置。
```

如果所有元素都等于 1，很多错误可能仍然得到看似正确的结果。

所以一定还要使用非均匀输入。

例如：

```cpp
#include <random>

std::mt19937 rng(123);

std::uniform_real_distribution<float> dist(
    -1.0f, 1.0f
);

for (float& x : h_A) {
    x = dist(rng);
}

for (float& x : h_B) {
    x = dist(rng);
}
```

使用 CPU 参考实现或 cuBLAS 验证结果。

由于不同归约顺序和 FMA 可能产生浮点舍入差异，随机浮点输入应使用合理的绝对误差和相对误差容忍范围。

## 21.3 建议测试哪些矩阵尺寸？

先用小矩阵保证正确性：

```text
M=32, N=32, K=32

M=128, N=128, K=128

M=130, N=257, K=131
```

最后一个用于测试：

```text
M 方向边界。

N 方向边界。

K 方向边界。
```

然后测试性能：

```text
512×512×512

1024×1024×1024

2048×2048×2048

4096×4096×4096
```

如果当前 Naive Kernel 比较慢，就减少 repeat 次数。

不要每个版本无条件执行 100 次。

GEMM 的计算量远大于 Reduce，尤其大矩阵下 Naive 版本可能执行很久。

# 二十二、如何使用 cuBLAS 作为性能参考？

对于 Reduce，参考的是显存带宽。

对于 GEMM，除了理论峰值算力，还应该考虑：

```text
自己手写 GEMM

vs

NVIDIA cuBLAS
```

cuBLAS 是 NVIDIA 提供的高性能 BLAS 库。

其中：

```cpp
cublasSgemm(...)
```

可以用来执行单精度矩阵乘法。

不过 cuBLAS 的传统接口默认按照 Column-major 解释矩阵。

而你写的 CUDA Kernel 使用 Row-major。

所以必须注意参数映射。

---

## 22.1 Row-major 如何调用 cuBLAS？

我们计算：

$$
C=AB
$$

利用：

$$
C^T=B^TA^T
$$

可以交换 A、B 和 M、N，让 cuBLAS 按照 Column-major 解释原来的 Row-major 内存。

示例：

```cpp
#include <cublas_v2.h>

cublasHandle_t handle;

cublasCreate(&handle);

// 尽量避免与普通 FP32 Kernel 比较时
// 引入不同的低精度计算模式
cublasSetMathMode(
    handle,
    CUBLAS_PEDANTIC_MATH
);

float alpha = 1.0f;

float beta = 0.0f;

cublasSgemm(
    handle,

    CUBLAS_OP_N,
    CUBLAS_OP_N,

    N,
    M,
    K,

    &alpha,

    d_B,
    N,

    d_A,
    K,

    &beta,

    d_C,
    N
);

cublasDestroy(handle);
```

编译：

```bash
nvcc -O3 -arch=sm_89 gemm.cu -lcublas -o gemm
```

实际工程中需要检查 cuBLAS API 的返回状态，并将 handle 的创建和销毁放在 Benchmark 计时范围之外。

这里先展示如何调用和处理 Row-major 布局。

注意：

应尽量保证自己实现和 cuBLAS 的数据类型、计算精度、矩阵布局以及计时范围一致。

不要将使用 Tensor Core 加速、允许 TF32 精度的 GEMM，与普通 CUDA Core FP32 Kernel 直接进行不加区分的性能比较。

---

## 22.2 相对于 cuBLAS 的性能比例

假设：

```text
自己手写 GEMM：8 TFLOPS

cuBLAS：10 TFLOPS
```

那么：

$$
\eta_{\mathrm{cublas}}=\frac{8}{10}=80\%
$$

这也是很多 GEMM 优化文章经常使用的指标。

例如：

```text
达到 cuBLAS 80% 的性能。
```

注意它并不等价于：

```text
达到 GPU 理论峰值算力的 80%。
```

这是两个不同的参考基准。

# 二十三、怎么用 NCU 分析 GEMM？

先正常运行：

```bash
./gemm
```

得到真实 Benchmark 耗时。

然后使用：

```bash
ncu --set full \
    --kernel-name regex:gemm_register_tiling \
    --launch-skip 5 \
    --launch-count 1 \
    -o gemm_report \
    ./gemm
```

这里假设程序执行了 5 次匹配 Kernel 的 Warmup。

不要直接将 Profiler 运行期间 CUDA Event 的耗时当成正常性能数据。

---

## 23.1 GEMM 需要重点观察哪些指标？

| 指标 | 可以帮助分析什么 |
|---|---|
| Compute Throughput | 计算流水线是否得到充分利用 |
| DRAM Throughput | 是否受显存吞吐量限制 |
| L2 Throughput / Hit Rate | Block 间的数据复用 |
| Shared Memory Bank Conflicts | Shared Memory 地址布局 |
| Registers Per Thread | Register Tiling 的资源代价 |
| Achieved Occupancy | 实际驻留 Warp 情况 |
| Long Scoreboard | 较长延迟的访存数据依赖 |
| Short Scoreboard | 较短延迟的数据依赖 |
| MIO Throttle | 某些访存及特殊指令流水线的发射压力 |
| Barrier | 同步等待情况 |

这些指标提供的是诊断线索，不是机械的判断公式。

例如：

```text
Long Scoreboard 很高。
```

可能需要研究：

```text
Global Memory 延迟。

Cache 命中率。

预取。

Occupancy。

ILP。
```

而不是简单认为一定需要增加 Block Size。

---

## 23.2 怎么针对不同优化版本使用 NCU？

Naive → Shared Memory Tiling：

主要观察：

```text
Global Memory 请求数量。

DRAM 传输数据量。

L2 Cache。

TFLOPS。
```

Shared Memory Tiling → Register Tiling：

主要观察：

```text
Shared Memory Load 指令。

FFMA 吞吐量。

Register Usage。

Occupancy。
```

Register Tiling → Warp Tiling：

主要观察：

```text
Shared Memory Bank Conflict。

Broadcast 和访存请求效率。
```

Scalar → float4：

主要观察：

```text
Load/Store Instruction 数量。

MIO Throttle。

是否生成向量化指令。
```

Single Buffer → Double Buffer：

主要观察：

```text
Long Scoreboard。

Short Scoreboard。

Barrier。

Register / Shared Memory Usage。
```

不要单纯期待每项指标都变得更好。

真正需要验证的是 Kernel 最终性能是否提升。

# 二十五、GEMM 的完整硬件数据流

到这里，你应该形成下面这张非常重要的脑图：

```text
Global Memory
│
│ 存储完整 A、B 矩阵
│
│ Block Tiling
│ Cooperative Load
│ float4
│ cp.async
▼
Shared Memory
│
│ 存储当前 K-Tile
│
│ As[BM][BK]
│ Bs[BK][BN]
│
│ Warp Tiling
│ Bank Conflict 优化
│ Broadcast
│ Vectorized Load
▼
Register
│
│ a_frag[TM]
│ b_frag[TN]
│ c_frag[TM][TN]
│
│ Outer Product
│ FFMA
│ ILP
▼
Register 中不断累加 C
│
│ 遍历完整 K 维度
│
▼
Global Memory
│
└── 最终 C 矩阵
```

各级优化分别解决：

| 层级 | 核心目标 |
|---|---|
| Global → Shared | 提高数据复用，减少较慢存储层的请求 |
| Shared → Register | 提高每线程局部数据复用 |
| Warp Mapping | 改善 Bank Conflict 和 Broadcast |
| Register Compute | 增加 ILP 和计算吞吐量 |
| Pipeline | 重叠数据搬运和计算 |
| Write Back | 高效写出最终结果 |

# 二十六、这一章和你之前学的 Transformer 有什么关系？

你之前学习 Transformer 时：

```python
Q = X @ W_Q

K = X @ W_K

V = X @ W_V
```

这些都可以对应 GEMM。

例如：

```text
X：

[B*S, H]


W：

[H, H]
```

那么：

```text
M = B*S

K = H

N = H
```

Prefill 阶段：

```text
S 较大。

M 较大。

矩阵乘法有较多数据复用机会。
```

而 Decode 阶段，如果 Batch Size 较小：

```text
M 很小。

K、N 仍然很大。
```

例如：

```text
M = 1

K = 4096

N = 4096
```

数学上就接近矩阵向量乘法 GEMV。

每个权重元素可能只参与很少的计算。

数据复用率明显降低。

所以：

```text
Prefill 更容易成为 Compute-Bound。

小 Batch Decode 更容易成为 Memory-Bound。
```

这不是绝对结论，但能够很好地解释常见 LLM 推理场景中的性能差异。

现在你可以从 CUDA GEMM 的数据复用角度，重新理解之前学过的 LLM Prefill 和 Decode。

# 二十九、最后总结

如果把整篇文章压缩成三个最重要的优化思想：

## 第一个：分块复用

```text
Global Memory 数据太贵。

所以使用 Block Tiling。

让多个 Thread 共享 A、B Tile。
```

## 第二个：寄存器复用

```text
Shared Memory 也不是无限快。

所以使用 Register Tiling。

让每个 Thread 读取少量数据，
执行大量独立的 FFMA。
```

## 第三个：搬运和计算重叠

```text
即使减少了内存请求，
访存延迟仍然存在。

所以使用 Double Buffering 和 Pipeline。

让 GPU 在计算当前 Tile 时，
提前准备下一批数据。
```

这三个思想组成 GEMM 的性能优化核心。

```text
Data Reuse

+

Instruction-Level Parallelism

+

Latency Hiding
```

而之前学习的：

```text
Coalescing

Bank Conflict

Occupancy

Vectorization

Synchronization
```

都是为了更好地实现这三个目标。
