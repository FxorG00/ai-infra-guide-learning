# 2.2 CUDA 内存访问优化：真正理解 Coalescing、Bank Conflict 和 Vectorized Load

这一篇非常重要。

你刚刚学完 2.1：

```text
Warp
SIMT
Warp Divergence
Warp Shuffle
Warp Reduce
```

2.1 主要解决的问题是：

> **一个 Warp 的 32 个 Thread 到底怎么执行？**

而 2.2 开始问另一个更现实的问题：

> **这 32 个 Thread 到底在访问哪些内存地址？**

这就是 CUDA 性能优化真正开始的地方。

你可以先记住这一篇的总主线：

```text
Warp 的 32 个 Thread
        ↓
访问 Global Memory
        ↓
地址是否连续？
        ↓
Coalesced Access

如果用了 Shared Memory
        ↓
访问落在哪些 Bank？
        ↓
Bank Conflict

如果数据连续而且对齐
        ↓
能不能一次多读几个？
        ↓
Vectorized Load
```

所以这一篇其实就是研究一句话：

> **GPU 不仅关心你“读了多少数据”，还非常关心你“怎么读这些数据”。**

---

# 一、为什么内存访问会成为 GPU 的性能瓶颈？

GPU 的计算能力非常强。

例如原文用 A100 举例：

```text
FP16 Tensor Core 峰值算力
≈ 312 TFLOPS

HBM2e 带宽
≈ 2 TB/s
```

看起来都非常夸张。

但是考虑最简单的向量加法：

```cpp
C[i] = A[i] + B[i];
```

每一个元素需要：

```text
读取 A[i]    4 Bytes
读取 B[i]    4 Bytes
写入 C[i]    4 Bytes
```

总共：

```text
12 Bytes
```

但真正的计算只有：

```text
1 次加法
```

也就是大约：

```text
1 FLOP
```

所以 Arithmetic Intensity：

$$
\mathrm{AI}
=
\frac{1\ \mathrm{FLOP}}
{12\ \mathrm{Bytes}}
$$

大约：

$$
\mathrm{AI}
\approx
0.083\ \mathrm{FLOP/Byte}
$$

---

# 二、这意味着什么？

假设显存带宽：

$$
2\ \mathrm{TB/s}
$$

那么即使把内存带宽完全跑满，能够支撑的计算吞吐量大概也只有：

$$
2\ \mathrm{TB/s}
\times
0.083\ \mathrm{FLOP/Byte}
$$

大约：

$$
166\ \mathrm{GFLOPS}
$$

而 GPU 理论计算能力却是：

```text
几百 TFLOPS
```

两者差了巨大数量级。

所以这种 Kernel 根本不是：

```text
算不动
```

而是：

```text
数据送不过来
```

也就是：

```text
Memory-Bound
```

---

# 三、重新理解 Memory-Bound 和 Compute-Bound

原文再次用了 Roofline 的分类。

## Memory-Bound

意思是：

> **性能主要被内存带宽限制。**

例如：

```text
Elementwise

Vector Add

Matrix Transpose

很多 Reduction
```

这种 Kernel 的重点不是：

```text
减少一两个加法
```

而是：

```text
减少内存访问

提高内存访问效率

提高 Data Reuse
```

---

## Compute-Bound

意思是：

> **数据已经喂得够快，真正卡在计算单元。**

这时候优化方向才更多是：

```text
提高计算并行度

提高 Tensor Core 利用率

减少计算指令
```

---

# 四、所以这一章的第一大主角：Global Memory Coalescing

前面已经学过：

```text
一个 Warp
=
32 Threads
```

现在假设这 32 个 Thread 同时执行：

```cpp
float x = data[tid];
```

GPU 不会把它简单理解成：

```text
Thread 0 自己读一次

Thread 1 自己读一次

Thread 2 自己读一次

...
```

硬件会观察：

> **这整个 Warp 的 32 个地址是什么样的？**

然后尝试把它们合并成尽可能少的：

```text
Memory Transaction
```

这就是：

```text
Coalesced Access
```

中文：

```text
合并访问
```

---

# 五、合并访问最核心的一句话

直接记：

> **Warp 内连续 Thread，尽量访问连续内存地址。**

例如：

```text
Thread 0  → data[0]

Thread 1  → data[1]

Thread 2  → data[2]

Thread 3  → data[3]

...

Thread 31 → data[31]
```

这是非常理想的模式。

---

# 六、为什么连续访问这么舒服？

一个 `float` 是：

$$
4\ \mathrm{Bytes}
$$

一个 Warp：

$$
32
$$

个 Thread。

如果每个 Thread 读一个连续 `float`：

$$
32\times4
=
128\ \mathrm{Bytes}
$$

所以整个 Warp 正好需要连续的：

```text
128 Bytes
```

原文这里介绍：

```text
Global Memory Transaction 的基本 Sector 粒度
=
32 Bytes
```

同时：

```text
一个 128 Bytes Cache Line
=
4 个 32 Bytes Sector
```

所以连续访问：

```text
data[0]
data[1]
...
data[31]
```

会覆盖一段紧凑的 128 Bytes 数据。

可以理解成：

```text
32 Threads
       ↓
请求 32 个连续 float
       ↓
形成连续 128B 区域
       ↓
硬件可以非常高效地合并请求
```

---

# 七、注意原文表格里的“1x”怎么理解

原文后面的表格会写：

```text
连续访问：
事务数 1x
```

这里的：

```text
1x
```

主要表示：

> **最理想访问模式对应的基准开销。**

不是说前面提到的 32B Sector 突然消失了。

按照原文前面的定义：

```text
128B
=
4 个 32B Sector
```

你只需要把它理解成：

```text
连续访问
=
最少、最有效的 Memory Transaction 模式

stride 越大
=
相对于这个基准，需要越来越多事务
```

就够了。

---

# 八、非合并访问是什么样？

例如：

```cpp
out[tid] = data[tid * 32];
```

一个 Warp 会访问：

```text
Thread 0  → data[0]

Thread 1  → data[32]

Thread 2  → data[64]

Thread 3  → data[96]

...
```

一个 float 是 4 Bytes。

因此相邻 Thread 地址之间相差：

$$
32\times4
=
128\ \mathrm{Bytes}
$$

于是：

```text
Thread 0 要一块数据

隔 128B

Thread 1 又要一块

隔 128B

Thread 2 又要一块
```

完全散开。

---

# 九、为什么这样会浪费带宽？

因为内存不是：

```text
你要 4 Bytes
我刚好只运输 4 Bytes
```

而是按一定的 Transaction / Sector 去搬数据。

于是可能发生：

```text
搬回来一整块数据
↓
Thread 实际只用了里面很少一部分
```

大量带宽被浪费。

所以你可以把：

```text
Effective Bandwidth
```

理解成：

> **搬回来的数据里，到底有多少是真正被 Thread 用到的？**

---

# 十、原文给出的 Stride 直觉

原文用 A100 读取 1GB 数据举例：

| 访问模式 | 相对事务 | 有效带宽利用率 | 相对耗时 |
|---|---:|---:|---:|
| stride = 1 | 1x | 约 95% | 1x |
| stride = 2 | 2x | 约 50% | 2x |
| stride = 4 | 4x | 约 25% | 4x |
| stride = 32 | 32x | 约 3% | 32x |
| 随机访问 | 32x | 约 3% | 32x |

你不用死背数字。

真正记住趋势：

```text
stride 越大
↓
Warp 地址越分散
↓
Memory Transaction 越多
↓
真正有效的数据比例越低
↓
带宽利用率越差
```

---

# 十一、这就是为什么 CUDA 优化要站在 Warp 视角看地址

以后看到：

```cpp
data[some_index]
```

不要只问：

> “这个 Index 算得对不对？”

还要问：

> **同一个 Warp 的 32 个 Thread，算出来的 32 个 Index 分别是什么？**

例如：

```cpp
data[tid]
```

Warp 0：

```text
0
1
2
3
...
31
```

很好。

但：

```cpp
data[tid * 32]
```

Warp 0：

```text
0
32
64
96
...
```

就很差。

所以 CUDA 优化里：

> **Thread → Data 的映射既决定正确性，也决定性能。**

---

# 十二、第二个问题：Alignment

光连续还不完全够。

还要考虑：

```text
对齐
```

例如 Warp 连续读取：

```text
data[0] ~ data[31]
```

这是：

```text
128 Bytes
```

如果起始地址刚好位于适当边界上：

```text
非常舒服
```

但如果你从：

```cpp
data[1]
```

开始读，

那么 Warp 访问的是：

```text
data[1] ~ data[32]
```

虽然还是连续，

但整个 128B 区间发生了偏移。

可能跨越更多 Transaction / Cache Sector。

于是可能需要额外访问。

---

# 十三、cudaMalloc 为什么在这里很友好？

原文指出：

```text
cudaMalloc
```

返回的地址天然具有较高对齐保证。

原文这里给出的值是：

```text
256 Bytes 对齐
```

所以：

```cpp
float* data;

cudaMalloc(&data, size);
```

然后从：

```cpp
data[0]
```

开始正常连续访问，

通常不需要担心基础地址没对齐。

真正需要注意的往往是：

```cpp
float* ptr = data + offset;
```

这种：

```text
手动 Offset
```

---

# 十四、比如 data + 1 为什么可能影响对齐？

假设：

```text
data
```

本来对齐得非常好。

但：

```cpp
data + 1
```

对于 `float` 来说，就是偏移：

$$
4\ \mathrm{Bytes}
$$

原本：

```text
128B 边界
```

可能就被打破。

所以：

```text
连续
```

和：

```text
对齐
```

是两个相关但不同的问题。

最理想：

```text
连续
+
对齐
```

# 十五、AoS 和 SoA 再正式理解一次

你在 1.3 已经见过。

这一篇重新从：

```text
Coalescing
```

角度解释。

---

# 十六、AoS：Array of Structures

例如：

```cpp
struct Particle {
    float x;
    float y;
    float z;
    float w;
};

Particle particles[N];
```

内存布局：

```text
x0 y0 z0 w0
x1 y1 z1 w1
x2 y2 z2 w2
...
```

假设现在一个 Warp 每个 Thread 都只需要：

```text
x
```

那么：

```text
Thread 0 → x0

Thread 1 → x1

Thread 2 → x2
```

但是地址实际是：

```text
x0
↓
隔 y0 z0 w0
↓
x1
↓
隔 y1 z1 w1
↓
x2
```

相邻 `x` 相隔：

$$
16\ \mathrm{Bytes}
$$

所以不是最理想的连续模式。

---

# 十七、SoA：Structure of Arrays

改成：

```cpp
struct Particles {
    float x[N];
    float y[N];
    float z[N];
    float w[N];
};
```

内存：

```text
x0 x1 x2 x3 x4 ...

y0 y1 y2 y3 y4 ...

z0 z1 z2 z3 z4 ...
```

那么一个 Warp 读取 x：

```text
Thread 0 → x[0]

Thread 1 → x[1]

Thread 2 → x[2]

...
```

直接变成连续访问。

所以原文强调：

> GPU 的 Warp 并行模式天然喜欢 SoA 这种连续字段布局。

---

# 十八、不过真正应该记的不是“SoA 永远正确”

真正应该记：

> **数据结构的 Layout 会改变 Warp 的 Memory Access Pattern。**

所以以后看到数据结构，不只考虑：

```text
代码好不好写
```

还要考虑：

```text
Warp 的地址是不是连续
```

这就是 GPU 编程和普通 CPU 编程一个很大的思维区别。

---

# 十九、二维数组为什么行访问和列访问差很多？

C / C++ 二维数组通常是：

```text
Row-Major
```

也就是按行连续存储。

假设：

```text
Matrix:

a00 a01 a02 a03
a10 a11 a12 a13
a20 a21 a22 a23
```

实际内存：

```text
a00 a01 a02 a03 a10 a11 a12 a13 a20 ...
```

公式：

$$
\mathrm{index}
=
\mathrm{row}
\times
\mathrm{cols}
+
\mathrm{col}
$$

---

# 二十、按行访问

例如：

```text
Thread 0 → matrix[row][0]

Thread 1 → matrix[row][1]

Thread 2 → matrix[row][2]
```

Index：

```text
row * cols + 0

row * cols + 1

row * cols + 2
```

连续。

所以：

```text
Coalesced
```

---

# 二十一、按列访问

如果：

```text
Thread 0 → matrix[0][col]

Thread 1 → matrix[1][col]

Thread 2 → matrix[2][col]
```

Index：

```text
0 * cols + col

1 * cols + col

2 * cols + col
```

相邻地址之间相差：

```text
cols
```

也就是：

```text
stride = cols
```

如果 Matrix 很宽：

```text
stride 非常大
```

Coalescing 就非常差。

这也是后面：

```text
矩阵转置
```

为什么这么经典。

---

# 二十二、到这里 Global Memory 的核心已经出来了

你现在要形成：

```text
Warp
↓
32 个地址
↓
连续吗？
↓
对齐吗？
↓
可以合并成多少 Memory Transaction？
```

这就是 Global Memory 优化第一视角。

---

# 二十三、接下来第二大主角：Shared Memory Bank Conflict

这部分你已经理解不少了。

原文这里正式给出 Shared Memory Bank 的结构。

Shared Memory：

```text
32 Banks
```

每个 Bank 宽：

```text
4 Bytes
```

也就是：

```text
32 bits
```

所以对于一个 `float` 数组：

```cpp
__shared__ float data[];
```

可以粗略理解成：

```text
data[0]  → Bank 0

data[1]  → Bank 1

data[2]  → Bank 2

...

data[31] → Bank 31

data[32] → Bank 0

data[33] → Bank 1
```

---

# 二十四、你之前说的 mod 32 就在这里

对于 32-bit word，可以理解：

$$
\mathrm{Bank}
=
\mathrm{wordIndex}
\bmod 32
$$

更一般地按 Byte Address 写：

$$
\mathrm{Bank}
=
\left(
\frac{\mathrm{byteAddress}}{4}
\right)
\bmod 32
$$

例如：

```text
shared[0]
```

属于：

```text
Bank 0
```

而：

```text
shared[32]
```

也是：

```text
Bank 0
```

因为：

$$
32\bmod32=0
$$

---

# 二十五、什么时候发生 Bank Conflict？

非常重要。

必须同时满足：

```text
同一个 Warp
+
同一条 Shared Memory 访问指令
+
多个 Thread
+
访问同一个 Bank
+
但地址不同
```

就会产生：

```text
Bank Conflict
```

例如：

```text
Thread 0 → shared[0]

Thread 1 → shared[32]
```

都是：

```text
Bank 0
```

但地址不同。

于是发生冲突。

---

# 二十六、Bank Conflict 为什么会慢？

按照原文的模型：

```text
每个 Bank 每个周期只能服务一个访问
```

所以本来：

```text
32 个 Thread
→ 32 Banks
→ 一起完成
```

现在如果：

```text
多个 Thread
→ Bank 0
```

就需要：

```text
部分串行化
```

例如：

```text
2-way Conflict
```

粗略理解成：

```text
2 次服务
```

而：

```text
32-way Conflict
```

最糟糕时可能变成：

```text
32 次串行访问
```

---

# 二十七、但是 Broadcast 是特殊情况

如果：

```text
Thread 0 → shared[0]

Thread 1 → shared[0]

Thread 2 → shared[0]

...
```

所有 Thread：

```text
同一个 Bank
```

而且：

```text
完全相同地址
```

这时候硬件可以：

```text
读取一次
↓
广播给所有 Thread
```

所以：

```text
Same Bank
+
Same Address
```

不是普通 Bank Conflict。

真正的问题是：

```text
Same Bank
+
Different Address
```

---

# 二十八、矩阵转置为什么会出现经典 32-way Bank Conflict？

假设 Shared Memory：

```cpp
__shared__ float tile[32][32];
```

C/C++ Row-Major。

所以：

```cpp
tile[row][col]
```

线性位置：

$$
\mathrm{index}
=
row\times32+col
$$

Bank：

$$
\mathrm{bank}
=
(row\times32+col)\bmod32
$$

---

# 二十九、按行访问没有问题

比如一个 Warp：

```text
Thread 0 → tile[0][0]

Thread 1 → tile[0][1]

Thread 2 → tile[0][2]

...

Thread 31 → tile[0][31]
```

Bank：

```text
Bank 0
Bank 1
Bank 2
...
Bank 31
```

完美。

---

# 三十、按列访问会发生什么？

假设固定：

```text
col = 0
```

不同 Thread 访问：

```text
tile[0][0]

tile[1][0]

tile[2][0]

...

tile[31][0]
```

Bank：

$$
(0\times32+0)\bmod32=0
$$

$$
(1\times32+0)\bmod32=0
$$

$$
(2\times32+0)\bmod32=0
$$

全部都是：

```text
Bank 0
```

但是地址不同。

所以：

```text
32 Threads
↓
同一个 Bank
↓
32 个不同地址
↓
32-way Bank Conflict
```

非常惨。

---

# 三十一、Padding 为什么只加 1 就能救回来？

把：

```cpp
__shared__ float tile[32][32];
```

改成：

```cpp
__shared__ float tile[32][33];
```

现在：

$$
\mathrm{index}
=
row\times33+col
$$

Bank：

$$
\mathrm{bank}
=
(row\times33+col)\bmod32
$$

因为：

$$
33\bmod32=1
$$

所以每换一行：

```text
Bank 会往后错一格
```

---

# 三十二、还是访问第 0 列

现在：

```text
tile[0][0]
→ Bank 0

tile[1][0]
→ Bank 1

tile[2][0]
→ Bank 2

tile[3][0]
→ Bank 3

...
```

原本：

```text
全部撞 Bank 0
```

现在：

```text
32 Threads
↓
32 Banks
```

冲突消失。

---

# 三十三、Padding 的本质

不是：

> “多一列能提高计算能力。”

而是：

> **故意改变内存 Layout，破坏原来的 Bank 周期。**

也就是：

```text
原来每行 32 个 float
↓
刚好等于 Bank 数量
↓
下一行又回到同一个 Bank Pattern
```

改成：

```text
33
```

以后：

```text
每行错位一个 Bank
```

于是把访问打散。

---

# 三十四、Padding 的代价大吗？

每行只多：

```text
1 float
```

也就是：

$$
4\ \mathrm{Bytes}
$$

32 行也就多：

$$
32\times4
=
128\ \mathrm{Bytes}
$$

相比消除：

```text
32-way Bank Conflict
```

通常非常划算。

---

# 三十五、Swizzle 又是什么？

原文还介绍了高级方法：

```text
Swizzle
```

Padding 是：

```text
多放一点空间
↓
改变 Layout
```

Swizzle 则是：

```text
不额外 Padding
↓
通过索引变换
↓
把地址重新排列
```

例如原文给出 XOR 思路：

```cpp
tile[row][col ^ row]
```

让不同 Thread 的 Bank 分布被打散。

---

# 三十六、你现在 Swizzle 学到什么程度就够了？

现在只需要知道：

> **Swizzle = 用数学方式重新映射地址，避免 Bank Conflict。**

而且它会在：

```text
高性能 GEMM

CUTLASS
```

这种地方大量出现。

目前不用自己设计 Swizzle。

Padding 能理解透就够了。

---

# 三十七、怎么知道代码真的有 Bank Conflict？

不是全靠肉眼猜。

原文介绍：

```text
Nsight Compute
```

可以查看 Shared Memory Bank Conflict 指标。

例如：

```text
Shared Load Bank Conflict

Shared Store Bank Conflict
```

如果计数明显不为 0，

就需要检查：

```text
Warp 的 Shared Memory 地址 Pattern
```

# 三十八、第三大主角：Vectorized Load

现在考虑一个问题。

普通代码：

```cpp
float x = input[idx];
```

一个 Thread：

```text
一次读 1 个 float
=
4 Bytes
```

如果一个 Thread 本来就要连续处理：

```text
4 个 float
```

传统方式可能需要：

```text
Load
Load
Load
Load
```

也就是：

```text
4 条加载指令
```

---

# 三十九、float4 是什么？

CUDA 提供：

```cpp
float4
```

它里面包含：

```text
4 个 float
```

所以大小：

$$
4\times4
=
16\ \mathrm{Bytes}
$$

于是可以：

```cpp
float4 value =
    reinterpret_cast<float4*>(input)[tid];
```

一次读取：

```text
16 Bytes
```

---

# 四十、Vectorized Load 的核心不是“总共少读数据”

这一点非常重要。

假设你本来就需要：

```text
4 个 float
```

Scalar Load：

```text
读 4 次
```

Vectorized Load：

```text
读 1 次 float4
```

真正的数据量：

```text
还是 16 Bytes
```

没有凭空减少。

减少的是：

```text
Memory Instruction 数量
```

例如原文概括：

```text
4 次 LDG.32
↓
1 次 LDG.128
```

所以主要收益是：

```text
更少的 Load 指令

更少的指令调度开销

每条指令搬更多有效数据
```

---

# 四十一、常见 Vector Type

原文列出：

| 类型 | 大小 | 内容 |
|---|---:|---|
| `float2` | 8 Bytes | 2 个 float |
| `float4` | 16 Bytes | 4 个 float |
| `int4` | 16 Bytes | 4 个 int |
| `double2` | 16 Bytes | 2 个 double |

其中最常见的之一：

```cpp

```

# 四十二、为什么一个 Warp 用 float4 会读取 512 Bytes？

一个 Thread：

$$
16\ \mathrm{Bytes}
$$

32 个 Thread：

$$
32\times16
=
512\ \mathrm{Bytes}
$$

因此一个 Warp 这次一共处理：

```text
512 Bytes
```

而 Scalar float：

$$
32\times4
=
128\ \mathrm{Bytes}
$$

所以 `float4` 不是说：

```text
用一条 Cache Line 搬四倍数据
```

而是：

```text
每条 Thread Load 指令直接处理 4 倍元素
```

整个 Warp 自然需要更多 Cache Line。

# 四十三、Vectorized Copy 怎么写？

Scalar：

```cpp
__global__ void scalar_copy(
    float* dst,
    float* src,
    int N
) {
    int tid =
        threadIdx.x
        +
        blockIdx.x * blockDim.x;

    if (tid < N) {
        dst[tid] = src[tid];
    }
}
```

每个 Thread：

```text
1 个元素
```

# 四十四、float4 版本

```cpp
__global__ void vectorized_copy(
    float* dst,
    float* src,
    int N
) {
    int tid =
        threadIdx.x
        +
        blockIdx.x * blockDim.x;

    int idx = tid * 4;

    if (idx + 3 < N) {

        float4 value =
            reinterpret_cast<float4*>(src)[tid];

        reinterpret_cast<float4*>(dst)[tid]
            = value;
    }
}
```

注意这里非常有意思。

# 四十五、为什么是 [tid] 而不是 [idx]？

原本：

```cpp

```

类型是：

```cpp

```

所以：

```cpp

```

代表跳：

$$
4\ \mathrm{Bytes}
$$

但转成：

```cpp

```

以后：

```cpp

```

代表跳：

$$
16\ \mathrm{Bytes}
$$

所以：

```text
float4[0]
=
原 float 的 0 ~ 3

float4[1]
=
原 float 的 4 ~ 7

float4[2]
=
原 float 的 8 ~ 11
```

因此：

```cpp

```

正好就行。

因为这个 Thread 要处理：

```text

idx + 2

```

四个元素。

# 四十七、Vectorized Load 最大的问题：Alignment

`float4` 大小：

$$

$$

所以地址需要满足：

```text

```

例如：

```cpp

```


通常没问题。

# 四十八、但如果 data + 3 呢？

一个 float：

$$

$$

所以：

```cpp

```

偏移：

$$

$$

如果原来是 16B 对齐：

```text

```

以后就不再是：

```text

```

# 四十九、怎么处理未对齐的头部？

经典做法：

```text

↓

最后不足 4 个元素
↓
Scalar 处理 Tail
```

所以模式：

```text

↓
Scalar

Body
↓
Vectorized

Tail
↓
Scalar
```

这是一种非常常见的 SIMD / GPU 向量化思路。

应该马上想到：

```text
Warp 0:

data[0]
data[32]
data[64]
...

→ 大 Stride
→ 非合并
→ 差
```

这个必须形成条件反射。

# 八十三、第二件事：Bank Conflict

对于：

```cpp
__shared__ float data[];
```

看到：

```text
data[0]
data[32]
data[64]
```

应该想到：

```text
Bank 0
Bank 0
Bank 0
```

如果同 Warp Thread 同时这么访问不同地址：

```text
Bank Conflict
```

# 八十四、第三件事：Padding

```cpp

```

然后：

```text

```

马上想到：

```text
32-way Bank Conflict
```

```cpp
float tile[32][33];
```

以后：

```text
每行 Bank Pattern 错开一位
```

冲突消失。

# 八十六、第五件事：Shared Memory 不只是“更快的缓存”

你之前可能把 Shared Memory 理解成：

> **把 HBM 数据搬近一点。**

这没错。

但是这一篇矩阵转置告诉你，Shared Memory 还有第二个非常重要的功能：

> **改变数据访问 Pattern。**

也就是：

```text
Global Memory 不方便按某个方向访问
↓
先以 Coalesced 方式搬到 Shared Memory
↓
在 Shared Memory 内重新组织
↓
再以 Coalesced 方式写出去
```

这个思维后面 GEMM、Attention 都非常重要。

# 八十八、你现在最好自己做的一个小练习

## Pattern 1

```cpp

```

```text

```



```text

需要更多 Memory Transaction
```


Warp 0：

```text
0
32
64
96
...
```

结论：

```text

```

## Pattern 4

Shared Memory：

```cpp
x = shared[threadIdx.x];
```

Warp 0：

```text
Bank 0
Bank 1
...
Bank 31
```

```text
No Bank Conflict
```


```text

Bank 0
Bank 0
...
```

# 九十二、最后把整篇压成 10 句话

第一句：

> **很多 CUDA Kernel 真正的瓶颈不是算力，而是 Memory Bandwidth。**

第二句：

> **Global Memory 优化首先应该站在 Warp 视角观察 32 个 Thread 的地址。**

第三句：

> **连续 Thread 访问连续地址，可以让硬件更高效地合并 Memory Transaction。**

第四句：

> **大 Stride 和随机访问会浪费大量有效带宽。**

第五句：

> **连续访问之外，还要考虑地址 Alignment。**

第六句：

> **Shared Memory 有 32 个 Bank，同 Warp 访问同 Bank 不同地址会产生 Bank Conflict。**

第七句：

> **Padding 可以通过改变 Shared Memory Layout 消除周期性的 Bank Conflict。**

第八句：

> **Vectorized Load 用 float4 等类型让一条 Load 指令处理多个连续元素。**

第九句：

> **Shared Memory 不只是高速缓存，也可以作为中转站改变 Global Memory 的访问 Pattern。**

第十句：

> **CUDA 内存优化的核心就是：让数据搬得更少、搬得更连续、搬回来以后尽量多用几次。**
