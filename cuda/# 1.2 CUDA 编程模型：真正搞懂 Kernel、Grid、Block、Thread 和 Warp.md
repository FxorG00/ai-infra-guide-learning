# 1.2 CUDA 编程模型：真正搞懂 Kernel、Grid、Block、Thread 和 Warp

这一篇是你正式进入 CUDA 之后非常重要的一篇。

前面的 GPU Basics 更多是在告诉你：

```text
GPU 有 SM
有 Warp
有 Thread
有 Register
有 Shared Memory
```

但那些还是“硬件地图”。

这一篇开始真正回答：

> **我写一个 CUDA 程序以后，到底怎么让成千上万个 GPU 线程去处理数据？**

所以这一篇最核心的主线其实只有：

```text
CPU Host
   ↓
启动 CUDA Kernel
   ↓
一个 Grid
   ↓
很多 Block
   ↓
很多 Thread
   ↓
Block 被调度到 SM
   ↓
Thread 又以 Warp 为单位执行
```

原文的核心内容也是围绕：

```text
Host / Device
Grid / Block / Thread
线程索引
Kernel Launch
Block Size
Warp
Occupancy
```

展开的。

---

# 一、先理解 CUDA 为什么叫“异构计算”

CUDA 程序不是：

```text
所有代码都在 GPU 上跑
```

而是：

```text
CPU + GPU
```

一起工作。

这里有两个非常重要的词：

```text
Host
```

通常就是：

```text
CPU
```

而：

```text
Device
```

通常就是：

```text
GPU
```

所以：

```text
Host = CPU

Device = GPU
```

---

# 二、CPU 和 GPU 在 CUDA 程序里分别干什么？

可以这样理解：

```text
CPU：

负责控制
负责准备数据
负责申请 GPU 内存
负责把数据传给 GPU
负责启动 Kernel
负责最后拿回结果


GPU：

收到任务以后
启动大量线程
并行执行计算
```

所以原文用了一个很形象的类比：

```text
CPU = 厂长

GPU = 有很多工人的车间
```

CPU 负责：

> “你们现在去处理这批数据。”

GPU 负责：

> “收到，几千几万个线程一起干。”

---

# 三、一个典型 CUDA 程序的执行流程

大概可以先想成：

```text
CPU
│
├── 创建 / 初始化数据
│
├── 在 GPU 上申请显存
│
├── 把数据从 CPU 搬到 GPU
│
├── 启动 Kernel
│
│       ↓
││     GPU
││      ↓
││   大量线程并行计算
││
├── 等待 GPU
│
├── 把结果从 GPU 搬回 CPU
│
└── 后续处理
```

数据流通常类似：

```text
CPU DRAM
   ↓
cudaMemcpy
   ↓
GPU HBM
   ↓
Kernel
   ↓
GPU HBM
   ↓
cudaMemcpy
   ↓
CPU DRAM
```

所以你前面学过的：

```python
x = x.cuda()
```

背后其实就在做类似：

```text
Host → Device
```

的数据移动。

---

# 四、CUDA 里面的三种函数修饰符

原文这里介绍了三个：

```cpp
__global__

__device__

__host__
```

这三个其实是在告诉 CUDA：

> **这个函数到底在哪里运行，又能从哪里调用？**

---

## 1. __global__

例如：

```cpp
__global__ void myKernel() {
    ...
}
```

意思是：

```text
这个函数在 GPU 上执行
```

它就是我们常说的：

```text
CUDA Kernel
```

通常由 CPU 启动。

所以：

```text
CPU
↓
调用 __global__ Kernel
↓
GPU 执行
```

---

## 2. __device__

例如：

```cpp
__device__ float square(float x) {
    return x * x;
}
```

意思是：

```text
在 GPU 上运行
并且主要由 GPU 代码调用
```

可以把它理解成：

> Kernel 内部使用的 GPU 辅助函数。

---

## 3. __host__

表示：

```text
CPU 函数
```

普通 C++ 函数本来默认就是 Host 函数。

---

# 五、Kernel 到底是什么？

这个概念你刚刚问过。

Kernel 可以先定义成：

> **一段会让大量 GPU 线程并行执行的函数。**

例如：

```cpp
__global__ void doubleArray(float* x) {
    ...
}
```

CPU 可以启动这个 Kernel。

然后 GPU 可能产生：

```text
Thread 0
Thread 1
Thread 2
Thread 3
...
Thread 99999
```

大家都执行：

```cpp
doubleArray(...)
```

但是每一个 Thread 负责不同的数据。

所以：

```text
Kernel

不是一个线程
```

而是：

> **所有线程都会执行的那段程序。**

这个区别非常重要。

---

# 六、Kernel 和 Thread 的关系

比如 Kernel 写的是：

```cpp
__global__ void doubleArray(float* x) {

    int i = ...;

    x[i] = x[i] * 2.0f;
}
```

假设启动 1000 个线程。

那么：

```text
Thread 0：

i = 0
x[0] *= 2


Thread 1：

i = 1
x[1] *= 2


Thread 2：

i = 2
x[2] *= 2


...


Thread 999：

i = 999
x[999] *= 2
```

它们执行的：

```text
代码完全一样
```

但：

```text
i 不一样
```

于是处理不同的数据。

这就是 GPU 数据并行最基本的思想。

---

# 七、为什么不能直接说“启动 100000 个线程”就完事？

因为 CUDA 不会把所有线程扔在一个巨大平面里。

它会组织成三级结构：

```text
Grid
  ↓
Block
  ↓
Thread
```

这是这篇文章最重要的地方。

你必须真正吃透。

---

# 八、Grid / Block / Thread 到底是什么？

原文用了学校的类比，非常好用。

可以理解成：

```text
Grid
=
整个学校


Block
=
一个班


Thread
=
一个学生
```

所以：

```text
一次 Kernel Launch
        ↓
      一个 Grid
        ↓
很多个 Block
        ↓
每个 Block 很多个 Thread
```

---

# 九、Grid 是什么？

最重要的一句话：

> **一次 Kernel 启动产生的所有线程整体，就属于一个 Grid。**

比如：

```cpp
myKernel<<<100, 256>>>(...);
```

大概表示：

```text
启动一个 Grid

Grid 里面：
100 个 Block

每个 Block：
256 个 Thread
```

所以总线程数：

$$
100 \times 256 = 25600
$$

也就是说：

```text
Kernel Launch
       ↓
     Grid
       ↓
  100 Blocks
       ↓
每 Block 256 Threads
```

---

# 十、Block 是什么？

Block 是：

> **一组能够互相协作的 Thread。**

同一个 Block 里的线程有两个非常重要的能力：

```text
1. 可以共享 Shared Memory

2. 可以进行 Block 内同步
```

所以 Block 不只是：

```text
为了把线程分组好看
```

它其实还是：

```text
线程协作单位
```

后面你学：

```text
Shared Memory
Reduce
GEMM Tiling
```

都会大量使用 Block。

---

# 十一、Thread 是什么？

Thread 是 CUDA 编程里逻辑上的最小执行单位。

比如：

$$
C_i=A_i+B_i
$$

可以：

```text
Thread 0 → C[0]

Thread 1 → C[1]

Thread 2 → C[2]

...

Thread N → C[N]
```

所以一个最基本的思维就是：

> **给每一个 Thread 分配一份数据。**

问题就变成：

> Thread 怎么知道自己到底应该处理哪个数据？

这就进入索引。

---

# 十二、Thread 怎么知道“我是谁”？

CUDA 提供几个内置变量：

```cpp
threadIdx

blockIdx

blockDim

gridDim
```

这四个一定要认识。

---

# 十三、threadIdx

```cpp
threadIdx
```

表示：

> **当前 Thread 在自己的 Block 里面是第几个。**

比如一个 Block 有：

```text
256 Threads
```

那么可能：

```text
threadIdx.x = 0
threadIdx.x = 1
threadIdx.x = 2
...
threadIdx.x = 255
```

注意：

```text
threadIdx
```

只是：

> Block 内编号。

不是整个 Grid 的全局编号。

---

# 十四、blockIdx

```cpp
blockIdx
```

表示：

> **当前 Block 在 Grid 里面是第几个 Block。**

例如：

```text
Block 0
Block 1
Block 2
Block 3
```

那么：

```cpp
blockIdx.x
```

分别就是：

```text
0
1
2
3
```

---

# 十五、blockDim

```cpp
blockDim
```

表示：

> **一个 Block 有多少个 Thread。**

例如启动：

```cpp
myKernel<<<100, 256>>>();
```

那么：

```cpp
blockDim.x
```

就是：

$$
256
$$

---

# 十六、gridDim

```cpp
gridDim
```

表示：

> **整个 Grid 有多少个 Block。**

还是：

```cpp
myKernel<<<100, 256>>>();
```

那么：

```cpp
gridDim.x
```

就是：

$$
100
$$

---

# 十七、把四个变量放在一起

假设：

```cpp
myKernel<<<100, 256>>>();
```

那么：

```text
gridDim.x
=
100


blockDim.x
=
256
```

对于某一个线程：

```text
它可能在 Block 3

并且是 Block 3 里的 Thread 10
```

那么：

```cpp
blockIdx.x = 3

threadIdx.x = 10
```

---

# 十八、最重要的公式：全局 Thread ID

现在问题来了：

```text
Block 3 里面的 Thread 10

在整个 Grid 里面到底是第几个 Thread？
```

公式就是：

$$
\mathrm{globalIdx}
=
\mathrm{blockIdx.x}
\times
\mathrm{blockDim.x}
+
\mathrm{threadIdx.x}
$$

这个公式你一定要理解，不要只是背。

---

# 十九、为什么是这个公式？

假设：

$$
\mathrm{blockDim.x}=256
$$

也就是每个 Block 有：

$$
256
$$

个 Thread。

那么：

```text
Block 0：

Thread 0 ~ 255
```

Block 1 前面已经有：

$$
1\times256
$$

个线程。

所以 Block 1 的：

```text
Thread 0
```

全局编号就是：

$$
1\times256+0=256
$$

Block 1 的：

```text
Thread 10
```

就是：

$$
1\times256+10=266
$$

同理 Block 3 Thread 10：

$$
3\times256+10=778
$$

所以：

```cpp
int idx =
    blockIdx.x * blockDim.x
    + threadIdx.x;
```

实际上就是：

> **前面的 Block 一共有多少线程 + 我在当前 Block 里的编号。**

---

# 二十、用一个小例子彻底理解

假设：

```text
Grid：

4 个 Block


每个 Block：

8 个 Thread
```

那么：

```text
Block 0:
0 1 2 3 4 5 6 7

Block 1:
8 9 10 11 12 13 14 15

Block 2:
16 17 18 19 20 21 22 23

Block 3:
24 25 26 27 28 29 30 31
```

比如：

```text
Block 2
Thread 3
```

那么：

$$
2\times8+3=19
$$

所以这个线程：

```text
globalIdx = 19
```

可以负责：

```text
data[19]
```

---

# 二十一、这就是最经典的 CUDA 写法

以后你会看到无数次：

```cpp
int idx =
    blockIdx.x * blockDim.x
    + threadIdx.x;

if (idx < N) {
    output[idx] = ...;
}
```

你必须一眼看懂：

```text
第一行：

给当前线程算一个全局编号


第二行：

防止越界


第三行：

这个 Thread 处理对应的数据
```

---

# 二十二、为什么一定要 if (idx < N)？

比如有：

$$
N=1000
$$

个元素。

Block Size：

$$
256
$$

需要多少个 Block？

如果只开：

$$
3
$$

个 Block：

$$
3\times256=768
$$

不够。

所以要开：

$$
4
$$

个 Block。

但是：

$$
4\times256=1024
$$

会产生：

$$
24
$$

个多余线程。

也就是：

```text
Thread 1000
Thread 1001
...
Thread 1023
```

但你的数组只有：

```text
0 ~ 999
```

所以必须：

```cpp
if (idx < N)
```

否则就会访问越界。

---

# 二十三、Block 数怎么计算？

假设：

```text
N 个数据
```

每个 Block：

```text
blockSize 个线程
```

那么需要向上取整：

$$
\mathrm{gridSize}
=
\left\lceil
\frac{N}{\mathrm{blockSize}}
\right\rceil
$$

C++ 里常写：

```cpp
int gridSize =
    (N + blockSize - 1) / blockSize;
```

例如：

$$
N=1000
$$

$$
blockSize=256
$$

那么：

$$
gridSize
=
\frac{1000+256-1}{256}
$$

整数除法以后得到：

$$
4
$$

---

# 二十四、Kernel Launch 的 <<< >>> 是什么意思？

CUDA 有一个非常特殊的语法：

```cpp
kernel<<<gridDim, blockDim>>>(args);
```

例如：

```cpp
doubleArray<<<4, 256>>>(data, N);
```

可以翻译成：

> GPU，执行 `doubleArray` 这个 Kernel。

同时创建：

```text
4 个 Block

每个 Block 256 个 Thread
```

所以总共最多：

$$
4\times256=1024
$$

个 Thread。

---

# 二十五、<<< >>> 里面其实最多有四个参数

完整形式：

```cpp
kernel<<<
    gridDim,
    blockDim,
    sharedMemBytes,
    stream
>>>(args);
```

目前你只需要真正理解前两个：

```text
gridDim
=
有多少个 Block


blockDim
=
每个 Block 有多少个 Thread
```

后面两个：

```text
sharedMemBytes

stream
```

以后再详细学。

---

# 二十六、Kernel Launch 是同步的吗？

不是。

这个地方和你前面学 PyTorch benchmark 直接连起来。

通常：

```cpp
myKernel<<<grid, block>>>(...);
```

CPU 做的更像是：

```text
“GPU，你去执行这个任务。”
```

然后 CPU 不一定站在那里等 GPU 执行完。

而是可能继续往下执行。

也就是：

```text
Kernel Launch 通常是异步的
```

所以：

```text
CPU
↓
Launch Kernel
↓
继续执行后续 CPU 代码


与此同时


GPU
↓
执行 Kernel
```

这也是为什么你之前 benchmark GPU 要使用：

```python
torch.cuda.synchronize()
```

---

# 二十七、cudaDeviceSynchronize 是什么？

CUDA 里面：

```cpp
cudaDeviceSynchronize();
```

大致意思：

> CPU 等一下，等 GPU 前面的工作全部执行完成以后再继续。

所以：

```cpp
kernel<<<...>>>();

cudaDeviceSynchronize();
```

就相当于：

```text
启动 Kernel
↓
CPU 等 GPU 执行完
↓
继续
```

这也常用来检查运行时错误。

---

# 二十八、Kernel 启动错误为什么不一定当场报？

因为：

```text
Kernel Launch 是异步的
```

CPU 把任务发出去以后：

```text
GPU 还没真正执行完
```

所以很多错误可能晚一点才暴露。

原文因此给出了两类检查：

```cpp
cudaGetLastError();
```

用于检查 Kernel Launch 本身的问题。

以及：

```cpp
cudaDeviceSynchronize();
```

等待真正执行以后，再检查运行时错误。

这个你现在先认识即可。

---

# 二十九、Grid 和 Block 为什么还可以是二维、三维？

到现在我们一直是：

```text
1D Grid

1D Block
```

因为处理的是：

```text
一维数组
```

但是 CUDA 支持：

```text
1D
2D
3D
```

主要是为了让数据结构和线程结构更自然地对应。

---

# 三十、为什么处理矩阵时喜欢 2D Block？

假设矩阵：

$$
A\in\mathbb R^{H\times W}
$$

每一个元素有：

```text
row

col
```

所以我们可以直接让一个 Thread 对应一个矩阵元素。

例如：

```cpp
int col =
    blockIdx.x * blockDim.x
    + threadIdx.x;

int row =
    blockIdx.y * blockDim.y
    + threadIdx.y;
```

这样：

```text
x 方向 → column

y 方向 → row
```

非常自然。

---

# 三十一、例如 16 × 16 的 Block

写：

```cpp
dim3 block(16, 16);
```

意味着一个 Block：

```text
x 方向 16 Threads

y 方向 16 Threads
```

所以总线程数：

$$
16\times16=256
$$

然后：

```cpp
dim3 grid(..., ...);
```

可以覆盖整个二维矩阵。

---

# 三十二、二维索引最后为什么又变成一维？

因为内存最终还是：

```text
一长串连续地址
```

例如一个矩阵：

```text
row 0: a b c d

row 1: e f g h
```

在 Row-Major Memory 里可能是：

```text
a b c d e f g h
```

所以二维坐标：

```text
row
col
```

需要转换成：

$$
\mathrm{linearIdx}
=
\mathrm{row}
\times
\mathrm{width}
+
\mathrm{col}
$$

这个和你以前学矩阵存储是一回事。

---

# 三十三、Grid-stride Loop 是什么？

这一篇有一个非常值得你现在理解的 CUDA 编程模式：

```text
Grid-stride Loop
```

普通写法：

```cpp
int idx =
    blockIdx.x * blockDim.x
    + threadIdx.x;

if (idx < N) {
    data[idx] *= 2.0f;
}
```

这里：

> 一个 Thread 只处理一个元素。

但如果：

```text
数据特别特别多
```

你不一定需要：

> 给每一个元素永远对应一个独立 Thread。

可以让：

```text
一个 Thread 处理多个元素。
```

---

# 三十四、Grid-stride Loop 的代码

原文类似：

```cpp
__global__ void processLargeArray(
    float* data,
    int N
) {
    int idx =
        blockIdx.x * blockDim.x
        + threadIdx.x;

    int stride =
        blockDim.x * gridDim.x;

    for (
        int i = idx;
        i < N;
        i += stride
    ) {
        data[i] *= 2.0f;
    }
}
```

重点是：

```cpp
stride =
    blockDim.x * gridDim.x;
```

这是什么？

就是：

> **整个 Grid 的总线程数。**

---

# 三十五、为什么 stride 等于总线程数？

例如：

```text
4 个 Block

每个 Block 8 Thread
```

总线程数：

$$
4\times8=32
$$

所以：

$$
stride=32
$$

假设 Thread 5：

```text
第一次处理：

data[5]
```

下一次：

```text
data[5 + 32]
=
data[37]
```

再下一次：

```text
data[69]
```

所以：

```text
Thread 5：

5
37
69
101
...
```

而 Thread 6：

```text
6
38
70
102
...
```

所有线程合起来就能覆盖整个数组。

---

# 三十六、Grid-stride Loop 为什么很重要？

因为它把：

```text
数据大小
```

和：

```text
启动多少线程
```

解耦了一点。

例如：

$$
N=10^9
$$

你不一定非得启动十亿个逻辑 Thread 才能处理。

可以：

```text
启动适量 Thread
↓
每个 Thread 循环处理多个元素
```

所以它是 CUDA 里面非常常见的模式。

这篇现在至少要做到：

> 看懂它为什么能覆盖整个数组。

---

# 三十七、现在进入 Block Size

你已经知道：

```cpp
kernel<<<gridSize, blockSize>>>();
```

那么很自然会问：

> blockSize 到底填多少？

比如：

```text
32？

64？

100？

128？

256？

512？

1024？
```

这不是随便填的。

---

# 三十八、为什么 Block Size 通常选择 32 的倍数？

因为 GPU 实际执行线程时，有一个非常关键的单位：

```text
Warp
```

一个 Warp：

$$
32
$$

个 Thread。

所以如果：

```text
Block Size = 128
```

那么正好：

$$
128 / 32 = 4
$$

个 Warp。

每一个 Warp 都是完整的。

---

# 三十九、如果 Block Size = 100 呢？

100 个线程需要几个 Warp？

前三个 Warp：

$$
3\times32=96
$$

还剩：

$$
4
$$

个线程。

但硬件还是需要再组织一个 Warp。

所以：

```text
Warp 0 → 32 active threads

Warp 1 → 32 active threads

Warp 2 → 32 active threads

Warp 3 → 只有 4 active threads
```

第 4 个 Warp 的大量 lane 没有对应有效线程。

所以资源利用不理想。

因此常见经验：

```text
Block Size 使用 32 的倍数
```

---

# 四十、那是不是 Block Size 永远填 1024 最好？

不是。

这点非常重要。

虽然一个 Block 最多通常可以有：

$$
1024
$$

个线程，

但是：

> Block 越大不代表性能越好。

因为一个 SM 上的资源是有限的。

例如：

```text
Register 数量有限

Shared Memory 有限

最大 Active Thread 数有限

最大 Active Block 数有限
```

所以一个 Block 吃太多资源，

可能导致：

```text
一个 SM 同时只能住很少的 Block
```

甚至导致并行度下降。

---

# 四十一、原文给出的 Block Size 经验

原文建议：

```text
Block Size 通常选择 32 的倍数
```

并且常见范围：

```text
128 ~ 512
```

简单 Elementwise Kernel 经常会看到：

```text
256

或

512
```

但并不存在：

```text
256 永远最好
```

后面需要结合：

```text
Register 使用量

Shared Memory 使用量

Occupancy

实际 Benchmark
```

来决定。

---

# 四十二、Warp 到底是什么？

现在正式回来讲 Warp。

Block 是：

> CUDA 编程模型里的逻辑协作单位。

Warp 则更接近：

> **GPU 硬件真正调度线程时的重要执行单位。**

一个 Warp：

$$
32
$$

个连续 Thread。

比如 Block 有：

$$
128
$$

个 Thread。

就会形成：

```text
Warp 0:
Thread 0 ~ 31


Warp 1:
Thread 32 ~ 63


Warp 2:
Thread 64 ~ 95


Warp 3:
Thread 96 ~ 127
```

---

# 四十三、SIMT 再理解一次

同一个 Warp 的 Thread 会以 SIMT 模型执行。

SIMT：

```text
Single Instruction
Multiple Threads
```

也就是：

```text
同一个 Warp

32 个 Thread

执行同一种指令

但处理不同数据
```

比如：

$$
y_i=x_i\times2
$$

Warp 里面：

```text
Thread 0:
y[0] = x[0] * 2


Thread 1:
y[1] = x[1] * 2


...


Thread 31:
y[31] = x[31] * 2
```

这就是 GPU 特别擅长的模式。

---

# 四十四、Warp Divergence 是什么？

假设：

```cpp
if (threadIdx.x % 2 == 0) {
    pathA();
} else {
    pathB();
}
```

一个 Warp：

```text
Thread 0  → A

Thread 1  → B

Thread 2  → A

Thread 3  → B

...
```

于是同一个 Warp 里：

```text
一半想执行 A

一半想执行 B
```

这就发生：

```text
Warp Divergence
```

---

# 四十五、为什么 Divergence 会慢？

你可以先粗略理解成：

```text
先执行 A 分支
↓
B 那一半线程暂时不干活

再执行 B 分支
↓
A 那一半线程暂时不干活
```

本来希望：

```text
32 个线程齐步走
```

现在变成：

```text
一部分工作
另一部分等着
```

所以效率下降。

---

# 四十六、不同 Warp 走不同分支有没有问题？

这点特别重要。

假设：

```text
Warp 0 全部走 A

Warp 1 全部走 B
```

这不叫 Warp 内分歧。

真正麻烦的是：

> **同一个 Warp 内部的线程走不同分支。**

所以 Warp Divergence 的分析单位是：

```text
Warp
```

不是整个 Block。

---

# 四十七、Warp Shuffle 是什么？

原文后面提到：

```cpp
__shfl_sync
```

以及：

```cpp
__shfl_down_sync
```

它们让：

> 同一个 Warp 里的 Thread 可以直接交换 Register 中的数据。

例如：

```text
Thread 0 有一个值

Thread 1 想读取它
```

可以通过 Warp Shuffle 完成。

这个后面 Reduce 会非常重要。

你现在不用背 API。

只需要知道：

> **Warp 内线程不仅可以一起执行，还可以通过 Warp-level primitive 高效交换数据。**

后面 Reduce 时你会重新碰到。

---

# 四十八、Block、Warp、Thread、SM 到底是什么关系？

这个关系你必须开始形成。

可以粗略画：

```text
GPU
│
├── SM 0
│
├── SM 1
│
├── SM 2
│
└── ...
```

当 Kernel 启动以后：

```text
Grid
↓
很多 Block
```

这些 Block 会被调度到不同 SM 上。

例如：

```text
Block 0 → SM 0

Block 1 → SM 1

Block 2 → SM 2

Block 3 → SM 0

...
```

一个 Block 一旦被调度到某个 SM：

> 这个 Block 会在这个 SM 上完成。

然后 Block 内：

```text
Thread
↓
按 Warp 分组
↓
SM 调度 Warp 执行
```

所以可以粗略记：

```text
Grid
↓
Block
↓
分配到 SM
↓
Block 内 Thread 组成 Warp
↓
SM 调度 Warp
```

这张图特别重要。

---

# 四十九、注意：Thread 不是一一绑定 CUDA Core

这个很容易误解。

不要想成：

```text
Thread 0 永远对应 CUDA Core 0

Thread 1 永远对应 CUDA Core 1
```

不是这样的。

Thread 是：

```text
逻辑执行单位
```

Warp 是：

```text
硬件调度的重要单位
```

SM 上的执行资源会在不同 Warp / Thread 指令之间被调度使用。

你现在不要建立：

```text
1 Thread = 1 CUDA Core
```

这种错误映射。

---

# 五十、Occupancy 是什么？

这一篇最后开始碰 Occupancy。

这个现在先建立直觉，不需要深挖。

Occupancy 大致定义成：

$$
\mathrm{Occupancy}
=
\frac{\mathrm{Active\ Warps\ on\ SM}}
{\mathrm{Maximum\ Warps\ supported\ by\ SM}}
$$

翻成人话：

> **一个 SM 理论上能同时容纳很多 Warp，现在实际有多少 Warp 在里面处于活跃状态？**

---

# 五十一、为什么要同时放很多 Warp？

因为 GPU 有时候会遇到：

```text
Warp A：

我要的数据还在等 HBM
```

如果 SM 上只有 Warp A：

```text
那计算资源只能干等。
```

但如果还有：

```text
Warp B

Warp C

Warp D
```

那么：

```text
Warp A 等数据
↓
SM 先调度 Warp B
↓
Warp B 等了
↓
再调度 Warp C
```

这样就能通过：

```text
切换 Warp
```

隐藏很多延迟。

这叫：

```text
Latency Hiding
```

这是 GPU 非常重要的思想。

---

# 五十二、所以 Occupancy 越高越好吗？

不一定。

这个非常重要。

高 Occupancy 意味着：

```text
SM 里面有很多活跃 Warp
```

通常有利于：

```text
隐藏延迟
```

但：

```text
Occupancy = 100%
```

不等于：

```text
性能一定最好
```

因为一个高性能 Kernel 也可能：

```text
Occupancy 没有达到 100%

但数据复用特别好

Tensor Core 利用特别高
```

照样很快。

所以：

> Occupancy 是重要指标，但不是最终目标。

真正目标还是：

```text
Kernel 跑得快
```

---

# 五十三、什么东西会限制 Occupancy？

SM 的资源有限。

主要包括：

```text
1. 每个 Thread 用多少 Register

2. 每个 Block 用多少 Shared Memory

3. 一个 Block 有多少 Thread

4. SM 自身最大 Thread / Warp / Block 限制
```

---

# 五十四、Register 为什么会影响 Occupancy？

假设一个 SM 有固定数量 Register。

情况 A：

```text
每个 Thread 只用很少 Register
```

那么一个 SM 可以放很多 Thread。

情况 B：

```text
每个 Thread 使用大量 Register
```

那么 Register 很快被吃完。

于是：

```text
SM 只能同时容纳较少 Thread / Warp
```

所以 Occupancy 下降。

这就是：

```text
Register Pressure
```

开始产生的地方。

后面 2.3 会详细学。

---

# 五十五、Shared Memory 为什么也会影响 Occupancy？

同理。

假设一个 SM 有固定大小 Shared Memory。

如果：

```text
一个 Block 用 20 KB
```

可能可以同时放多个 Block。

但如果：

```text
一个 Block 用 100 KB
```

可能整个 SM：

```text
只能容纳一个 Block
```

那可以同时驻留的 Warp 数就可能降低。

所以 CUDA 优化一直是在做 trade-off：

```text
更多 Register

更多 Shared Memory

更多 Data Reuse

更多 Active Warp
```

这些东西不是越多越好。

要平衡。

---

# 五十六、现在暂时怎么看 Occupancy？

你现在只需要记：

> **一个 SM 上同时驻留足够多 Warp，可以帮助隐藏 Memory / Pipeline Latency。**

但是：

> **Occupancy 不是越高越好。**

然后先继续往下学。

真正深入留到：

```text
2.3 Occupancy 与资源分配
```

那里。

# 六十一、再拿向量乘 2 完整走一次

假设：

$$
N=1000
$$

我们想：

$$
y_i=2x_i
$$

Kernel：

```cpp
__global__ void doubleArray(
    float* x,
    float* y,
    int N
) {
    int idx =
        blockIdx.x * blockDim.x
        + threadIdx.x;

    if (idx < N) {
        y[idx] = 2.0f * x[idx];
    }
}
```

选择：

```cpp
int blockSize = 256;
```

Grid：

```cpp
int gridSize =
    (N + blockSize - 1)
    / blockSize;
```

得到：

$$
gridSize=4
$$

启动：

```cpp
doubleArray<<<4, 256>>>(
    d_x,
    d_y,
    N
);
```

于是：

```text
Grid
│
├── Block 0
│      Thread 0 ~ 255
│
├── Block 1
│      Thread 256 ~ 511
│
├── Block 2
│      Thread 512 ~ 767
│
└── Block 3
       Thread 768 ~ 1023
```

但是：

```text
1000 ~ 1023
```

这些线程没有对应有效数据。

所以：

```cpp
if (idx < N)
```

把它们挡掉。

这就是一个最基本 CUDA Kernel 从：

```text
数据
→ Grid
→ Block
→ Thread
→ Index
```

完整映射的过程。
