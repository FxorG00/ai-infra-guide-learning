---

## 1. `_sync` 不要理解成“额外再执行一次同步”

比如：

```cpp
__shfl_down_sync(mask, val, offset)
```

这里 `_sync` 可以理解成：

> **指定参与这次 Warp-level collective operation 的 Lane。**

这些参与的 Lane 必须以符合要求的方式执行到这个操作。

但不用想成：

```text
先执行一个 __syncwarp()
↓
再执行 shuffle
```

它就是这一条 Warp primitive 本身的同步语义。

你现在的理解已经足够使用了。

---

## 2. Occupancy 那个“400 cycle / 4 cycle = 100 Warp”只是直觉模型

你笔记里写：

```text
Memory Latency = 400 cycles

一个 Warp 提供 4 cycles 工作

所以需要 100 Warp
```

这个可以作为：

```text
为什么需要很多 Warp
```

的直觉。

但不要把：

$$
400 / 4 = 100
$$

当成真正的 Occupancy 计算公式。

因为真实 GPU 还涉及：

```text
多个 Warp Scheduler

Instruction-Level Parallelism

不同指令延迟

Pipeline

Memory-Level Parallelism

一个 SM 本身最大 Warp 数
```

所以你在笔记旁边标一句：

```text
只是 Latency Hiding 的直觉例子，不是真实计算公式。
```

就非常好了。

# 二、为什么并行程序需要同步？

先看最简单的问题。

假设：

```cpp
int counter = 0;
```

两个 Thread 同时执行：

```cpp
counter++;
```

你可能以为：

```text
Thread A:
counter 0 → 1

Thread B:
counter 1 → 2

最终：
counter = 2
```

但实际上：

```cpp
counter++;
```

并不是一个不可分割操作。

它本质上更接近：

```text
Load counter
↓
+1
↓
Store counter
```

于是可能出现：

```text
初始：

counter = 0


Thread A:
读取 counter = 0


Thread B:
读取 counter = 0


Thread A:
0 + 1
写回 1


Thread B:
0 + 1
写回 1
```

最后：

```text
counter = 1
```

而不是：

```text
counter = 2
```

这就是：

```text
Race Condition
```

---

# 三、Race Condition 到底是什么？

可以定义成：

> **多个 Thread 并发访问同一份数据，并且至少一个 Thread 在写，而且最终结果依赖它们的执行时序。**

例如：

```cpp
counter++;
```

多个 Thread 同时做：

```text
Read
Modify
Write
```

就可能产生 Data Race。

---

# 四、为什么这种 Bug 特别恶心？

因为它可能：

```text
这次运行正确

下次运行错误

Debug 模式正确

Release 模式错误

换一张 GPU 又变了
```

原因就是：

> **你不能假设不同 Thread 的具体执行先后顺序。**

比如：

```text
Thread 0
```

不一定比：

```text
Thread 1
```

先执行。

甚至：

```text
Block 0
```

也不一定比：

```text
Block 1
```

先完成。

所以 GPU 编程里面很重要的一句话：

> **不要依赖你没有显式保证的执行顺序。**

---

# 五、同步其实要解决两个不同的问题

原文这里非常重要。

同步不只是：

```text
谁先执行
```

还有：

```text
数据是否已经对别人可见
```

所以可以分成：

```text
1. Execution Ordering

确保：
A 写完
↓
B 再读
```

以及：

```text
2. Memory Visibility

确保：
A 写的数据
↓
B 真正能够看到最新值
```

这两个概念后面：

```text
Barrier

Memory Fence

Atomic
```

一定要区分。

# 七、第一大主角：__syncthreads()

你已经在：

```text
Matrix Transpose

Block Reduce
```

里用过很多次：

```cpp
__syncthreads();
```

现在正式定义它。

一句话：

> **Block 内所有 Thread 都到达这个 Barrier 以后，才能继续往下执行。**

而且：

> **Barrier 之前的内存写入，对于 Block 内其他 Thread 可见。**

---

# 八、最经典的使用场景

比如：

```cpp
__shared__ float smem[256];

int tid = threadIdx.x;

smem[tid] = input[tid];

__syncthreads();

float x = smem[tid ^ 1];
```

为什么一定要同步？

因为：

```text
Thread 0
```

后面可能要读取：

```text
Thread 1
```

刚刚写进去的数据。

但没有同步的话：

```text
Thread 0:
写完 smem[0]
↓
马上读取 smem[1]
```

此时：

```text
Thread 1
```

可能还没完成：

```cpp
smem[1] = ...
```

于是：

```text
Thread 0
```

读到的是：

```text
旧数据
未初始化数据
```

都有可能。

---

# 九、__syncthreads() 可以想成集合点

例如 256 个 Thread：

```text
Thread 0  ----\
Thread 1  -----\
Thread 2  ------\
...              > __syncthreads()
Thread 255 -----/
```

到了这里：

```text
先到的人等
```

直到：

```text
Block 内所有 Thread
```

都到了：

```text
大家再继续
```

所以它是一个：

```text
Barrier
```

---

# 十、你之前的 Matrix Transpose 为什么需要它？

你写过：

```cpp
tile[j + offset][i] =
    A[real_row * M + real_col];

__syncthreads();

C[...] =
    tile[i][j + offset];
```

这里第一阶段：

```text
不同 Thread
↓
共同把 Tile 搬到 Shared Memory
```

第二阶段：

```text
Thread 开始读取其他 Thread 写入的 tile 元素
```

所以中间必须：

```cpp
__syncthreads();
```

确保：

```text
整个 tile
```

已经准备好。

这个你已经理解透了。

---

# 十一、__syncthreads() 最大的陷阱

这个必须记住：

> **同一个 Block 的所有 Thread 必须能够到达同一个 Barrier。**

错误代码：

```cpp
if (threadIdx.x < 128) {
    __syncthreads();
}
```

假设：

```text
Block Size = 256
```

那么：

```text
Thread 0 ~ 127
```

进来了。

但是：

```text
Thread 128 ~ 255
```

根本不会执行这个 Barrier。

于是前 128 个 Thread：

```text
一直等另外 128 个
```

但另外 128 个：

```text
永远不会来
```

结果：

```text
Deadlock / Undefined Behavior
```

---

# 十二、正确做法

把同步移出来：

```cpp
if (threadIdx.x < 128) {
    do_something();
}

__syncthreads();
```

这样：

```text
所有 256 Thread
```

都会到达：

```cpp
__syncthreads()
```

---

# 十三、循环里同样危险

比如：

```cpp
for (
    int i = 0;
    i < length[threadIdx.x];
    ++i
) {
    do_something();

    __syncthreads();
}
```

假设：

```text
Thread 0:
length = 10

Thread 1:
length = 5
```

Thread 1：

```text
第 5 次循环以后退出
```

Thread 0：

```text
第 6 次到达 __syncthreads()
```

然后开始等 Thread 1。

但 Thread 1：

```text
已经退出循环了
```

于是挂住。

---

# 十四、正确原则

如果循环内有：

```cpp
__syncthreads();
```

就要确保：

> **Block 中参与的 Thread 会执行相同数量的 Barrier。**

例如：

```cpp
for (
    int i = 0;
    i < MAX_LEN;
    ++i
) {
    if (i < length[threadIdx.x]) {
        do_something();
    }

    __syncthreads();
}
```

虽然不同 Thread：

```text
实际工作量不同
```

但是：

```text
Barrier 次数一致
```

---

# 十五、__syncthreads() 本身是不是很慢？

Barrier 指令本身不一定特别贵。

真正贵的往往是：

> **等最慢的 Thread。**

例如：

```text
Thread 0 ~ 127
↓
很快到 Barrier


Thread 128 ~ 255
↓
Cache Miss / Divergence
↓
过了很久才到
```

那么前面的 Thread：

```text
一直闲着等
```

---

# 十六、所以 Barrier 的真正性能代价

主要是：

```text
1. 等待最慢 Thread

2. 打断 Pipeline / 指令重排

3. Block 内所有 Warp 必须在这里重新汇合
```

所以：

> **需要同步就同步，但不要没必要地疯狂同步。**

---

# 十七、第二大主角：__syncwarp()

你在 2.1 已经接触过。

形式：

```cpp
__syncwarp(mask);
```

作用范围：

```text
Warp
```

而不是：

```text
Block
```

---

# 十八、为什么以前 Warp 好像不需要同步？

早期 NVIDIA GPU 的 Warp 执行方式非常接近：

```text
32 Threads Lockstep
```

也就是：

```text
Warp 内 Thread
几乎一直执行同一条指令
```

所以程序员以前经常偷懒认为：

```text
Warp 内天然同步
```

比如：

```cpp
smem[threadIdx.x] = value;

float x =
    smem[threadIdx.x ^ 1];
```

以前很多代码直接这么写。

---

# 十九、Volta 之后为什么不同？

Volta 开始引入：

```text
Independent Thread Scheduling
```

所以：

> **不能再假设 Warp 内所有 Lane 永远严格同步到达每一个代码位置。**

如果你：

```text
Warp 内通过 Shared Memory 通信
```

那么正确写法应该是：

```cpp
smem[threadIdx.x] = value;

__syncwarp();

float x =
    smem[threadIdx.x ^ 1];
```

---

# 二十、__syncwarp() 和 __syncthreads() 最大区别

```cpp
__syncwarp()
```

只等待：

```text
指定 Warp 中参与的 Lane
```

而：

```cpp
__syncthreads()
```

等待：

```text
整个 Block
```

所以：

```text
Warp 内协作
↓
优先考虑 Warp-level primitive

Block 内协作
↓
__syncthreads()
```

---

# 二十一、Shuffle 为什么不需要额外 __syncwarp()？

比如：

```cpp
val +=
    __shfl_down_sync(
        mask,
        val,
        offset
    );
```

这里：

```cpp
__shfl_down_sync
```

本身就是：

```text
Warp-level collective operation
```

已经带相应的参与线程同步语义。

所以不用写：

```cpp
__syncwarp();

__shfl_down_sync(...);

__syncwarp();
```

没有必要。

# 二十二、第三大主角：Memory Fence

这一部分非常容易和：

```text
Barrier
```

混淆。

先记住一句：

> **Memory Fence 不是 Barrier。**

也就是说：

```cpp
__threadfence();
```

不会说：

> “所有 Thread 都在这里集合。”

它解决的是：

```text
Memory Ordering / Visibility
```

---

# 二十三、Barrier 和 Fence 的区别

Barrier：

```text
你必须等我
我必须等你
大家到齐再走
```

例如：

```cpp
__syncthreads();
```

而 Fence：

```text
我保证我 Fence 之前的 Memory Operation
在规定范围内按照要求变得可见 / 有序
```

但是：

```text
我不等其他 Thread
```

---

# 二十四、为什么跨 Block 会需要 Fence？

一个 Block 内：

```cpp
__syncthreads();
```

很好用。

但不同 Block 之间：

```text
Block 0
Block 1
Block 2
```

传统 Kernel 中不能直接随便：

```cpp
__syncthreads();
```

因为：

```text
__syncthreads()
只管自己 Block
```

那假设：

```text
Block 0
```

写：

```cpp
partial[0] = result;
```

然后：

```text
Block 5
```

想读取：

```cpp
partial[0]
```

你必须考虑：

```text
写入到底什么时候对 Block 5 可见？
```

---

# 二十五、三个 Fence

原文介绍：

```cpp
__threadfence_block();
```

作用范围：

```text
同一个 Block
```


作用范围：

```text

```


作用范围：

# 二十六、先重点记 __threadfence()

你目前最常遇到的是：

```cpp
__threadfence();
```

可以先理解成：

> **确保当前 Thread 在 Fence 前面的 Global Memory 写入，在后续信号操作之前对 Device 范围正确发布。**

注意：

```text
它不是等待其他 Block
```

这一点必须钉住。

# 二十七、经典问题：跨 Block Reduce

假设有：

```text
100 个 Block
```

每个 Block 先算自己的：

```text
Partial Sum
```

然后：

```text
Block 0 → partial[0]

Block 1 → partial[1]

...

Block 99 → partial[99]
```

接下来：

> **最后完成的 Block 负责把 100 个 Partial Sum 再加一次。**

怎么判断：

```text
谁最后完成？
```

可以使用：

```text
Atomic Counter
```

# 二十八、经典流程

每个 Block 的 Thread 0：

```cpp
partial[blockIdx.x] = block_sum;

unsigned int ticket =
    atomicInc(&block_counter, gridDim.x);
```

这个顺序特别重要：

```text
先写 partial
↓
Fence
↓
再告诉别人：
“我完成了”
```

# 二十九、为什么不能把 Fence 删掉？

假设：

```text
Block A
```

逻辑上执行：

```cpp

atomicInc(&counter);
```

如果没有正确保证：

```text

```

已经对其他 Block 可见，

就可能出现：

```text

```

但另一个 Block 读取：

```text

```

却还没看到最新结果。

于是：

```text
“完成信号”
比
“数据”
先被别人看到
```

这就出 Bug 了。

# 三十一、所以 Fence 最重要的直觉

记成：

# 三十二、第四大主角：Atomic Operation

你之前已经见过：

```cpp
atomicExch(found, tid);
```

现在正式学 Atomic。

定义：

> **Atomic Operation 是不可分割的 Read-Modify-Write 操作。**

例如：

```cpp
atomicAdd(&counter, 1);
```

硬件保证：

```text
读 counter
↓
+1
↓
写回 counter
```

这三个步骤对这个原子操作来说：

```text
不可被其他对同地址的原子修改插进来破坏
```

---

# 三十三、为什么 counter++ 不安全？

普通：

```cpp
counter++;
```

可能：

```text
Thread A:
Load 5

Thread B:
Load 5

Thread A:
Store 6

Thread B:
Store 6
```

最终：

```text
6
```

---

# 三十四、atomicAdd 怎么解决？

```cpp
atomicAdd(&counter, 1);
```

可以粗略想成：

```text
Thread A:
获得这个地址的原子更新权
↓
5 → 6
↓
完成

Thread B:
再来
↓
6 → 7
```

最后：

```text
7
```

结果正确。

---

# 三十五、Atomic 保证的是什么？

非常重要：

Atomic 保证的是：

```text
某一个地址上的某一次原子操作
```

不可分割。

它不是：

```text
整个 Kernel 同步
```

也不是：

```text
所有变量一起变成事务
```

例如：

```cpp
atomicAdd(&A, 1);
B = 100;
```

并不意味着：

```text
A 和 B
```

整体形成一个数据库 Transaction。

不要这样理解。

# 三十七、atomicExch 再看一次

你之前见过：

```cpp
atomicExch(found, tid);
```

它的意思：

```text
原子地把：

*found

替换为：

tid
```

同时返回旧值。

如果多个 Thread 都找到目标：

```text
Thread 20
Thread 35
Thread 98
```

都：

```cpp
atomicExch(found, tid);
```

那么最终：

```text
found 是其中某一个 tid
```

具体哪个：

```text
不保证
```

但：

```text
不会发生破坏性的 Data Race
```

# 三十八、Atomic 最大的问题：Contention

假设：

```text
1,000,000 个 Thread
```

全部：

```cpp
atomicAdd(&counter, 1);
```

它们全在竞争：

```text
同一个地址
```

虽然结果正确，

但是：

```text
访问被大量串行化
```

这就叫：

```text
Atomic Contention
```

---

# 三十九、Atomic 的性能和什么最相关？

核心：

> **有多少 Thread 在竞争同一个地址。**

情况一：

```text
Thread 0 → atomicAdd(&A[0])

Thread 1 → atomicAdd(&A[1])

Thread 2 → atomicAdd(&A[2])
```

地址不同。

冲突很小。

---

情况二：

```text
Thread 0 ─┐
Thread 1 ─┤
Thread 2 ─┤
...       ├→ atomicAdd(&counter)
Thread N ─┘
```

所有人竞争：

```text
同一个地址
```

性能就会非常差。

---

# 四十、所以 Atomic 慢，不是因为“Atomic 这个名字天然慢”

更准确说：

```text
Atomic
+
High Contention
=
慢
```

而：

```text
Atomic
+
Low Contention
```

可能完全可以接受。

这个思维很重要。

---

# 四十一、Shared Memory Atomic 和 Global Atomic

如果地址在：

```text
Global Memory
```

那么 Atomic 需要走更远的 Memory Hierarchy。

如果地址在：

```text
Shared Memory
```

操作可以在：

```text
SM 内
```

完成。

所以一般：

```text
Shared Memory Atomic
```

会比：

```text
Global Memory Atomic
```

便宜很多。

这直接引出了后面的优化策略。

---

# 四十二、atomicCAS 是什么？

CAS：

```text
Compare And Swap
```

接口：

```cpp
atomicCAS(
    addr,
    compare,
    val
);
```

语义可以理解成：

```text
old = *addr

if old == compare:
    *addr = val

return old
```

关键是：

> **整个 Compare + Swap 是原子的。**

---

# 四十三、为什么 CAS 很厉害？

因为很多更复杂的 Atomic 都可以构造为：

```text
读取旧值
↓
算新值
↓
CAS 尝试更新
↓
如果失败
说明别人抢先改了
↓
重新读
↓
再算
↓
再 CAS
```

也就是：

```text
CAS Loop
```

---

# 四十四、CAS Loop 怎么理解？

比如想实现一个特殊 Atomic。

初始：

```text
value = 10
```

Thread A：

```text
读取 10
↓
计算新值 15
```

准备 CAS：

```text
如果当前还是 10
就写成 15
```

但这期间 Thread B：

```text
已经把 10 改成 20
```

于是 A 的：

```text
CAS(10 → 15)
```

失败。

A 得重新：

```text
读取 20
↓
重新计算
↓
再尝试 CAS
```

---

# 四十五、为什么高竞争下 CAS 很慢？

因为：

```text
很多 Thread
↓
同时计算新值
↓
只有少数成功
↓
其他全部失败
↓
重新算
↓
再抢
```

于是：

```text
大量 Retry
```

所以：

> **CAS 可以实现复杂 Atomic，但高竞争时性能可能非常差。**

---

# 四十六、接下来进入这一篇真正重要的优化思想

不要：

```text
所有 Thread
↓
直接竞争一个 Global Atomic
```

而应该：

> **先局部聚合，再逐层汇总。**

你现在已经学会 Warp Reduce。

所以这部分会特别顺。

---

# 四十七、最差方案：所有 Thread 直接 atomicAdd

假设要求：

$$
\mathrm{sum}
=
\sum_i x_i
$$

最简单：

```cpp
atomicAdd(output, x[tid]);
```

假设：

```text
1,000,000 Threads
```

那么：

```text
1,000,000 个 Atomic
```

全部竞争：

```text
output[0]
```

非常惨。

---

# 四十八、第一层优化：Warp Reduce

一个 Warp：

```text
32 Threads
```

先：

```cpp
val = warp_reduce_sum(val);
```

于是：

```text
32 个值
↓
1 个 Warp Sum
```

然后只有：

```text
Lane 0
```

去：

```cpp
atomicAdd(...)
```

Atomic 数量直接减少：

$$
32\times
$$

---

# 四十九、第二层：Block 内聚合

假设：

```text
Block Size = 256
```

有：

```text
8 Warps
```

先：

```text
每 Warp Reduce
```

得到：

```text
8 个 Warp Sum
```

然后：

```text
8 个 Lane 0
```

去更新：

```text
Shared Memory block_sum
```

例如：

```cpp
atomicAdd(&block_sum, val);
```

现在竞争只有：

```text
8 Threads
```

而且是在：

```text
Shared Memory
```

上。

---

# 五十、第三层：Block 结果写 Global

整个 Block 最终得到：

```text
1 个 block_sum
```

然后只有：

```cpp
if (threadIdx.x == 0)
```

执行：

```cpp
atomicAdd(output, block_sum);
```

这样：

```text
原来：

N Threads
↓
N Global Atomics


现在：

Warp Reduce
↓
Block Reduce
↓
GridDim 个 Global Atomics
```

冲突大幅减少。

---

# 五十一、这就是 Hierarchical Reduction

数据层级：

```text
Thread
↓
Warp
↓
Block
↓
Grid
```

Reduction 也按照一样的层级：

```text
Thread Values

↓ Warp Shuffle

Warp Sums

↓ Shared Memory

Block Sum

↓ Global Atomic

Final Sum
```

这是极其重要的 GPU 优化模式。

---

# 五十二、这和你之前写的 Block Reduce 已经完全连起来了

你之前写：

```text
Thread Value
↓
Warp Reduce
↓
每 Warp Lane 0
↓
Shared Memory
↓
第一个 Warp
↓
Block Sum
```

现在只需要再补最后一步：

```text
Block Sum
↓
Global Atomic
↓
Final Sum
```

你就得到一个：

```text
Multi-Block Reduction
```

所以第 3 章 Reduce 你现在已经有很大一部分基础了。

---

# 五十三、第二种 Atomic 优化：Shared Memory Aggregation

经典例子：

```text
Histogram
```

假设：

```text
hist[0]
hist[1]
...
hist[255]
```

每个输入数据：

```text
属于某个 Bin
```

朴素：

```cpp
atomicAdd(
    &hist[data[tid]],
    1
);
```

这是：

```text
Global Memory Atomic
```

---

# 五十四、优化 Histogram

先给每个 Block：

```cpp
__shared__ int local_hist[256];
```

然后：

```text
Block 内 Thread
↓
先更新 local_hist
```

也就是：

```cpp
atomicAdd(
    &local_hist[bin],
    1
);
```

这里 Atomic：

```text
发生在 Shared Memory
```

---

# 五十五、最后才写回 Global

Block 处理完：

```text
local_hist
```

以后，

再：

```cpp
atomicAdd(
    &hist[bin],
    local_hist[bin]
);
```

于是 Global Atomic 从：

```text
每个元素一次
```

变成：

```text
每个 Block / 每个 Bin 一次
```

数量大幅下降。

---

# 五十六、核心思想还是一样

```text
Global Contention
↓
先局部化
↓
Local Aggregation
↓
最后合并
```

这个模式以后你会反复看到。

---

# 五十七、第三种优化：Privatization

更激进一点：

> **先别共享，每个 Thread 自己算自己的。**

例如只有 4 个 Bin：

```cpp
int private_hist[4] = {
    0, 0, 0, 0
};
```

然后：

```cpp
private_hist[data[i]]++;
```

如果这些值能放 Register：

```text
完全没有竞争
```

因为：

```text
每个 Thread
都有自己的 private_hist
```

---

# 五十八、最后才 Atomic

Thread 自己处理很多数据后：

```text
private_hist[0]
private_hist[1]
private_hist[2]
private_hist[3]
```

最后：

```cpp
atomicAdd(
    &hist[bin],
    private_hist[bin]
);
```

于是：

```text
大量 Input
```

变成：

```text
每 Thread 最多几次 Atomic
```

---

# 五十九、Privatization 的本质

原本：

```text
共享状态
↓
大量冲突
```

变成：

```text
私有状态
↓
无冲突计算
↓
最后一次合并
```

代价就是：

```text
Register / Shared Memory 使用增加
```

你应该马上想到：

```text
Occupancy Trade-off
```

没错。

第 2.3 和 2.4 已经连起来了。

---

# 六十、第四种优化：Warp Aggregated Atomic

假设一个 Warp：

```text
32 Threads
```

都想：

```cpp
atomicAdd(counter, 1);
```

朴素：

```text
32 Atomic Operations
```

但我们其实知道：

```text
整个 Warp 一共就是 +32
```

那为什么不能：

```text
先计算有多少 Thread 参与
↓
Leader 一次 atomicAdd(counter, 32)
```

当然可以。

---

# 六十一、先找 Active Mask

```cpp
unsigned active =
    __activemask();
```

得到：

```text
这个 Warp 当前哪些 Lane Active
```

---

# 六十二、找 Leader

```cpp
int leader =
    __ffs(active) - 1;
```

`__ffs`：

```text
Find First Set
```

也就是：

```text
找到最低位的 1
```

比如：

```text
active:
000...00101000
```

找到第一个 Active Lane。

它当：

```text
Leader
```

---

# 六十三、计算有多少 Active Thread

```cpp
int num_peers =
    __popc(active);
```

`__popc`：

```text
Population Count
```

就是：

> **这个 bitmask 里面有多少个 1。**

比如：

```text
32 个 Lane
其中 20 个 Active
```

那么：

```cpp
__popc(active)
```

得到：

```text
20
```

---

# 六十四、Leader 只做一次 Atomic

```cpp
if (lane == leader) {
    old_val =
        atomicAdd(
            counter,
            num_peers
        );
}
```

原来：

```text
20 个 Atomic
```

现在：

```text
1 个 Atomic
```

---

# 六十五、再通过 Shuffle 把结果广播回 Warp

```cpp
old_val =
    __shfl_sync(
        active,
        old_val,
        leader
    );
```

于是整个 Warp 都知道：

```text
Leader AtomicAdd 之前 counter 的值
```

然后每个 Lane 根据：

```text
自己在 Active Thread 中的 Rank
```

计算自己的编号。

这就是：

```text
Warp Aggregated Atomic
```

---

# 六十六、这里你应该发现很多东西开始串起来了

这个技巧同时用了：

```text
__activemask

__ffs

__popc

__shfl_sync

atomicAdd
```

你在 2.1 学的：

```text
Warp Primitive
```

现在开始真正用于：

```text
性能优化
```

这就是为什么前面的基础不是白学的。

# 六十七、第五大部分：Cooperative Groups

原文最后介绍：

```text
Cooperative Groups
```

简称：

```text
CG
```

它解决的问题是：

> **传统 CUDA 同步粒度比较固定。**

例如：

```cpp
__syncthreads()
```

就是：

```text
整个 Block
```

而：

```cpp
__syncwarp()
```

就是：

```text
Warp
```

但如果我想：

```text
16 个 Thread 一组

8 个 Thread 一组

或者自定义 Thread Group
```

怎么办？

Cooperative Groups 就提供更加结构化的 API。

---

# 六十八、基本写法

```cpp
#include <cooperative_groups.h>

namespace cg =
    cooperative_groups;
```

Block：

```cpp
cg::thread_block block =
    cg::this_thread_block();
```

然后：

```cpp
block.sync();
```

可以理解成类似：

```cpp
__syncthreads();
```

---

# 六十九、把 Block 划成 Tile

例如：

```cpp
cg::thread_block_tile<16> tile =
    cg::tiled_partition<16>(block);
```

意思：

```text
把整个 Block
↓
划成多个 16-Thread Group
```

然后：

```cpp
tile.sync();
```

只同步：

```text
这 16 个 Thread
```

而不是：

```text
整个 Block
```

---

# 七十、为什么这种写法不错？

因为代码可以明确表达：

```text
这组 Thread 是一个协作单元
```

例如：

```cpp
warp.shfl_down(...)
```

而不是 everywhere：

```cpp
__shfl_down_sync(
    0xffffffff,
    ...
);
```

代码通常更容易：

```text
封装

复用

推理同步范围
```

---

# 七十一、Cooperative Groups 也可以做 Reduce

例如：

```cpp
cg::thread_block_tile<32> warp =
    cg::tiled_partition<32>(block);
```

然后：

```cpp
for (
    int offset = warp.size() / 2;
    offset > 0;
    offset >>= 1
) {
    val +=
        warp.shfl_down(
            val,
            offset
        );
}
```

逻辑和你现在的：

```cpp
__shfl_down_sync
```

完全一样。

只是 API 更抽象。

---

# 七十二、Grid-level Sync

这一部分你现在浅学即可。

普通 CUDA Kernel：

```text
Block 0
Block 1
Block 2
```

一般不能随便在 Kernel 中做：

```text
全 Grid Barrier
```

但是 Cooperative Groups 支持特殊：

```cpp
grid.sync();
```

让：

```text
整个 Grid
```

同步。

---

# 七十三、但是 Grid Sync 有一个巨大限制

必须保证：

> **参与 Cooperative Grid 的所有 Block 都能够满足 Cooperative Launch 的驻留条件。**

为什么？

想象：

```text
SM 全部已经被前一批 Block 占满
```

这些 Block 到：

```cpp
grid.sync();
```

然后开始等：

```text
“等剩下 Block 也到这里。”
```

但剩下 Block：

```text
还没获得资源
根本还没运行
```

于是：

```text
前面的 Block 不退出
↓
后面的 Block 没资源进来
↓
前面的 Block 又在等后面的 Block
```

这就形成：

```text
Deadlock
```

所以 Grid Sync 和：

```text
Occupancy
```

又直接联系起来了。

---

# 七十四、这篇最容易混的三个概念

现在一定把它们分开。

---

## 1. Barrier

代表：

```text
“大家在这里等。”
```

例如：

```cpp
__syncthreads();
```

---

## 2. Memory Fence

代表：

```text
“保证我之前的 Memory Operation
在规定范围内按要求有序 / 可见。”
```

例如：

```cpp
__threadfence();
```

但：

```text
不等大家
```

---

## 3. Atomic

代表：

```text
“对这个地址的这次 Read-Modify-Write
是不可分割的。”
```

例如：

```cpp
atomicAdd(...);
```

但：

```text
它不是整个 Block Barrier
```

---

# 七十五、用一个非常简单的表记

| 工具 | 核心问题 |
|---|---|
| `__syncthreads()` | 大家到齐了吗？ |
| `__syncwarp()` | 这个 Warp 的参与 Lane 到齐了吗？ |
| `__threadfence()` | 我之前的内存写入是否正确发布？ |
| `atomicAdd()` | 多线程同时改这个地址会不会丢更新？ |

这个表非常值得记。

---

# 七十六、什么时候只需要 __syncthreads()？

例如：

```text
同一个 Block
↓
大家写 Shared Memory
↓
然后互相读取
```

直接：

```cpp
__syncthreads();
```

它同时解决：

```text
Block Barrier
+
Block 内 Memory Visibility
```

---

# 七十七、什么时候只需要 Atomic？

例如：

```text
很多 Thread
↓
只需要对一个 Counter +1
```

你不关心：

```text
谁先谁后
```

只要求：

```text
所有 +1 都不能丢
```

那么：

```cpp
atomicAdd(&counter, 1);
```

就够了。

不需要：

```cpp
__syncthreads();
```

---

# 七十八、什么时候需要 Fence + Atomic？

经典：

```text
Thread / Block
先写一批 Data
↓
然后用 Atomic Counter / Flag
告诉别人：
“数据准备好了”
```

这时候：

```text
Data Write
↓
Fence
↓
Atomic Signal
```

才是正确思路。

---

# 七十九、为什么 Atomic Counter 自己不够？

因为 Atomic 保证：

```text
counter
```

本身的更新正确。

但你真正要保护的逻辑可能是：

```text
partial result
+
counter
```

例如：

```cpp
partial[blockIdx.x] = result;

atomicAdd(&counter, 1);
```

Atomic 只保证：

```text
counter
```

不会丢更新。

它不能自动代表：

```text
partial
```

已经按照你需要的顺序被其他 Block 观察到。

所以：

```text
Fence
```

负责：

```text
数据发布顺序
```

Atomic：

```text
负责 Signal / Counter 安全更新
```

# 八十七、一个非常重要的判断题

下面代码安全吗？

```cpp
__shared__ float smem[256];

smem[threadIdx.x] = value;

float neighbor =
    smem[threadIdx.x ^ 1];
```

答案：

```text
不能依赖它安全。
```

如果是整个 Block 需要协作：

```cpp

```

如果确定：

```text
只在 Warp 内通信
```

可以：

```cpp
__syncwarp();
```

# 九十五、最后把整篇压成 10 句话

第一句：

> **并行程序不能假设不同 Thread 的执行先后顺序。**

第二句：

> **多个 Thread 并发读写同一数据且结果依赖时序时，会出现 Race Condition。**

第三句：

> **`__syncthreads()` 是 Block Barrier，并保证 Barrier 前的 Block 内相关内存写入对其他 Block 内 Thread 可见。**

第四句：

> **`__syncwarp()` 用于 Warp 范围的线程同步。**

第五句：

> **Memory Fence 解决 Memory Ordering / Visibility，不是线程集合 Barrier。**

第六句：

> **Atomic Operation 保证一次 Read-Modify-Write 不可分割。**

第七句：

> **Atomic 是否昂贵主要取决于多少 Thread 在竞争同一地址。**

第八句：

> **最好的 Atomic 优化通常不是“让 Atomic 更快”，而是“减少 Atomic 次数和竞争者数量”。**

第九句：

> **Warp Reduce、Shared Memory Aggregation、Privatization 都是在先局部聚合，再全局合并。**

第十句：

> **Barrier、Fence、Atomic 分别解决“等人”“内存顺序”“同地址竞争”，不要混为一谈。**
