# 2.3 Occupancy 与资源分配：真正理解一个 SM 到底能同时“塞下”多少 Warp

这一篇非常重要。

你前面已经学了：

```text
2.1 Warp 与执行模型
↓
Warp Scheduler
Latency Hiding
Warp Divergence
Warp Shuffle

2.2 内存访问优化
↓
Coalescing
Bank Conflict
Padding
Vectorized Load
```

现在 2.3 要解决一个非常自然的问题：

> **既然 GPU 靠多个 Warp 轮流执行来隐藏延迟，那一个 SM 到底能够同时放多少个 Warp？**

答案不是：

```text
想放多少就放多少
```

而是受 SM 上有限硬件资源约束。

最主要的三个限制就是：

```text
Register

Shared Memory

Block Size / Block 数量
```

所以这一篇最核心的主线是：

```text
SM 有固定资源
        ↓
Block 进入 SM 时要占资源
        ↓
一个 Block 占得越多
        ↓
一个 SM 能同时驻留的 Block 越少
        ↓
Active Warp 越少
        ↓
Occupancy 下降
```

但这一篇还有一个非常重要的反转：

> **Occupancy 不是越高越好。**

这句话一定要真正理解。

---

# 一、先重新理解 Occupancy 是什么

原文用了一个非常好理解的比喻：

```text
SM = 停车场

Warp = 车

SM 最大 Warp 数 = 总车位

当前 Active Warp = 当前停了多少辆车
```

假设一个 SM：

```text
最多能驻留 64 个 Warp
```

现在实际只能驻留：

```text
32 个 Warp
```

那么 Occupancy：

$$
\mathrm{Occupancy}
=
\frac{32}{64}
=
50\%
$$

正式定义就是：

$$
\mathrm{Occupancy}
=
\frac{\mathrm{每个\ SM\ 上活跃\ Warp\ 数}}
{\mathrm{每个\ SM\ 支持的最大\ Warp\ 数}}
$$

---

# 二、这里的 Active Warp 是什么意思？

这里不要把：

```text
Active
```

理解成：

> “这一纳秒正在执行算术指令的 Warp。”

这里更接近：

> **已经驻留在这个 SM 上，有资格被 Warp Scheduler 调度的 Warp。**

比如 SM 上现在有：

```text
Warp 0
Warp 1
Warp 2
...
Warp 47
```

其中：

```text
Warp 0 正在计算

Warp 1 等 HBM

Warp 2 等依赖

Warp 3 Ready

...
```

它们都属于当前驻留在 SM 上的 Warp。

所以 Occupancy 主要描述：

> **SM 里面同时驻留了多少 Warp。**

---

# 三、为什么 Occupancy 会影响性能？

因为你刚在 2.1 学过：

```text
Latency Hiding
```

例如：

```text
Warp A
↓
发起 Global Memory Load
↓
等 HBM
```

如果 SM 上还有很多 Warp：

```text
Warp B
Warp C
Warp D
Warp E
...
```

Scheduler 可以：

```text
Warp A 等
↓
执行 Warp B

Warp B 等
↓
执行 Warp C

Warp C 等
↓
执行 Warp D
```

从而：

```text
不让 SM 白白等待
```

所以：

> **Occupancy 的一个核心意义，就是提供足够多的 Warp 来隐藏延迟。**

---

# 四、Occupancy 高并不是让 Memory Latency 变低

这一点一定要区分。

假设 HBM Load：

```text
需要几百 cycle
```

Occupancy 提高以后：

```text
这个 Load 本身还是几百 cycle
```

并没有变快。

真正变化的是：

```text
Warp A 等待
↓
Warp B 工作
↓
Warp C 工作
↓
Warp D 工作
```

所以：

```text
Latency 没消失
```

而是：

```text
Latency 被别的工作覆盖掉了
```

这就是：

```text
Latency Hiding
```

---

# 五、那是不是 Warp 越多越好？

这正是这一篇后面要回答的问题。

现在暂时先记：

```text
太少 Warp
↓
很难隐藏延迟
↓
可能出现 SM 空等
```

但：

```text
为了追求更多 Warp
↓
强行减少 Register / Shared Memory
↓
又可能让单个 Warp 干活效率下降
```

所以最终是：

```text
Trade-off
```

而不是：

```text
Occupancy = 100%
就是最终目标
```

---

# 六、一个 SM 到底有哪些有限资源？

原文列了 A100、RTX 4090、H100 的资源表。

这里你不用死背具体数字。

你真正要知道 SM 有：

```text
最大 Thread 数

最大 Warp 数

最大 Block 数

Register 总量

Shared Memory 总量

每 Thread 最大 Register 数

每 Block 最大 Thread 数
```

比如按照原文的 A100 示例：

```text
每 SM 最大 Thread：
2048

每 SM 最大 Warp：
64

每 SM 最大 Block：
32

Register：
65536

Shared Memory：
164 KB

每 Block 最大 Thread：
1024
```

这些都是：

> **有限资源。**

---

# 七、为什么 2048 Thread 等于 64 Warp？

因为：

$$
1\ \mathrm{Warp}
=
32\ \mathrm{Threads}
$$

所以：

$$
2048 / 32
=
64
$$

也就是说：

```text
A100 一个 SM

最多 2048 Threads

也就是最多 64 Warps
```

---

# 八、最重要的资源分配原则：以 Block 为单位进入 SM

这是这一篇特别重要的一句话：

> **Block 要么整个进入一个 SM，要么整个不进去。**

不存在：

```text
半个 Block 在 SM 0

另外半个 Block 在 SM 1
```

不行。

一个 Block：

```text
所有 Thread
所有 Warp
所需 Register
所需 Shared Memory
```

必须作为整体驻留到同一个 SM。

---

# 九、这和你之前学的 Block / Shared Memory 直接对应

因为：

```text
Shared Memory
```

本来就是：

```text
Block 级资源
```

一个 Block 内：

```text
所有 Thread
```

共享：

```text
同一份 Shared Memory
```

所以一个 Block 被调度到 SM 后，

SM 必须一次性给它准备：

```text
Thread Slots

Warp Slots

Register

Shared Memory
```

资源。

---

# 十、为什么“整体分配”非常重要？

假设一个 SM 还有：

```text
40 KB Shared Memory
```

但是下一个 Block 需要：

```text
48 KB
```

你不能说：

```text
先塞进去 40 KB

剩下 8 KB 等会儿再说
```

这个 Block 就：

```text
完全进不来
```

于是剩余 40 KB：

```text
可能就闲着
```

所以资源利用存在：

```text
颗粒度
```

和：

```text
碎片
```

问题。

---

# 十一、影响 Occupancy 的三大因素

原文重点讲三个：

```text
1. Register 用量

2. Shared Memory 用量

3. Block 大小
```

接下来分别看。

---

# 十二、第一个因素：Register

你前面已经知道：

```text
Register
=
Thread 私有
```

比如 Kernel：

```cpp
float a;
float b;
float c;
float sum;
```

这些局部变量很多最终可能放到：

```text
Register
```

里。

假设：

```text
每个 Thread 用 64 个 Register
```

那么一个 Warp：

$$
64\times32
=
2048
$$

个 Register。

---

# 十三、为什么 Register 会限制 Warp 数？

假设一个 SM 总共：

$$
65536
$$

个 Register。

每 Warp 需要：

$$
2048
$$

那么最多：

$$
65536 / 2048
=
32
$$

个 Warp。

但是这个 SM 理论最大：

```text
64 Warps
```

所以：

$$
\mathrm{Occupancy}
=
\frac{32}{64}
=
50\%
$$

你现在应该看到核心关系了：

```text
每 Thread Register 越多
↓
每 Warp Register 越多
↓
SM 能容纳的 Warp 越少
↓
Occupancy 越低
```

---

# 十四、极端一点

按照原文 A100 示例：

```text
每 Thread 32 Registers
→ 最多约 64 Warps
→ 100% Occupancy
```

```text
每 Thread 64 Registers
→ 最多约 32 Warps
→ 50% Occupancy
```

```text
每 Thread 128 Registers
→ 最多约 16 Warps
→ 25% Occupancy
```

趋势非常明显：

$$
\mathrm{Registers/Thread}\uparrow
$$

通常意味着：

$$
\mathrm{Occupancy}\downarrow
$$

---

# 十五、但真实 Register 分配还存在 Granularity

现实并不是：

```text
需要 1301 个 Register
硬件就刚好分配 1301 个
```

硬件会按照一定：

```text
Allocation Granularity
```

分配。

原文这里以：

```text
每 256 Registers
```

作为一个 Warp 的分配粒度。

所以可以理解成：

$$
\mathrm{WarpRegs}
=
\left\lceil
\frac{
\mathrm{RegsPerThread}\times32
}{
256
}
\right\rceil
\times256
$$

例如需要：

```text
8160 Registers
```

可能实际上分配：

```text
8192
```

所以实际 Occupancy 计算不是完全连续变化的。

而是会出现：

```text
台阶
```

---

# 十六、这是什么意思？

例如你把：

```text
每 Thread Register
```

从：

```text
40
```

改成：

```text
41
```

性能和 Occupancy 不一定只变化一点点。

有可能刚好跨过某个资源分配边界：

```text
原本一个 SM 能塞 6 Blocks

↓

突然只能塞 5 Blocks
```

所以 CUDA Performance 经常出现：

> **改一点代码，Occupancy 突然掉一档。**

---

# 十七、那我们是不是应该疯狂减少 Register？

不是。

这是这一篇最容易踩的坑。

因为 Register 是：

```text
最快的 Thread Private Storage
```

如果你强行让编译器少用 Register，

那些变量总得放别处。

可能发生：

```text
Register Spilling
```

---

# 十八、Register Spilling 再复习一次

正常：

```text
变量
↓
Register
```

非常快。

Register 不够：

```text
变量
↓
Local Memory
```

但你已经知道：

```text
Local Memory
```

名字虽然叫 Local，

实际背后在：

```text
Global Memory / Cache 路径
```

一侧。

所以：

```text
Register Access
```

变成：

```text
Memory Access
```

性能可能反而暴跌。

---

# 十九、所以 Register 的 Trade-off 是什么？

左边：

```text
Register 多
↓
Thread 计算舒服
↓
变量留在 Register
↓
少访问 Memory
```

但：

```text
Occupancy 下降
```

右边：

```text
Register 少
↓
Occupancy 上升
```

但如果太少：

```text
Register Spill
↓
Local Memory
↓
反而变慢
```

所以正确目标不是：

```text
Register 越少越好
```

而是：

> **在足够 Occupancy 和足够 Register 之间找平衡。**

---

# 二十、__launch_bounds__ 是干什么的？

原文介绍：

```cpp
__launch_bounds__(
    maxThreadsPerBlock,
    minBlocksPerMultiprocessor
)
```

例如：

```cpp
__global__
__launch_bounds__(256, 2)
void my_kernel(...) {
    ...
}
```

可以大致理解成告诉编译器：

```text
这个 Kernel：

Block 最大大约 256 Threads

我希望一个 SM 至少能驻留 2 个 Block
```

于是编译器在分配 Register 时：

```text
不能太任性
```

否则一个 Block 用太多 Register，

两个 Block 就塞不进 SM 了。

---

# 二十一、原文的 A100 示例怎么理解？

假设：

```text
SM Register 总量
=
65536
```

要求：

```text
256 Threads / Block

至少 2 Blocks / SM
```

那么同时需要容纳：

$$
256\times2
=
512
$$

个 Thread。

平均每 Thread 能使用的 Register 上限大致：

$$
65536 / 512
=
128
$$

所以编译器需要控制 Register 使用。

---

# 二十二、但 __launch_bounds__ 不是免费午餐

如果：

```text
Kernel 本来真的需要很多 Register
```

你为了 Occupancy 强行限制它：

```text
Register 不够
↓
Spill
↓
Local Memory
↓
Memory Traffic 增加
```

可能比原来：

```text
低 Occupancy
```

还慢。

所以原文特别强调：

> **最后一定要 Profile / Benchmark。**

---

# 二十三、第二个因素：Shared Memory

你已经知道：

```text
Shared Memory
=
Block 级资源
```

假设一个 Block 用：

```text
64 KB Shared Memory
```

一个 SM 总共：

```text
164 KB
```

那么理论上：

$$
\left\lfloor
\frac{164}{64}
\right\rfloor
=
2
$$

所以最多只能放：

```text
2 Blocks
```

---

# 二十四、为什么第三个 Block 放不进去？

两个 Block 已经使用：

$$
2\times64
=
128\ \mathrm{KB}
$$

剩下：

$$
164-128
=
36\ \mathrm{KB}
$$

但第三个 Block 需要：

```text
64 KB
```

所以：

```text
放不进去
```

剩下那 36 KB：

```text
只能闲置
```

这又体现：

> **Block 是整体分配的。**

---

# 二十五、Shared Memory 如何影响 Occupancy？

假设每 Block：

```text
256 Threads
=
8 Warps
```

如果因为 Shared Memory 限制，

一个 SM 只能放：

```text
2 Blocks
```

那么：

$$
2\times8
=
16\ \mathrm{Warps}
$$

如果 SM 最大 64 Warp：

$$
\mathrm{Occupancy}
=
\frac{16}{64}
=
25\%
$$

所以：

```text
Shared Memory / Block 越大
↓
SM 能驻留的 Block 越少
↓
Warp 越少
↓
Occupancy 越低
```

---

# 二十六、这和 Tiling 发生直接冲突

你在 2.2 学过：

```text
Tile 做大
↓
Shared Memory 放更多数据
↓
Data Reuse 更强
↓
HBM Traffic 更少
```

听起来：

```text
Tile 越大越好
```

但现在发现：

```text
Tile 越大
↓
Shared Memory / Block 越多
↓
Block / SM 越少
↓
Occupancy 越低
```

所以又出现 Trade-off：

```text
大 Tile
=
高 Data Reuse
+
低 Occupancy

小 Tile
=
低 Data Reuse
+
高 Occupancy
```

这就是后面 GEMM 优化最核心的权衡之一。

---

# 二十七、第三个因素：Block Size

你以前一直听：

```text
blockSize = 256
```

现在终于开始理解为什么 256 经常是一个不错的默认值。

Block Size 太小，也可能让 Occupancy 上不去。

---

# 二十八、为什么 Block 太小反而不好？

假设：

```text
Block Size = 32
```

也就是：

```text
1 Block
=
1 Warp
```

A100 按原文：

```text
每 SM 最大 Block 数
=
32
```

那么即使：

```text
Register 足够
Shared Memory 也足够
```

你最多也只能放：

```text
32 Blocks
```

因为一个 Block 只有 1 Warp：

```text
32 Blocks
=
32 Warps
```

但 SM 最大：

```text
64 Warps
```

所以：

$$
\mathrm{Occupancy}
=
50\%
$$

---

# 二十九、也就是说限制你的不是 Thread 数

而是：

```text
每 SM 最大 Block 数
```

这个硬件限制。

这非常容易被忽略。

你可能觉得：

> “我的 Block 很小，很省资源，应该 Occupancy 特别高。”

结果：

```text
Block 太小
↓
需要很多 Block 才能填满 SM
↓
但 SM 能容纳的 Block 数本身有限
↓
填不满 Warp Slots
```

---

# 三十、为什么 64 Threads 就可能好很多？

如果：

```text
Block Size = 64
```

那么：

```text
一个 Block
=
2 Warps
```

32 Blocks：

$$
32\times2
=
64\ \mathrm{Warps}
$$

正好填满。

当然现实中还要考虑：

```text
Register
Shared Memory
其他硬件限制
```

但单看 Block Count：

```text
64 Threads
```

就比：

```text
32 Threads
```

更容易把 Warp Slots 填满。

---

# 三十一、为什么原文推荐 128 或 256？

因为这两个通常是一个比较舒服的范围：

```text
128 Threads
=
4 Warps

256 Threads
=
8 Warps
```

一个 Block 自带多个 Warp，

但又不会像：

```text
1024 Threads
```

那样一个 Block 太巨大。

所以原文给的经验是：

> **通常 256 是一个不错的默认 Block Size。**

注意：

```text
默认
≠
永远最佳
```

最终还是要测。

---

# 三十二、现在进入最重要的部分：Occupancy 到底怎么计算？

你可以把问题想成：

> **一个 SM 最多到底能驻留多少 Warp？**

然后分别从不同资源角度计算：

```text
Register 允许多少？

Shared Memory 允许多少？

Thread 数允许多少？

Block 数允许多少？
```

最后：

> **谁最小，谁就是瓶颈。**

但是还没完。

因为最后还要满足：

```text
Block 整体进入
```

这个条件。

---

# 三十三、原文的综合例子

条件：

```text
A100

每 Thread：
40 Registers

Block Size：
256 Threads
=
8 Warps

每 Block Shared Memory：
16 KB
```

然后一步一步算。

---

# 三十四、第一步：Register 限制

每 Warp：

$$
40\times32
=
1280
$$

个 Register。

SM 总共有：

$$
65536
$$

所以 Register 角度最多：

$$
\left\lfloor
\frac{65536}{1280}
\right\rfloor
=
51
$$

个 Warp。

也就是：

```text
Register 说：
最多 51 Warps
```

---

# 三十五、第二步：Shared Memory 限制

一个 Block：

```text
16 KB
```

SM：

```text
164 KB
```

所以：

$$
\left\lfloor
\frac{164}{16}
\right\rfloor
=
10
$$

个 Block。

一个 Block：

```text
8 Warps
```

所以理论对应：

$$
10\times8
=
80
$$

个 Warp。

也就是：

```text
Shared Memory 说：
最多 80 Warps
```

当然后面还有最大 Warp / Thread 限制。

---

# 三十六、第三步：Thread / Warp 硬件上限

A100：

```text
最大：
2048 Threads
=
64 Warps
```

所以：

```text
Hardware Limit：
64 Warps
```

---

# 三十七、先取最小值

现在三个答案：

```text
Register：
51 Warps

Shared Memory：
80 Warps

Hardware：
64 Warps
```

所以：

$$
\min(51,80,64)
=
51
$$

看起来：

```text
51 Warps
```

---

# 三十八、但是不能真的放 51 Warp

为什么？

因为：

```text
1 Block
=
8 Warps
```

Block 必须整个进去。

不能：

```text
6 个完整 Block
+
3 个 Warp
```

最后那 3 个 Warp 没办法脱离 Block 单独进入。

所以：

$$
\left\lfloor
\frac{51}{8}
\right\rfloor
=
6
$$

个完整 Block。

实际：

$$
6\times8
=
48
$$

Warps。

所以 Occupancy：

$$
\frac{48}{64}
=
75\%
$$

---

# 三十九、这个例子特别重要

因为它告诉你：

> Occupancy 不能只简单算“总资源 / 单 Thread 资源”。

还要考虑：

```text
Warp 粒度

Block 粒度

Register 分配粒度

Shared Memory 分配粒度
```

最终真正驻留的是：

```text
完整 Block
```

---

# 四十、你现在可以建立 Occupancy 的通用算法

以后看到一个 Kernel，可以这么想：

```text
Kernel 配置
↓
Block Size
Regs / Thread
Shared Memory / Block
↓
分别计算：
Register Limit
Shared Memory Limit
Thread Limit
Block Count Limit
↓
取最严格限制
↓
再按照完整 Block 对齐
↓
得到 Active Warps
↓
除以 SM 最大 Warps
↓
Occupancy
```

---

# 四十一、CUDA 可以帮我们自动算吗？

可以。

原文介绍：


# 四十三、另一个 API

原文还给：


# 四十五、为什么 33% Occupancy 可能比 100% 更快？

原文给了矩阵乘例子。

Version A：

```text

Shared Memory 少

Occupancy：
100%
```

Version B：

```text

Shared Memory 多

Occupancy：
33%
```

结果可能：


因为 B：

```text

↓
更多数据复用
↓
```

```text

```

所以虽然：

```text

```

但：

```text

```

最终反而更快。

# 四十七、强行追求高 Occupancy 的第一个代价：Register Spilling

比如你发现：

```text

↓

```

```text

```

但是：

```text

```

于是：

```text

```

性能反而掉了。

# 四十八、第二个代价：Shared Memory Reuse 降低

例如 GEMM：

原本：

```text

```

Shared Memory 比较大。

为了提高 Occupancy：

```text

```

现在一个 SM 可以塞更多 Block。

Occupancy：

```text

```

但是：

```text

↓
Global Memory Load 增多
↓
Memory Traffic 增加
```

最后可能更慢。

---

# 四十九、第三个代价：Cache Thrashing

如果同时驻留特别多 Warp：

```text
大家都在访问不同数据
```

可能会争抢：

```text

L2
```

有限 Cache。

于是：

```text
刚加载进 Cache
↓
很快又被别人挤出去
↓
Cache Miss 增加
```

原文称：

```text
Cache Thrashing
```

所以：

```text
更多并行
```

并不天然等于：

```text
更高性能
```

# 五十、什么时候 Occupancy 特别重要？

原文列出的典型场景是：

```text

+

数据复用低
```

例如：

```text

Activation
```

因为它们：

```text

↓

↓
```

几乎没有太多：

```text

```

这种时候最重要的是：


所以足够高的 Occupancy 很有价值。

# 五十一、什么时候低 Occupancy 可以接受？

原文给：




已经够了。

# 五十四、ILP 是什么？

原文这里出现：

```text
ILP
```

全称：

```text
Instruction-Level Parallelism
```

你现在简单理解：

> **同一个 Thread / Warp 内，有多少互相独立的指令可以同时推进。**

比如：

```cpp
a = x1 * y1;
b = x2 * y2;
c = x3 * y3;
d = x4 * y4;
```

如果这些彼此独立，

硬件有机会：

```text
同时推进多个独立操作
```

这就是 ILP。

---

# 五十五、ILP 和 Occupancy 都可以帮助隐藏延迟

假设：

```text

```

你可以：

```text

↓
切 Warp B
```

这属于：

```text

```

但如果一个 Warp 自己就有很多独立指令：

```text

同时算 B

同时算 C
```

也能在一定程度上覆盖等待。

所以：

```text
Occupancy
```

不是唯一的 Latency Hiding 手段。



所以整体性能依然非常强。

最终目标不是：

```text
Occupancy 最大
```

而是：

```text
Kernel Performance 最大
```

# 八十二、把它和 GEMM 提前连接起来

Tile 大：


Tile 小：

```text

Register 更少

Occupancy 更高

```

```text
Sweet Spot
```

# 八十三、把它和 FlashAttention 提前连接起来

FlashAttention 也是：

```text

↓
减少 HBM Traffic
```

因此：

```text
Shared Memory / Register Usage
```

通常非常关键。

它完全可能：

```text

```

```text

```

```text
高性能 Kernel Occupancy 只有 30%
```

不要第一反应觉得：

```text

```

可能恰恰相反。

# 八十五、最后把整篇压成 10 句话

第一句：

> **Occupancy = 一个 SM 上 Active Warp 数 / 该 SM 最大 Warp 数。**

第二句：

> **Occupancy 的核心意义是提供足够多 Warp 来隐藏执行和内存访问延迟。**

第三句：

> **一个 Block 必须作为整体驻留到一个 SM。**

第四句：

> **Register 用得越多，一个 SM 通常能容纳的 Warp 越少。**

第五句：

> **Shared Memory / Block 越大，一个 SM 通常能驻留的 Block 越少。**

第六句：

> **Block 太小也可能因为每 SM 最大 Block 数限制而无法填满 Warp Slots。**

第七句：

> **Register 太少可能导致 Spilling，所以不能为了 Occupancy 无脑压 Register。**

第八句：

> **大 Tile 虽然降低 Occupancy，却可能通过更高 Data Reuse 大幅减少 HBM Traffic。**

第九句：

> **Memory-Bound、低复用 Kernel 通常更依赖高 Occupancy；GEMM、FlashAttention 等高复用 Kernel 可以接受较低 Occupancy。**

第十句：

> **最终优化目标不是 Occupancy 最大，而是实际 Kernel 吞吐量最大。**
